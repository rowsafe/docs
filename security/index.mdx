Rowsafe is built so that the hosted service never needs your data or your secrets. The part that touches your data, the agent, is [open source](https://github.com/rowsafe/rowsafe) under Apache-2.0, so you can read exactly what runs on your servers.

## What runs on your server

- **The agent** (`rowsafe-agent`), as the `postgres` system user. It refuses to run as root.
- **pgBackRest**, which the agent and PostgreSQL's `archive_command` run.
- A systemd unit with `NoNewPrivileges`, a read-only system except its own directories, a private `/dev`, no capabilities and restricted address families. The kernel's out-of-memory killer picks the agent before production PostgreSQL, and it gets half the default CPU and IO weight.
- **Only if you allow it at install**, a small root helper, `rowsafe-pg-restart`, the one part that runs as root. It restarts, stops or starts PostgreSQL when a person asked for it (Restart, and Rewind the whole database). It reads the agent's request with the agent's own privileges, accepts one strict line, and acts only on the PostgreSQL units that root listed in `/etc/rowsafe/restart-allowed` at install. Restarts happen at most once a minute.

The agent:

- connects to PostgreSQL **only over the local Unix socket**, as the `postgres` role (a superuser is needed for `ALTER SYSTEM` and backups);
- makes **only outbound HTTPS requests**, to `api.rowsafe.sh` and your bucket (or Rowsafe Storage). Nothing listens on your server;
- runs **only a fixed set of tasks**: inspect, adopt (plan or apply), check, backup, drill (Proof), restore point (Mark), restart (only on a server where you allowed it), maintenance, a short list of fixes described below, and PostgreSQL updates and upgrades, security updates and reboots (only on a server where you allowed them), and Databases & users (create or remove databases, users and extensions, when a person asks), the [standby](/docs/guides/standby) tasks, and the Rewind tasks: restore a copy, compare, bring back rows, rewind in place, undo and clean up. It never runs commands or SQL sent over the network.

Proof, the weekly restore test, restores your data onto the same server, into a scratch cluster with no network listener, and deletes it afterwards. A Rewind copy is restored the same way and kept until it expires (24 hours by default, at most 7 days); the agent deletes it on time even when it can't reach Rowsafe.

**Rewind runs only when a person asks.** Restoring a copy, bringing rows back, rewinding a whole database, undoing it and deleting the data kept aside all start from the dashboard or `rowsafe rewind`, by an owner or admin. Bringing rows back and rewinding ask you to type the database name, and Rowsafe saves a Mark first. The comparison and the rows stay on your server: only table names, counts and sizes reach Rowsafe. Read-only API keys and the MCP server (AI agents) can't do any of it. See [Restore a database](/docs/guides/restore).

**Fixes run only when a person asks.** Rowsafe can run a fixed set of maintenance actions: `VACUUM` and `ANALYZE` tables, `REINDEX INDEX CONCURRENTLY`, `DROP INDEX CONCURRENTLY`, cancel a query (`pg_cancel_backend`), end a session (`pg_terminate_backend`) and drop an inactive replication slot. It never runs them on its own: only when an owner or admin clicks **Apply fix** in the dashboard (or runs `rowsafe fix`) and confirms. The service proposes each fix from a health finding and the client can only pick one by its ID, never send SQL or object names. The agent checks again right before it runs: the object still exists, the session is still the same one and isn't a Rowsafe, replication or autovacuum session, the slot is still inactive, and an index that backs a constraint is never dropped. Before dropping an index, Rowsafe saves a Mark so you can restore to just before it. Read-only API keys and the MCP server (AI agents) can't apply fixes. See [Apply fix](/docs/guides/monitoring#apply-fix).

**Updates are opt-in, per capability.** Rowsafe installs PostgreSQL's minor releases, upgrades PostgreSQL to a new major, installs the server's security updates or reboots the server only when someone clicks it (or opted a database in to automatic minor updates) and confirms, and only what you allowed during install: `--allow-updates`, `--allow-security-updates` and `--allow-reboot`, each off by default without a terminal. A root helper does it, from a fixed list of requests it checks against root's allow lists; it builds the package names itself (only PostgreSQL's own packages for an update or upgrade, only upgrades from the security repository for security updates) and never runs a command it was sent. Rowsafe saves a Mark first, and a major upgrade needs a passed rehearsal on a restored copy. See [Update and upgrade PostgreSQL](/docs/guides/updates).
**Databases and users change only when a person asks.** Rowsafe can create and remove databases, users and extensions inside your PostgreSQL server, and set new passwords, only when an owner or admin clicks and confirms in the dashboard (removing a database asks for its name, and saves a Mark first) or uses the CLI with a read-write API key. The agent checks every name against the catalogs and builds the statements itself; it never removes PostgreSQL's own databases, superusers, its own user or Rowsafe's. New passwords are **end-to-end encrypted to your browser**: it makes a one-time key pair whose private key never leaves its memory, the agent encrypts the password to it (ECDH P-256, HKDF-SHA256, AES-256-GCM), and Rowsafe only relays the ciphertext once, then deletes it. PostgreSQL stores only a SCRAM verifier, so the password isn't in any statement or log. AI agents (MCP) can only read the list. See [Create databases and users](/docs/guides/databases-and-users).
**Standby secrets move only between your servers.** A standby needs your bucket settings, your passphrase and a replication password. Each agent has its own X25519 key pair (the private key never leaves the server); the primary's agent encrypts what the standby needs to the standby agent's key, and Rowsafe only relays the encrypted box. You confirm the standby's key fingerprint before pairing, and every handoff is logged on the primary with the fingerprint it was sealed to. Because Rowsafe relays the keys, a compromised Rowsafe service could present a key of its own. On servers where that matters, set `ROWSAFE_STANDBY=pinned` with the fingerprints of your own servers in `ROWSAFE_STANDBY_PEERS`, or `ROWSAFE_STANDBY=off`: then the agent itself refuses any other key. See [agent configuration](/docs/reference/agent-configuration#postgresql-and-the-server).

**Restarts are opt-in.** Rowsafe never restarts or stops PostgreSQL on its own. It restarts it only when someone clicks **Restart** in the dashboard (or runs `rowsafe restart`) and confirms, and stops and starts it only to rewind the whole database (or undo that), and only on servers where you allowed it during install ("Allow Rowsafe to restart or stop PostgreSQL when you ask?"). The installer asks; `--no-allow-restart` answers no and removes the helper. The installer itself can also restart PostgreSQL during setup, when you answer yes on the server. Only admins and owners can restart, never with a read-only API key or through MCP, and at most once every 2 minutes. In Docker, Rowsafe can restart or stop PostgreSQL only if you add the optional container control service, which alone holds the Docker socket and acts on that one container; see its [threat model](/docs/guides/docker#threat-model).

**Moving a database in needs a person and your password, which Rowsafe never sees.** [Move in](/docs/guides/move-in) starts only when an owner or admin pastes a connection string; the browser (or the CLI) encrypts it to a key the agent on your server made for that move, and Rowsafe relays only ciphertext. The password stays on your server in a 0600 file until you finish. The new login's connection string is encrypted on your server to a key your browser holds and shown once. AI agents on MCP can't start or change a move.

## What Rowsafe can and can't do

Someone who controlled the Rowsafe service, or held one of your API keys, **could**:

- queue the fixed tasks for your databases: plans, backups, checks, Proof runs and Marks, and apply an adoption plan (which sets `archive_mode`, `archive_command`, `archive_timeout` and, if it is `minimal`, `wal_level`);
- restart PostgreSQL, a few seconds of downtime, but only on a server where you allowed restarts during install;
- restore copies of your databases next to production (they use disk and some CPU until they expire), compare them with production, and bring rows back from a copy: insert rows that are missing in production, or set changed rows back to their older values. It never deletes rows this way;
- on a server where you allowed restarts, rewind a whole database to an earlier moment (downtime while it restores), and delete the data kept aside for undo. Every change is still in your bucket until retention removes it, so you could still [restore it by hand](/docs/guides/restore#advanced-restore-by-hand-or-to-another-server);
- on a server where you allowed it: install PostgreSQL's minor releases (a restart), upgrade PostgreSQL to a newer major after a rehearsal (minutes of downtime; undo for 7 days), install the server's security updates, or reboot the server;
- create databases, users and extensions, give a user access to databases, remove a user (handing what it owns to another user) or a database (after a Mark), or set a new password on an existing user, which locks out apps using the old one until they get the new one. They could not read a password Rowsafe made: it is encrypted to the browser or CLI that asked;
- with standby servers (`ROWSAFE_STANDBY=on`, the default): promote a standby, which stops the old primary for good, even where restarts aren't allowed; and pair a server of its own as a standby, which would receive the bucket settings. `ROWSAFE_STANDBY=pinned` or `off` rules both out;
- run the maintenance actions above: vacuum or analyze tables (extra load while they run), rebuild or drop indexes (queries that used a dropped index get slower until you recreate it), cancel queries or end sessions (an open transaction is rolled back, so its uncommitted changes are lost), and drop an inactive replication slot (whatever read from it has to start over);
- during a move you started, switch it over (the old database goes read-only until you make it writable again) or cancel it (deleting the partial copy on your server);
- read metadata: server and database names and sizes, table counts, PostgreSQL settings, task logs, metrics and long-running query text (unless you [turn it off](/docs/guides/monitoring#privacy));
- withhold agent updates, or offer a release that was properly signed but is known to be bad. Agents still self-test it, put it on probation and roll back;
- with [Rowsafe Storage](/docs/guides/rowsafe-storage) only: delete or withhold your backups, because Rowsafe runs that bucket. They still couldn't read them. If that matters to you, use your own bucket.

They **could not**:

- run arbitrary commands or SQL on your server;
- read your backups: they are encrypted with a passphrase that never leaves your server, except encrypted to another of your servers' agents when you set up a standby (see above);
- with your own bucket, reach it at all: its keys never leave your server, except in that same way;
- make an agent run a binary that wasn't signed with Rowsafe's release key, or downgrade an agent;
- restart PostgreSQL on a server where you didn't allow it, or stop it, except to fence an old primary after a standby promotion (see above);
- install or remove packages other than PostgreSQL's own and the security repository's upgrades, downgrade PostgreSQL, or do any of the updates on a server where you didn't allow them;
- read your rows: comparisons and restores run on your server and report only counts and sizes;
- drop a table: the maintenance actions never touch table data, and an index that backs a primary key, unique or exclusion constraint is never dropped (removing a whole database is the exception above, always after a Mark);
- change settings other than the archiving settings above.

## Encryption

- Backups and WAL are compressed, then **encrypted on your server** with `aes-256-cbc`, using your passphrase, before they are uploaded. Your bucket, or Rowsafe Storage, holds only ciphertext.
- The passphrase and the bucket keys live **only on your server**, in `/etc/rowsafe/agent.env` and the generated pgBackRest configuration, both mode 0600 and owned by `postgres`. Anyone who can become `postgres` can already read the database itself.
- Rowsafe can't recover a lost passphrase. Keep it in your secret manager.
- All traffic between the agent, the CLI and Rowsafe uses HTTPS.

## Credentials

| Credential | Prefix | Held by | Allows |
|---|---|---|---|
| API key | `rsk_` | You: CLI, scripts, CI, AI agents | The Rowsafe API for one organization. Read-only keys can only read. |
| Enrollment token | `rse_` | The installer, once | Enrolling one host. Single use, 1 hour by default. |
| Agent token | `rsa_` | `/var/lib/rowsafe/agent.json` (0600) | The agent API for one host: its own tasks and heartbeats. |
| Bucket keys | | `agent.env` and pgBackRest configuration, on your server | Your bucket. |
| Rowsafe Storage credentials | | `/var/lib/rowsafe/storage-credentials.json` and pgBackRest configuration (0600), on your server | Your organization's space in Rowsafe Storage only, for 7 days; renewed daily. |
| Encryption passphrase | | The same files, and your secret manager | Decrypting every backup. |

Rowsafe stores only SHA-256 hashes of API keys, enrollment tokens and agent tokens.

## Signed releases

The installer and the agent only install releases signed with Rowsafe's Ed25519 release key, which is built into them and never stored on the Rowsafe service. Every release also has build provenance, an SBOM and reproducible builds that you can check yourself: see [Verifying releases](/docs/security/verifying-releases).

## Webhooks

Webhook notifications are signed with a per-channel secret ([verify them](/docs/reference/webhooks#verify-the-signature)). Rowsafe only sends them to public `https` URLs, checks every address after DNS resolution, and never follows redirects.
