description: Guard is Rowsafe's safety net for coding agents that run migrations and SQL. Check that the database is safe, set a Mark, then proceed.
---

Coding agents run migrations, backfills and ad-hoc SQL, often without a person watching each command. When one goes wrong (a migration that drops the wrong column, a `DELETE` that lost its `WHERE`, `prisma migrate reset` against the wrong `DATABASE_URL`), what matters is whether you can get back to the moment before.

**Guard** gives you that moment. Before a risky change, the agent asks Rowsafe "is it safe?" (could this database be restored right now?) and sets a [Mark](/docs/concepts/restore-points), a named restore point. If something breaks, you know exactly where to rewind to.

Guard is three things you can combine: the MCP tools, a Claude Code hook (`rowsafe guard`), and a snippet for your agent instructions. For migrations your CI runs, the [GitHub Action](/docs/guides/deploys) saves a Mark before every deploy.

## The workflow

Before any destructive or risky database operation:

1. **Is it safe?** `safety_check` (or `rowsafe status app`) answers "could this database be restored right now?". If not, the agent tells you why and waits for your OK.
2. **Set a Mark** with a descriptive name: `create_restore_point` (or `rowsafe mark app before-drop-orders`). It waits until the Mark is in your bucket, and tells you its name.
3. **Proceed.**
4. **If something breaks, stop.** The agent doesn't try to repair data and never restores anything unless you say so. It tells you the Mark, and you decide whether to [rewind](/docs/guides/restore): in the dashboard, restore a copy at that Mark and bring back what was lost, or rewind the whole database. If you'd rather the agent start it, tell it: it does it with `request_change`, as you. If it's not clear when the damage happened, `find_moment` finds it ([Find the moment](/docs/guides/find-the-moment)), and its **Rewind to just before this** opens Rewind at exactly that point.

## What agents can do

An agent connected to Rowsafe can do what the dashboard does, **as the person who connected it**:

- **It reads everything the dashboard shows:** health and findings, alerts, what's running now and who blocks whom, metrics, the disk forecast, uptime, security, updates, standbys, pooling, forks, the audit log and the weekly Pulse, plus Rowsafe Cloud's sizes and prices and your Rowsafe Cloud servers.
- **It acts where production can't be hurt** (with write access): backups and Proof runs, acknowledging alerts, dismissing recommendations, testing indexes on a copy, checking and rehearsing an upgrade on a copy, the security check, files backups, and safe copies.
- **It changes production when you ask it to:** applying a fix, changing settings, restarting, restoring a copy, bringing rows back, rewinding, updating or upgrading, promoting a standby, moving a database, a new Rowsafe Cloud server ([Need a database?](#need-a-database)), and more, with `request_change` and tools like `apply_fix`. The change runs right away, as that person, with the same checks and Marks as their click. The agent tells you what it will do (and what it costs) before anything disruptive, destructive or paid.
- **Or Rowsafe refuses it, and nothing changes.** For example when the agent's person is a member (an owner or admin makes the change), there's no backup yet (the agent can take one and try again), or a server's key must be compared (a person does it in the dashboard). The agent tells you why and what you can do.

See [How AI agents act](/docs/guides/agent-autonomy) for the rules and the safety nets, and the [MCP reference](/docs/reference/mcp#tools) for every tool.

**Destructive** means: migrations and schema changes from any tool, `DROP`, `TRUNCATE`, `ALTER TABLE ... DROP/RENAME/TYPE`, `DELETE` or `UPDATE` without a narrow `WHERE`, backfills, `pg_restore --clean`, `dropdb`, and resetting or re-seeding a database.

## Need a database?

When the app an agent is building needs a database and has none, the agent can create one in [Rowsafe Cloud](/docs/guides/rowsafe-cloud): a server Rowsafe runs and protects from the first minute (backups, Proof, Pulse), billed to your organization. It costs money, so **the agent tells you the size and the price and gets your OK first**. Then it creates the server as you, right away if you're an owner or admin. If you're a member, Rowsafe refuses and an owner or admin creates it (see [How AI agents act](/docs/guides/agent-autonomy)).

<Steps>
<Step>

**The agent looks first.** `list_cloud_servers` shows the servers your organization already has; one may do. `cloud_catalog` shows the regions, the sizes with their price per hour and the most they cost a month, and what's sold out right now. The agent picks a region near the app and the cheapest size that fits (a small app fits the smallest one, about $10 a month at most), and tells you the price.

</Step>
<Step>

**It creates the server** (`create_cloud_server`), with a name, the region, the size and the addresses the app connects from, once you said yes. PostgreSQL unless the app needs MySQL, MariaDB, Valkey, ClickHouse, OpenSearch, Qdrant or Meilisearch (then with `engine`). The agent tells you what it created.

The first server needs a card, once (pay as you go), and only an owner pays. If you're an owner, the agent gives you a checkout link: add a card there, and the server is created right after. If you're an admin, Rowsafe refuses: an owner creates the server, or turns on pay as you go first (see [Paying for Rowsafe Cloud](/docs/guides/agent-autonomy#paying-for-rowsafe-cloud)).

</Step>
<Step>

**It waits.** The agent follows the new server until it's ready, about 5 to 10 minutes.

</Step>
<Step>

**It lets the app in.** If the app's address isn't allowed to connect, it changes who can connect (`cloud_firewall`). It checks with you first when that would cut off an address.

</Step>
<Step>

**It creates the app's own database and login** (`create_app_database`): a new, empty database and a new user that owns it. From a local `rowsafe mcp`, an owner's or admin's agent does that right away. From the plugins and other apps signed in with Rowsafe, you create it in the dashboard, because the password is made in your browser (below). The connection string uses the server's name (like `x7kq2mfa3pzd.cloud.rowsafe.sh`) with `sslmode=require`.

</Step>
<Step>

**It stores the connection string** in the app's environment, for example `DATABASE_URL` in `.env` (which git must ignore), never in code, a commit or the chat.

</Step>
</Steps>

**Rowsafe never sees the password.** Where it's made depends on how the agent is connected:

- **The Claude Code and Codex plugins, and other apps signed in with Rowsafe:** the agent asks you to create the database in the dashboard (**Databases & users**). The database server makes the password and your browser shows you the connection string once. Paste it into the app's `.env` yourself, or give it to the agent.
- **A local `rowsafe mcp --allow-writes`:** the password is made on your machine and Rowsafe only gets its verifier. The agent gets the full connection string at once; it works as soon as the database is created. This needs Rowsafe 0.9.4 or newer on the server (agents update themselves); on an older one the request is refused, and you can create the database in the dashboard instead ([Databases and users](/docs/guides/databases-and-users)).

Later, when you ask, the agent can move the server to a bigger size (`resize_cloud_server`, a Mark first), make a copy on a new server to test on (`clone_to_new_server`, deleted after the hours you choose) or delete a server (`delete_cloud_server`). It confirms each one with you first. Rowsafe refuses to delete a server whose backup passphrase was never saved, and keeps its backups.

The plugins' `rowsafe-new-database` skill teaches agents these steps. Creating needs **Act for you** (or `--allow-writes`); without it, the agent asks you to create the server in the dashboard and give it the connection string.

### Or from your terminal

The same in two commands, without an agent (or for an agent that runs shell commands):

```sh
rowsafe cloud create shop-db --wait   # the cheapest size free now; only this computer may connect
rowsafe env --on shop-db              # the app's database and login, DATABASE_URL written to .env
```

`rowsafe cloud create` shows the size and the price and asks before it creates anything. The first time, it gives you a link to add a card (an owner pays). `rowsafe env` makes the password on your computer and sends only its verifier, writes `DATABASE_URL` to `.env` and adds `.env` to `.gitignore`. Let your app's server in with `rowsafe cloud allow shop-db ADDRESS`. See [Rowsafe Cloud from the terminal](/docs/guides/rowsafe-cloud#from-the-terminal).

<Callout title="Limits">
  PostgreSQL 15 to 18 (17 unless you ask otherwise), MySQL 8.4, MariaDB 11.8, Valkey 8, ClickHouse 26.3 and 26.8, OpenSearch 3, Qdrant 1.19 or Meilisearch 1.54 ([Databases](/docs/guides/rowsafe-cloud#databases)); OpenSearch, Qdrant and Meilisearch restore to a snapshot, not to any second. `create_app_database` works on Rowsafe Cloud servers running PostgreSQL 15 or newer, MySQL, MariaDB or ClickHouse, not on your own servers or servers in your own cloud account: there, create the database in the dashboard or with `rowsafe env` (PostgreSQL). On MySQL, MariaDB and ClickHouse you always create it in the dashboard, which shows the password once. Valkey has no separate databases: make the app's login in the dashboard. On OpenSearch, Qdrant and Meilisearch, make the app's user or API key in the dashboard too. The new user owns only its database, but like every user it can connect to the server's other databases, with only what's granted to everyone there.
</Callout>

## Preview migrations and test on safe copies

Two more Guard tools never touch production, so agents get them without write access:

- **`preview_migration`** runs a migration's SQL on a fresh copy of the database and answers *safe*, *careful*, *dangerous* or *fails*, with what to change. The skill tells agents to preview every migration before running it. See [Preview a migration](/docs/guides/preview-migrations).
- **`create_safe_copy`** gives an agent a masked copy to test against, with a connection string, instead of production's. See [Safe copies](/docs/guides/safe-copies).

## Set it up

Pick one or combine them. First, name the project's database once, in the project directory:

```sh
rowsafe init app
```

This writes `.rowsafe.json` (`{"database": "app"}`). The CLI, the MCP server and the guard hook all use it.

## Snippet for AGENTS.md or CLAUDE.md

Copy this into your project's agent instructions and set the database name:

```markdown
## Database safety (Rowsafe)

This project's database is protected by Rowsafe (database: `app`). Before any destructive
or risky database operation (migrations, schema changes, DROP/TRUNCATE, DELETE or UPDATE
without a narrow WHERE, backfills, resets, restoring a dump):

1. Run `safety_check` for `app` (or `rowsafe status app`). If it is not protected,
   tell me the reasons and wait for my OK.
2. Set a Mark (a named restore point) with a descriptive name: `create_restore_point`
   (or `rowsafe mark app before-<what>`), wait until it is confirmed, and tell
   me its name.
3. Then proceed.

If something goes wrong: stop, don't try to repair the data, and don't restore, rewind or
restart anything unless I ask. Tell me what happened and the Mark's name; I'll decide whether
to Rewind. If I ask you to start it, use `request_change`; if Rowsafe refuses, tell me why.
```

## The guard hook

`rowsafe guard` runs before every Bash command in Claude Code. For a command that looks destructive, it:

1. finds the project's database, from `ROWSAFE_DATABASE` or the nearest `.rowsafe.json`;
2. sets the Mark `agent-<UTC time>` and waits up to 90 seconds for it to be confirmed;
3. lets the command run, and tells you and Claude the Mark's name.

If anything fails (no database configured, not logged in, Rowsafe unreachable, the Mark not confirmed), it only warns and the command runs.

**To block instead**, require protection:

```json title=".rowsafe.json"
{ "database": "app", "require_protection": true }
```

or set `ROWSAFE_REQUIRE_PROTECTION=1`. The hook then checks protection first, and **blocks** the command when the database isn't protected or the Mark can't be confirmed. It tells Claude to report the problem to you rather than work around it.

### What it matches

| | Examples |
|---|---|
| Migration tools | `prisma migrate deploy/reset/dev`, `prisma db push`; `rails`/`rake db:migrate`, `db:rollback`, `db:drop`, `db:reset`, `db:schema:load`; `alembic upgrade/downgrade`; `manage.py migrate/flush`; `knex migrate:latest`, `seed:run`; `sequelize db:migrate`; `typeorm migration:run`, `schema:sync`; `drizzle-kit push/migrate`; `goose up/down/reset`; `migrate ... up/down/drop`; `dbmate up`; `atlas schema apply`; `sqlx migrate run`; `diesel migration run`; `flyway migrate/clean`; `liquibase update/rollback`; `mix ecto.migrate`; `artisan migrate`; `supabase db reset/push`; `npm run db:migrate` and similar script names |
| SQL sent to a SQL client | `psql`, `pgcli`, `mysql`, `mariadb`, `mycli`, `clickhouse-client` (or `clickhouse client`), `sqlite3` and `litecli` with `DROP ...`, `TRUNCATE`, `RENAME TABLE`, `ALTER TABLE ... DROP/RENAME/TYPE/MODIFY/CHANGE`, ClickHouse mutations (`ALTER TABLE ... DELETE/UPDATE`, `DROP PARTITION`), `DELETE` or `UPDATE` without `WHERE`, in `-c`/`-e`/`--query`, a heredoc, a pipe, `< file`, or a small file passed with `-f`, `--queries-file`, `sqlite3 -init` or `.read` |
| MongoDB shell | `mongosh` or `mongo` with `drop()`, `dropDatabase()`, `deleteMany({})`, `updateMany({}, ...)`, `dropIndex`, `renameCollection`, in `--eval` or a small script file |
| Redis and Valkey | `redis-cli` or `valkey-cli` with `FLUSHALL`, `FLUSHDB` or `SWAPDB`, `DEL`/`UNLINK` fed by `xargs` (`--scan --pattern ... \| xargs redis-cli del`), or those commands in `< file` or an `--eval` script (CLI 0.9.2 and later) |
| Database tools | `dropdb`, `pg_restore --clean`, `mysqladmin drop`, `mongorestore --drop`, `myloader --overwrite-tables`, `sqlite3 ... .restore` |

It ignores status, dry-run and help commands (`migrate status`, `alembic upgrade --sql`, `manage.py migrate --plan`, `--help`), generating migrations, and commands that only mention a tool (`git commit -m "..."`, `grep`, `echo`, `cat`).

Test a command:

```sh
rowsafe guard --check 'npx prisma migrate deploy'   # destructive: ... (exit 0)
rowsafe guard --check 'npx prisma migrate status'   # not destructive (exit 1)
```

<Callout title="A safety net, not a sandbox">
  A destructive statement hidden in application code, an ORM script or an unusual wrapper won't match. The skill and the MCP tools cover what the hook can't see.
</Callout>

## Keep agents apart

Give each agent environment its own API key, so its actions show up separately in the audit log. Create it in the dashboard, under **Settings → API keys**: agents using it act as you. Or from a terminal:

```sh
rowsafe api-keys create ci-agent
rowsafe api-keys create reviewer-bot --read-only
```

A key made from the terminal is made by another key, not by a person, so agents using it [can't make changes](/docs/guides/agent-autonomy#agents-that-cant-make-changes-yet): Rowsafe refuses them. A **read-only** key can still run `safety_check`, but can't set Marks, run anything or change production.
