---
title: Create databases and users
description: Create databases, users and extensions inside your PostgreSQL, MySQL, MariaDB, MongoDB or ClickHouse server, and users on Redis and Valkey, from the dashboard or the CLI, with passwords only you ever see.
---

In Rowsafe, a "database" is a whole database server (the examples use PostgreSQL; [the others](#mysql-mariadb-mongodb-and-clickhouse) work the same, in their own terms, and [Redis and Valkey](#redis-and-valkey) have users only). The **Databases & users** tab of that server shows what's inside it, the databases, the users and the extensions, and lets you create and remove them without logging in to the server.

Every database you create is **backed up from the first second**: Rowsafe backs up the whole server, so a new database is part of the next backup and of continuous archiving as soon as it exists.

## Create a database

1. Open the server in the dashboard, then **Databases & users**.
2. Click **Create database** and type a name, such as `shop`.
3. Click **Create database**.

Rowsafe creates:

- the database, in UTF-8 and the server's locale;
- a new user with the same name that owns it, with a random 32-character password;
- the rights: only that user (and superusers) can connect to the new database, and only the owner can create tables in its `public` schema.

When it's done, you see the password **once**, with the connection string for the address your apps use and ready-made snippets for `.env`, `psql`, Prisma, Django, Rails and Laravel. Copy it now: Rowsafe doesn't keep it. If you lose it, set a new one (below).

Under **More options** you can:

- give the database to an **existing user** instead of creating one;
- turn on **extensions** right away (for example `pg_trgm`, `uuid-ossp`, `vector`);
- choose another **locale** (how text sorts), or start from the empty template (`template0`).

If something fails half-way, Rowsafe removes what it created, so nothing is left behind.

## Add a user

Click **Add user**, give it a name, choose the databases it can use and what it can do:

| Access | Can |
|---|---|
| **Read only** | Read every table, including tables the database's owner creates later. Change nothing. |
| **Read and write** | Also add, change and delete rows, and use sequences. Can't create or change tables. |
| **Full access** | Everything the owner can do, including creating and changing tables. |

The password is shown once, like above.

## New password, remove a user

In the users list, open a user's menu:

- **New password** makes a new random password and shows it once. Apps already connected stay connected; they need the new password the next time they connect. Passwords are stored the modern way (SCRAM); users with an old MD5 password are marked so you can move them.
- **Remove user** ends its connections and removes it. Anything it owns (tables, databases) goes to the user you choose.

Rowsafe never changes superusers, the user its agent connects as, or its own users.

## Extensions

Click a database's extensions (or **Extensions** in its menu) to turn extensions on and off. The extensions installed on the server are listed, and [pgvector, PostGIS and TimescaleDB](#pgvector-postgis-and-timescaledb), which Rowsafe can install for you. Other extensions that come in a separate package have to be installed on the server first. Turning one off is refused while something still uses it, with the reason.

Extensions that let database users run programs or read files on the server as PostgreSQL's system user (the untrusted languages such as `plpython3u`, and `file_fdw`) are marked, and need you to type their name to confirm.

### pgvector, PostGIS and TimescaleDB

Under **Installed by Rowsafe when you turn them on**, three popular extensions are one switch each, on PostgreSQL 15 to 18: **pgvector** (`vector`, AI search), **PostGIS** (`postgis`, maps and places) and **TimescaleDB** (`timescaledb`, time series). When you turn one on, Rowsafe installs its package from the PostgreSQL project's repository (apt.postgresql.org), then turns it on in that database.

- **TimescaleDB restarts PostgreSQL once.** It's loaded when PostgreSQL starts, so the first time, Rowsafe asks you to confirm a restart: it saves a Mark, restarts PostgreSQL (apps are disconnected for a few seconds), then turns it on. After that, turning it on in other databases needs no restart. On a server created with it, it's loaded already.
- **TimescaleDB is its Apache-2.0 edition**: hypertables and `time_bucket`, but not compression, continuous aggregates or the other features under the Timescale License.
- **Rowsafe installs them only where root allowed PostgreSQL updates** on the server (**Install PostgreSQL updates and upgrades**, [what Rowsafe may do](/docs/guides/permissions)), and TimescaleDB's restart only where restarts are allowed. If installing would also change PostgreSQL's own packages, Rowsafe says so and asks you to install PostgreSQL's update first, so nothing restarts by surprise.
- **On a server with a standby**, only extensions already installed (and for TimescaleDB, loaded) can be turned on: the standby needs them too. On [servers Rowsafe creates](/docs/guides/rowsafe-cloud#extensions), pick them when you create the server, and both servers get them.
- **Rowsafe keeps them working**: a settings change never drops TimescaleDB from the libraries PostgreSQL loads, Pulse offers to load it again if it goes missing, and Pulse offers **Update** (a Mark first) when a database runs an older version than the server has. A minor update of PostgreSQL through Rowsafe updates them in every database by itself. Before a major upgrade, the [upgrade check](/docs/guides/updates#timescaledb) says whether TimescaleDB can move with it.

## Remove a database

Open the database's menu and click **Remove database**, then type its name. Rowsafe first saves a **Mark**, so you can get the data back with [Rewind](/docs/guides/restore), then ends its connections and removes it. PostgreSQL's own databases (`postgres`, `template0`, `template1`) can't be removed.

## From the CLI

```sh
rowsafe db                                  # databases, users and extensions
rowsafe db create shop                      # a new database and its own user; the password is shown once
rowsafe db create shop --owner app --extension pg_trgm
rowsafe db user add reporting --db shop --access read_only
rowsafe db user password reporting
rowsafe db user remove old_app --reassign-to app
rowsafe db ext on shop vector                # pgvector: installed first if needed
rowsafe db ext on metrics timescaledb --restart   # a Mark, then one restart of PostgreSQL
rowsafe db drop shop                        # asks you to type the name; a Mark first
```

Add `--on NAME` to choose the server when your organization has several. See the [CLI reference](/docs/reference/cli#databases-and-users).

## How passwords stay private

Rowsafe never sees the passwords it creates:

1. Your browser (or the CLI) makes a one-time key pair. The private key never leaves its memory and can't be exported.
2. The agent on your server generates the password and encrypts it to that key (ECDH P-256, HKDF-SHA256 and AES-256-GCM).
3. Rowsafe relays only the encrypted password, once, to the person who asked, and deletes it; after 10 minutes it is deleted anyway.
4. Your browser decrypts it and shows it to you.

PostgreSQL stores only a SCRAM verifier the agent computes, so the password isn't in any SQL statement or server log either.

## A database for an AI agent's app

On a [Rowsafe Cloud](/docs/guides/rowsafe-cloud) server running PostgreSQL 15 or newer, MySQL, MariaDB or ClickHouse, an AI agent building an app can create the app's own database with `create_app_database` (see [Need a database?](/docs/guides/ai-agents#need-a-database)): right away from a local `rowsafe mcp` for an owner's or admin's agent, otherwise once an owner or admin [approves](/docs/guides/approvals#a-database-for-an-app) it in the dashboard. Rowsafe then creates a new, empty database and a new user that owns it, like **Create database** does. Existing databases and users are untouched, and the new database is backed up with the rest of the server.

The password still never passes through Rowsafe:

- **From the Claude Code and Codex plugins, or any app signed in with Rowsafe, and on MySQL, MariaDB and ClickHouse:** a person always approves it. Then the agent on the server makes the password and encrypts it to your browser, as above. You see the connection string once; put it in the app's `.env` or give it to the AI agent.
- **From a local `rowsafe mcp`, on PostgreSQL:** the password is made on your own machine, and only its SCRAM verifier is sent. The Rowsafe agent on the server creates the user from that verifier, so the AI agent has the full connection string at once, and it works once the database is created. This needs Rowsafe 0.9.4 or newer on the server (agents update themselves); on an older one the request is refused, and you can create the database here instead.

The connection string uses the server's name (like `x7kq2mfa3pzd.cloud.rowsafe.sh`) with TLS (`sslmode=require` on PostgreSQL, `secure=true` on ClickHouse). The new user owns only its database, and only it (and superusers) can connect there. Like every user, it can also connect to the server's other databases, with only what's granted to everyone there.

## MySQL, MariaDB, MongoDB and ClickHouse

The same page works for the other engines, in their own terms. Passwords are made on your server and reach only your browser, like PostgreSQL's.

- **MySQL and MariaDB:** a database's "owner" is a user with every right on it (MySQL has no owners). New users may log in from any host (`'name'@'%'`); where the server listens and your firewall decide who reaches it. Removing a database also takes back users' rights on it.
- **MongoDB:** users are created in `admin` (connect with `authSource=admin`) with `read`, `readWrite` or `dbOwner` on the databases you choose. A new database shows up in MongoDB once something is written to it.
- **ClickHouse:** `CREATE DATABASE`, `CREATE USER` and `GRANT`. Users defined in ClickHouse's configuration files (like `default`) are listed but never changed. A server that keeps its users only in configuration files can't get new ones until SQL users are on: the page says so and shows the small file that turns them on. On servers Rowsafe creates, new users get limits so one query can't take the whole server (at most 40% of its memory, and as many threads as it has processors), which they can't raise.
- **Redis and Valkey:** users only, see [below](#redis-and-valkey).
- **Rowsafe's own login** needs the rights to create users. Installs from before this feature can list but not change: the page shows the one command, for root on the server, that gives them.

## Redis and Valkey

On a Redis or Valkey server the page manages **ACL users**, Redis's own users.

**Add user** asks for a name, what it can do and, optionally, the keys it may use:

| Access | Can |
|---|---|
| **Read only** | Read keys. No writes, no pub/sub, nothing dangerous (`KEYS`, `CONFIG`...). |
| **Read and write** | Read and change keys, run scripts, use pub/sub, read `INFO`. Can't flush data (`FLUSHALL`, `FLUSHDB`), change settings, manage users, or run `KEYS`, `DEBUG`, `SHUTDOWN` or modules. |
| **Admin** | Every command, including settings, users and flushing all data. |

**Keys it can use** takes Redis key patterns, separated by spaces: `session:*` limits the user to keys starting with `session:`. Empty means every key. A Redis user reaches every numbered database; the pattern is how you keep apps apart.

The password is made on your server and shown once, with a `redis://` connection string and snippets for `.env`, `redis-cli`, Node.js and Python. Redis keeps only its SHA-256 hash, so the password isn't in any command the server logs. **New password** and **Remove user** work as above; removing a user disconnects apps signed in as it.

Rowsafe lists but never changes the `default` user (apps that sign in without a user name use it), Rowsafe's own user `rowsafe`, and the users replicas sign in with.

**Numbered databases.** Redis has a fixed number of logical databases (16 by default, numbered 0 to 15, the `databases` setting). The page lists the ones that hold keys, with their keys and connections. They can't be created or removed: give each app its own user, or its own key prefix.

**Kept across restarts.** Rowsafe saves each change where your server keeps its users: its ACL file (`ACL SAVE`), or its configuration file (`CONFIG REWRITE`). A server with neither (common in Docker, which starts Redis without a configuration file) forgets new users when it restarts; the result says so. Redis also doesn't copy users to its replicas: create the same user there for apps that read from a replica.

**Installs from before this feature.** Rowsafe's Redis user needs a few more rights to manage users. Until it has them, the page lists the numbered databases and says so. Run the Rowsafe installer on the server again: it gives Rowsafe's user the rights, asking for the administrator's password once. In Docker, run `rowsafe-agent redis login` again (the page shows the command).

With the CLI, Redis users take `--keys` instead of `--db`:

```sh
rowsafe db user add sessions --keys "session:*" --access read_write
rowsafe db user add everything --keys "*" --access read_only
```

## Who can do it

- Owners and admins, in the dashboard; read-write API keys, with the CLI. Members and read-only keys can only see the list.
- AI agents (MCP) read the list (`list_databases_on_server`). They can create a database for an existing owner, remove a database or user, or turn an extension on or off [as the person who connected them](/docs/guides/agent-autonomy): right away for an owner's or admin's agent (removing needs a backup to go back to, and Rowsafe saves a Mark first), otherwise once an owner or admin [approves](/docs/guides/approvals). When an agent removes a database from Rowsafe, its backups are [kept for you](/docs/guides/rowsafe-storage#kept-for-you). New users and passwords are for people only, except [a database for an AI agent's app](#a-database-for-an-ai-agents-app) on Rowsafe Cloud, whose password Rowsafe never sees.
- Every change is in the [audit log](/docs/guides/teams#audit-log), without passwords.

## Limits

- Extensions, templates and locales are PostgreSQL's; the other engines don't have them (see [MySQL, MariaDB, MongoDB and ClickHouse](#mysql-mariadb-mongodb-and-clickhouse)).
- Rowsafe installs pgvector, PostGIS and TimescaleDB on PostgreSQL 15 to 18 only, and not on a server with a standby unless they're installed there already. Upgrading PostgreSQL 15 to 16 with TimescaleDB isn't possible through Rowsafe yet.
- Redis and Valkey: users get one of the three presets; users with rules of their own are listed as "Custom rules" and keep them. Connection strings use `redis://` on the server's port (Rowsafe doesn't manage TLS for Redis).
- A new user can connect to the databases it was given, and also to databases every user may connect to (on most servers, `postgres`, where it can't read anything it wasn't given). Rowsafe doesn't change your other databases' rights or `pg_hba.conf`.
- "Tables created later" covers tables created by the database's owner and by users that already own tables in it.
- Connection strings use the server's direct port. `sslmode=require` when TLS is on for the server, otherwise `prefer`.
- The agent must be online: changes wait for it and are refused when it isn't reporting.
