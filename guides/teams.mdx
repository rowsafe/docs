## Members and roles

An organization has members with one of three roles:

| Role | Can |
|---|---|
| **Member** | View databases, backups, Proof results and activity. |
| **Admin** | Everything a member can, plus adopt databases, run tasks, restart PostgreSQL (on servers that allow it), [Rewind](/docs/guides/restore) (restore copies, bring back rows, rewind a database), manage hosts, alert rules, API keys and members. |
| **Owner** | Everything, including billing and [what AI agents may do](/docs/guides/agent-autonomy#the-team-setting). |

Invite people in the dashboard under **Settings**, then **Members**. Invitations expire after 7 days. Admins and owners can invite; only owners can make someone an owner or change another owner. Whoever creates the organization is its first owner.

## API keys

The CLI, scripts, CI and AI agents use **API keys** (`rsk_...`).

On your own machine you don't need to create one: `rowsafe login` opens the dashboard, you approve it, and a key is created for you. Only admins and owners can approve a CLI login.

For CI and headless machines, create a key in the dashboard under **Settings**, then **API keys**, and pass it with `ROWSAFE_API_KEY` or `rowsafe login --key` (to save a Mark before each deploy, see [Save a Mark before every deploy](/docs/guides/deploys)). Or from a terminal:

```sh
rowsafe api-keys create deploy-ci
rowsafe api-keys create dashboards --read-only
rowsafe api-keys list
rowsafe api-keys revoke key_...
```

- A key is shown **once**. Rowsafe stores only a hash of it.
- A **read-only** key can only read. Anything else is refused with `This API key is read-only.`
- A key works for the organization and can do everything the API allows. Keep it in a secret manager.
- **Each key records who made it.** **Settings → API keys** shows it: the person who created it in the dashboard, or who approved the `rowsafe login`. AI agents using the key (a local `rowsafe mcp`, or the remote MCP endpoint) [act as that person](/docs/guides/agent-autonomy), with their role at the moment of each change.
- **A key made by another key** (with `rowsafe api-keys create`) shows **Made by key ...**: no person made it, so AI agents using it always ask first, and every change they make waits for an owner or admin. For an agent that should act as you, create its key in the dashboard.
- Keys made before Rowsafe let agents act as their person keep asking first until the person who made the key clicks **Let agents using it act as me** (only they can), or makes a new one.
- Revoking takes effect on the next request. A key can't revoke itself.
- `rowsafe logout` revokes the key that `rowsafe login` created. Keys given with `--key` stay valid.

## Audit log

Every change is recorded: who did it, what, and to which database or host. See it in the dashboard under **Settings**, then **Audit log**, or from a terminal:

```sh
rowsafe audit              # newest first
rowsafe audit --limit 200
```

```text
WHEN                 ACTOR                                      ACTION                TARGET  DETAIL
2026-09-24 14:05:12  key:key_... (CLI · rowsafe CLI on laptop)  restore_point.create  app     before-migration-42
```

Changes an AI agent made name the person it acted as and the agent, for example `ana@example.com through their AI agent Claude`, with the request it came from. Letting an app or key act as you, and changing what AI agents may do, are recorded too.

It records, among others: databases added, changed and removed; hosts changed and removed; enrollment tokens created; tasks queued (backups, Proof runs, plans, restarts); Marks; forks (`database.fork`); Rewind (`rewind.copy`, `rewind.copy_extend`, `rewind.copy_delete`, `rewind.compare`, `rewind.rows`, `rewind.in_place`, `rewind.undo`, `rewind.cleanup`); API keys created and revoked; alerts acknowledged; alert rules and notification channels changed; plan changes; and CLI logins approved or denied.

Changes the installer makes, such as adding a database, show an actor like `installer on db-1`.
