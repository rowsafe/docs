Rowsafe speaks the [Model Context Protocol](https://modelcontextprotocol.io). AI assistants can read what the dashboard shows ("is everything backed up?", "why did this alert fire?", "what is blocking the app?") and, when you allow it, set Marks (restore points), run backups, Proof and checks, and make changes to production or create a [Rowsafe Cloud](/docs/guides/rowsafe-cloud) server **as the person who connected them**, with that person's rights in the dashboard. The change runs right away, or Rowsafe refuses it, changes nothing and says why (for example, a member's agent: an owner or admin makes the change). See [How AI agents act](/docs/guides/agent-autonomy). The MCP tools are part of [Guard](/docs/guides/ai-agents), the safety net for AI agents.

| | Transport | Credentials | Write tools |
|---|---|---|---|
| `rowsafe mcp` | stdio, on your machine | The CLI's login, or `ROWSAFE_API_KEY` | Off by default. `--allow-restore-points` or `--allow-writes`. |
| `https://api.rowsafe.sh/mcp` | Streamable HTTP | **Sign in with Rowsafe** (OAuth), or `Authorization: Bearer rsk_...` (an API key). | API keys: always listed; a read-only key can't use them. Signed-in apps: `create_restore_point` if you allowed Marks, and the write tools, `request_change`, the change tools and `create_app_database` if you allowed **Act for you**. |

For the safety-net workflow with coding agents, see [Use Rowsafe with AI agents](/docs/guides/ai-agents). To add Rowsafe to ChatGPT, Claude, Cursor, VS Code, Codex or Windsurf, see [Connect AI apps](/docs/guides/connect-ai-apps).

## Set up

<Tabs items={["Claude Code", "Claude Desktop", "Remote endpoint"]}>
<Tab value="Claude Code">

Log in with the CLI first (`rowsafe login`), then pick a mode:

```sh
# Read-only
claude mcp add rowsafe -- rowsafe mcp

# Read-only, plus Marks (what the Claude Code plugin uses)
claude mcp add rowsafe -- rowsafe mcp --allow-restore-points

# Also backups, Proof, checks, schedules, and changes to production as you
claude mcp add rowsafe -- rowsafe mcp --allow-writes

# A specific key instead of your login, in every project
claude mcp add --scope user rowsafe -e ROWSAFE_API_KEY=rsk_... -- rowsafe mcp
```

`--scope project` writes `.mcp.json` into your repository for everyone: don't put a key in it. Use the stdio form (each developer's own login) there.

</Tab>
<Tab value="Claude Desktop">

Claude Desktop runs local servers from its config file: `~/Library/Application Support/Claude/claude_desktop_config.json` on macOS, `%APPDATA%\Claude\claude_desktop_config.json` on Windows (**Settings**, **Developer**, **Edit Config**).

```json title="claude_desktop_config.json"
{
  "mcpServers": {
    "rowsafe": {
      "command": "/usr/local/bin/rowsafe",
      "args": ["mcp"],
      "env": {
        "ROWSAFE_API_KEY": "rsk_..."
      }
    }
  }
}
```

Use the absolute path of `rowsafe` (`which rowsafe`): Desktop doesn't use your shell's `PATH`. Add `"--allow-restore-points"` or `"--allow-writes"` to `args` for write tools. Restart Claude Desktop afterwards.

Or use a remote connector instead (**Settings**, **Connectors**, **Add custom connector**, `https://api.rowsafe.sh/mcp`), where you sign in with Rowsafe, with no key or local binary. See [Connect AI apps](/docs/guides/connect-ai-apps).

</Tab>
<Tab value="Remote endpoint">

No local binary needed. Sign in with Rowsafe:

```sh
claude mcp add --transport http rowsafe https://api.rowsafe.sh/mcp
```

Then run `/mcp` in Claude Code and choose **Authenticate**. Or connect with an API key, for CI:

```sh
claude mcp add --transport http rowsafe https://api.rowsafe.sh/mcp --header "Authorization: Bearer rsk_..."
```

- Every request needs an OAuth access token or an API key. Use a [read-only key](/docs/guides/teams#api-keys) (`rowsafe api-keys create NAME --read-only`) for an assistant that must never change anything.
- The endpoint is stateless and answers with plain JSON.
- Tool calls wait at most 45 seconds.

</Tab>
</Tabs>

## Sign in with Rowsafe (OAuth)

The remote endpoint is an OAuth 2.1 protected resource, following the [MCP authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) (2026-07-28). MCP clients discover everything from the first `401`; you only give them the URL. See [Connect AI apps](/docs/guides/connect-ai-apps) for each client.

| | |
|---|---|
| Protected resource metadata ([RFC 9728](https://www.rfc-editor.org/rfc/rfc9728)) | `https://api.rowsafe.sh/.well-known/oauth-protected-resource/mcp`, named in `WWW-Authenticate` on every `401` |
| Authorization server metadata ([RFC 8414](https://www.rfc-editor.org/rfc/rfc8414)) | `https://api.rowsafe.sh/.well-known/oauth-authorization-server` (issuer `https://api.rowsafe.sh`) |
| Client registration | Client ID metadata documents (an HTTPS `client_id`), or dynamic registration ([RFC 7591](https://www.rfc-editor.org/rfc/rfc7591)) at `/oauth/register`. Clients are public: no client secret. |
| Grant | Authorization code with PKCE, `S256` only. The response carries `iss` ([RFC 9207](https://www.rfc-editor.org/rfc/rfc9207)). |
| Redirect URIs | Exact match. Accepted: ChatGPT's, Claude's, VS Code's and Cursor's published callbacks, and loopback (`http://127.0.0.1`, `http://[::1]`, `http://localhost`, any port). |
| Resource ([RFC 8707](https://www.rfc-editor.org/rfc/rfc8707)) | `https://api.rowsafe.sh/mcp`. Tokens work on `/mcp` only. |
| Scopes | `rowsafe:read` (always), `rowsafe:marks` (optional, **Save Marks**: adds `create_restore_point`), `rowsafe:act` (optional, **Act for you**: adds the write tools, the copy tools, `request_change`, `create_cloud_server`, `cloud_firewall`, `apply_fix` and `create_app_database`, and lets the app act as the person who allowed it). `offline_access` is accepted; other scopes are ignored. |
| Tokens | Access tokens: 1 hour. Refresh tokens: 30 days, single use, rotated on every refresh; using one twice disconnects the app. Revocation ([RFC 7009](https://www.rfc-editor.org/rfc/rfc7009)) at `/oauth/revoke`. |

A person approves each app in the dashboard, for one organization. Owners and admins only. The app then acts as that person. Apps are listed, with who allowed them and whether they act as them or can't make changes yet, and can be disconnected, in **Settings**, **Connected apps**.

## Safety model

- **Everything goes through the Rowsafe API**, with the same API key, checks, plan limits and audit log as the CLI. Every change a tool makes or asks for is in `rowsafe audit`, attributed to the key or app, and to the person it acts as.
- **Tools can only do what the API can do.** They queue the fixed agent tasks and change schedules. Nothing runs commands or SQL on production or reads backup contents: Rowsafe can't do those at all.
- **Changes to production run as the agent's person.** Restoring, bringing rows back, rewinding, restarting, applying fixes, changing settings, updates and upgrades, standbys, moves, pooling, security fixes, Rowsafe Cloud servers and the rest go through `request_change` (or `create_cloud_server`, `cloud_firewall` and `apply_fix`, and a database for an app through `create_app_database`). Each one is recorded, checked and written up. Then Rowsafe asks the dashboard for the role, right now, of the person behind the agent (who allowed the app, made the API key, or approved the CLI login): for an owner or admin, it makes the dashboard's own API call as that person, at once, with the same checks, confirmations and Marks, and restarts still run only on servers where root allowed them at install. The tools never call those endpoints themselves.
- **Or Rowsafe refuses it, and nothing changes.** A member's agent, an API key made by another key, an app or key from before agents could act as their person, and the safety nets (no backup before a destructive change, a first payment only an owner makes, a server key to compare, the agents' budget) get a refusal with the reason, which the agent tells you. Nothing waits for a person. API keys and assistants can't change what AI agents may do. See [When Rowsafe refuses](/docs/guides/agent-autonomy#when-rowsafe-refuses).
- **Read-only unless you say otherwise.** `rowsafe mcp` registers read tools only, plus the copy tools, which never touch production (`preview_migration` runs SQL on a fresh copy as a regular role; `create_safe_copy` makes masked copies only, within your plan's limit). `--allow-restore-points` adds only `create_restore_point`. `--allow-writes` adds the actions that don't touch production, `request_change`, `create_cloud_server`, `cloud_firewall`, `apply_fix` and `create_app_database`.
- **No secrets through Rowsafe.** Passwords are set by people in the dashboard: new database users, password resets, restored copies, and safe copies made through the remote endpoint. The one exception is `create_app_database`: from a local `rowsafe mcp` the password is made on your machine and only its verifier is sent; on the remote endpoint the person creates the database in the dashboard, where the database server makes the password and only their browser sees it. Bucket keys and the passphrase never leave your server. Outputs are capped in size.
- **Not exposed at all:** enrollment tokens, API keys, removing hosts, members and roles, plan changes, agent update settings, and what root allowed on a server.
- **Annotations.** Read tools are marked read-only. `request_change`, `cloud_firewall`, `apply_fix`, `update_schedule` (lowering retention deletes old backups) and `delete_safe_copy` are marked destructive, so clients that confirm destructive calls will ask you. The tool descriptions also tell agents to confirm a disruptive, destructive or paid change with you in the chat first.

## Tools

**Read** tools are always there. **Marks** needs `--allow-restore-points` (or **Save Marks**). **Copies** never touch production: `rowsafe mcp` and API keys always get them; signed-in apps need **Act for you**. **Write** needs `--allow-writes`, a read-write API key, or **Act for you**.

| Tool | Access | What it does |
|---|---|---|

| `create_restore_point` | Marks | Set a Mark: name this moment, and wait until it is in your bucket. |
| `list_restore_points` | read | Marks (restore points) with their status and the backup to restore from. |

### Changes to production

| Tool | Access | What it does |
|---|---|---|
| `request_change` | write | Make a change to production: `action`, `database`, `params` and your `reason`, exactly like the dashboard's button. It runs right away: the answer starts with *Done*, names the person it ran as, and the change is `approved` (done) or `failed`, with its result and its page in the dashboard. Or Rowsafe refuses it: *Rowsafe refused this change, and nothing changed:* and the reason. |
| `create_cloud_server` | write | Create a Rowsafe Cloud server: `name`, `region`, `size`, `engine` (PostgreSQL unless you pass `mysql`, `mariadb`, `valkey`, `clickhouse`, `opensearch`, `qdrant` or `meilisearch`), `engine_version`, `allowed_ips`, `standby`, `extensions` and `reason`. The same as `request_change` `create_cloud_server`. When a first payment is needed, an owner's agent gets `checkout_url` to give you; the server is created once paid. |
| `cloud_firewall` | write | Set who can connect to a Rowsafe Cloud server: `server` and the whole new `allowed_ips` list. The same as `request_change` `cloud_firewall`. |
| `apply_fix` | write | Apply a fix Rowsafe proposed for a finding: `database`, `finding_id`, `fix_id`, and `confirm` when the fix restarts the database. Exactly like **Apply fix**: Rowsafe recomputes the fix and saves a Mark first when the fix says so. |
| `describe_change` | read | The actions, by group, with their risk and the JSON schema of their params. For one action, also as whom it would run here, and what would make Rowsafe refuse it. |
| `get_approval` | read | One change an AI agent made: `approved` (done, with the tasks it started) or `failed` (with why). Older records may say `pending`, `denied`, `expired` or `cancelled`: those never ran. The name is kept for compatibility. |
| `list_approvals` | read | Changes AI agents and API keys made in the organization, newest first. |
| `create_app_database` | write | A new, empty database and a new user that owns it, for the app you are building, on a Rowsafe Cloud server running PostgreSQL (15 or newer), MySQL, MariaDB or ClickHouse. Rowsafe never sees the password: on PostgreSQL from a local `rowsafe mcp` it is made on your machine, the tool returns the full connection string at once, and the database is created right away as the person who connected the agent (an owner or admin). On MySQL, MariaDB and ClickHouse, and on the remote endpoint, the password must be made in a person's browser: the tool says so, and the person creates the database in the dashboard (Databases & users), which shows the connection string once. Valkey has no separate databases: make the app's login in the dashboard. On OpenSearch, Qdrant and Meilisearch, the person makes the app's user or API key in the dashboard (Databases & users), which shows it once; the tool says so. |

| Group | Actions |
|---|---|
| Pulse | `apply_fix`, `change_settings`, `revert_settings`, `index_check_settings`, `restart`, `turn_on_backups` |
| Rewind | `restore_copy`, `compare_copy`, `extend_copy`, `delete_copy`, `bring_back_rows`, `rewind_in_place`, `undo_rewind`, `finish_rewind` |
| Updates | `update_database`, `upgrade_database`, `undo_upgrade`, `finish_upgrade`, `security_updates`, `reboot_server`, `auto_updates` |
| Standby | `create_standby`, `promote_standby`, `rebuild_standby`, `remove_standby`, `unfence`, `forget_fence`, `failover_settings` |
| Move | `move_database`, `move_schedule`, `move_switch`, `move_cancel`, `move_switch_back`, `move_finish`, `fork_database` |
| Security | `pooling_on`, `pooling_off`, `security_settings`, `security_action` |
| Data | `create_app_database` (through the `create_app_database` tool), `manage_databases_users`, `masking_rules`, `delete_database` |
| Files | `restore_files`, `undo_files_restore` |
| Alerts | `alert_rule` |
| Rowsafe Cloud | `create_cloud_server`, `cloud_firewall`, `resize_cloud_server`, `clone_to_new_server`, `delete_cloud_server` |

The Rowsafe Cloud actions that add to the bill (`create_cloud_server`, `resize_cloud_server`, `clone_to_new_server`) write the size and price into the change; the agent tells you before making them. A first payment is always an owner's: an owner's agent gets the checkout link, anyone else's is refused. `delete_cloud_server` is destructive: Rowsafe types the server's name for the agent and records that it did. See [Rowsafe Cloud changes](/docs/guides/agent-autonomy#rowsafe-cloud-changes).


`manage_databases_users` turning on `vector`, `postgis` or `timescaledb` installs the package first, where root allowed PostgreSQL updates. `timescaledb` is loaded when PostgreSQL starts, so it needs `restart: true` in `params` unless it's loaded already: Rowsafe saves a Mark, then restarts PostgreSQL once (apps are disconnected for a few seconds), and the agent tells you first. See [Extensions](/docs/guides/databases-and-users#pgvector-postgis-and-timescaledb).

Rowsafe refuses `create_standby`, `rebuild_standby`, `move_database` and `fork_database`: a person compares the server's key, in the dashboard or with the `rowsafe` CLI. It refuses a destructive action when it has no backup of the database yet (the agent can `run_backup` and try again). With **Within a budget**, `create_cloud_server` runs on the owner's behalf, plus `create_app_database`, `cloud_firewall` and `clone_to_new_server` on servers an agent created this way; everything else runs as the agent's person. See [When Rowsafe refuses](/docs/guides/agent-autonomy#when-rowsafe-refuses).

There are also two prompts: `incident_triage` checks the fleet, reads the evidence behind each problem, and proposes next steps without changing anything; `fix_what_pulse_found` lists a database's findings Rowsafe can fix, lets you pick, and files each fix you picked with `request_change`.

## Troubleshooting

- **"not logged in"** in the client's MCP log: run `rowsafe login`, or set `ROWSAFE_API_KEY` in the server's environment.
- **Tools missing:** write tools, `request_change` and the change tools only appear with `--allow-writes`, Marks with `--allow-restore-points`. Restart the client after changing flags. A signed-in app gets them only if you allowed **Act for you** (and **Save Marks**); connect it again to change that.
- **`forbidden (403): This API key is read-only.`:** the key can only read.
- **"Rowsafe refused this change, and nothing changed":** the reason follows (the person is a member, a first payment, no backup yet, a server key to compare, over the budget, ...); see [When Rowsafe refuses](/docs/guides/agent-autonomy#when-rowsafe-refuses). If it says the app or key was connected before agents could act as their person, that person clicks **Let it act as me** in **Settings → Connected apps** (or **Let agents using it act as me** under **API keys**), or connects it again.
- **A new Rowsafe Cloud server isn't created yet:** it waits for its first payment. An owner pays at the checkout link the agent gave.
- **A 402 error:** a plan limit is reached. `get_org` shows your usage.
- **Smoke test** without a client:

  ```sh
  printf '%s\n' \
    '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"t","version":"0"}}}' \
    '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
    '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' | (cat; sleep 2) | rowsafe mcp
  ```
