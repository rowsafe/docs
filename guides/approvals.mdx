title: Approvals
description: When an AI agent's change to production waits for a person, an owner or admin approves or denies it here. That happens when your team chose Ask me first, for a member's agent, and when a safety net needs a person.
---

AI agents connected to Rowsafe can do almost everything the dashboard does. By default, an agent [acts as the person who connected it](/docs/guides/agent-autonomy): when an owner's or admin's agent applies a fix, restarts the database or rewinds it, the change runs right away, as them.

A change waits here, for an owner or admin to click **Approve**, when:

- **your team chose Ask me first** in **Settings → AI agents** (an owner's choice). Then every change an agent makes waits, and nothing happens until you approve it;
- **the agent's person is a member**, or the agent [always asks first](/docs/guides/agent-autonomy#agents-that-always-ask-first) (a key made by another key, an app connected before agents could act as their person);
- **a safety net needs a person:** no backup to go back to yet, a first payment only an owner makes, a server's key to compare, the agents' budget, or an app database's password made in your browser. See [When a person still decides](/docs/guides/agent-autonomy#when-a-person-still-decides).

## How it works

<Steps>
<Step>

**The agent asks.** It explains what it wants to do and why, then makes the change (`request_change`, or a tool like `apply_fix`). When the change has to wait, the agent gets a link to the request in the dashboard and gives it to you. Apps that can open links for you (MCP URL elicitation) ask you to open it; others show the link.

</Step>
<Step>

**You get told.** The request shows under **Approvals** in the dashboard's sidebar, with a count, and as a one-line banner on **Home**. The people who get the [weekly Pulse](/docs/guides/monitoring#your-weekly-pulse) and your email [notification channels](/docs/guides/monitoring#notification-channels) also get an email with the link. Slack, Discord and webhook channels don't get requests yet.

</Step>
<Step>

**You read it.** The request's page shows:

- **What will change**, written by Rowsafe, not by the agent;
- the agent's reason, labeled as its words (Rowsafe doesn't check them);
- the **risk**: *Apps won't notice* (it changes Rowsafe or a copy), *Apps may notice* (a restart, a short pause or a switch) or *Replaces data* (it replaces or deletes data, or removes the way back);
- who asked (the app or API key, and the person behind it), why it waits for a person, and when the request expires.

</Step>
<Step>

**You approve or deny.** Only an owner or admin signed in to the dashboard can. To approve a change that replaces data, you type the database's name (the server's name, to delete a Rowsafe Cloud server). Deny it and nothing changes; you can add a note the agent will see.

</Step>
<Step>

**Rowsafe does it, as you.** It makes the same call the dashboard's own button makes, with the same checks and confirmations. The [audit log](/docs/guides/teams#audit-log) records it as you ("approved request apr_..."). The result (the tasks it started, or why it didn't work) shows on the request's page, and the agent sees it too.

</Step>
</Steps>

A request nobody decides expires after 24 hours. The agent can withdraw a request that is still waiting.

### Done right away

When the change doesn't have to wait, Rowsafe skips steps 2 to 4: it runs the change at once as the person who connected the agent, and the agent gets the result in the same call. The change still shows on the **Approvals** page, as **Done right away**, with a banner (*Done by AI agents in the last 24 hours*). The audit log records it as that person through their agent, for example *ana@example.com through their AI agent Claude*, and owners get a digest email. See [Know what agents did](/docs/guides/agent-autonomy#know-what-agents-did).

## What an agent can change

| | Changes |
|---|---|
| Pulse | Apply a fix, change database settings or undo a change, the index check schedule, restart the database, turn on backups |
| Rewind | Restore a copy, compare it with production, keep it longer or delete it, bring back rows, rewind the whole database, undo or finish a rewind |
| Updates | Install a minor update, upgrade to a new major version, undo or finish an upgrade, install the server's security updates, reboot the server, automatic minor updates |
| Standby | Create, promote (fail over), rebuild or remove a standby, start or stop watching a fenced old primary, automatic failover |
| Move and fork | Move to another server, schedule or make the switch, cancel, switch back, finish; fork the database |
| Security | Turn connection pooling on or off, change security settings, fix a security finding |
| Data | Create a database for an app (Rowsafe Cloud), create a database for an existing owner, remove a database or user, turn an extension on or off, change masking rules, stop protecting a database |
| Files and alerts | Restore files and undo it, change an alert rule |
| Rowsafe Cloud | Create a server, change who can connect, change a server's size, clone a database to a new server, delete a server |

The agent's `describe_change` tool lists them with their parameters.

## Rowsafe Cloud requests

An agent can create a [Rowsafe Cloud](/docs/guides/rowsafe-cloud) server for the app it's building, and later change it (see [Need a database?](/docs/guides/ai-agents#need-a-database)). When one of these waits for you, it works like the other requests, with a few more things on the page, because some of them cost money.

| Request | What you see |
|---|---|
| **Create a Rowsafe Cloud server** | Where it runs (cloud and region), the size, the price per hour and the most it costs a month (a standby doubles it), the traffic included, who can connect, and how it will be paid. |
| **Change who can connect** | The whole new list of addresses, and which addresses get cut off. Apps connecting from those lose access. |
| **Change a Rowsafe Cloud server's size** | The old and the new price. Rowsafe saves a Mark first. The database is offline for a few minutes while the server restarts (with a standby, writes pause for a few seconds instead). The disk never shrinks. |
| **Clone to a new Rowsafe Cloud server** | The database and the moment it copies (now, a second or a Mark), the new server's size and price, and when Rowsafe deletes it. The clone holds real data, not masked, and costs money until it's deleted. |
| **Delete a Rowsafe Cloud server** | The server, the bill that stops, and whether the backup passphrase was saved. You type the server's name to approve. Rowsafe refuses to delete a server whose passphrase was never saved (clones aside): without it, its backups can't be restored. |

Every address is listed, never cut short. An address that lets **everyone on the internet** try to connect (`0.0.0.0/0` or `::/0`) gets its own warning, and so does a very wide range. They'd still need a password, but limiting it to your apps' addresses is much safer. The page also says when its prices, payment state and addresses were read.

### Approve and pay

A request that costs money (a new server, a bigger size, a clone) says **This adds to your organization's bill**, and its button reads **Approve and pay**.

- **Pay as you go is on:** the server is created as soon as you approve, and billed by the hour like any Rowsafe Cloud server. See [How billing works](/docs/guides/rowsafe-cloud#how-billing-works). An owner's or admin's agent doesn't need a request here: it creates the server right away.
- **Pay as you go isn't on yet** (or the cloud is billed by the month, like OVHcloud Value): right after you approve, you go to the checkout. The server is created once it's paid. An owner's agent gets that checkout link without a request, and gives it to you.
- **Only owners pay.** An admin can approve, and is told that an owner of the organization pays for it to be created. The server waits for payment until then; an owner pays with **Pay to create it** on the request's page.

Nothing is created or billed before a request that waits is approved (and, where needed, paid). A first payment is always an owner's, whoever's agent asked.

### A database for an app

**Create a database for an app** makes a new, empty database and a new user that owns it, on a Rowsafe Cloud server running PostgreSQL, MySQL, MariaDB or ClickHouse. Existing databases and users are untouched. The page shows the connection string without the password, and where the password comes from:

- **Made on the assistant's machine** (a local `rowsafe mcp`, PostgreSQL): Rowsafe only has its verifier and never sees the password. The assistant can connect once the database is created: right away for an owner's or admin's agent, or once you approve.
- **Made on the database server when you approve** (apps signed in with Rowsafe, such as the Claude Code and Codex plugins, and always on MySQL, MariaDB and ClickHouse): it's shown only to you, once, in your browser. Put it in the app's environment (for example `DATABASE_URL` in `.env`), or give it to the assistant. So this one always waits for a person.

See [Databases and users](/docs/guides/databases-and-users#a-database-for-an-ai-agents-app) for what the new user can reach.

## What stays the same

- **Only a person approves.** API keys and AI agents can never approve, not even their own requests. An agent's change that runs right away needs no approval because it runs as its person, with exactly their rights.
- **Root's permissions still apply.** A restart, an update or a reboot runs only on servers where root allowed it at install. See [Permissions](/docs/guides/permissions).
- **Secrets never go through Rowsafe.** Passwords for new database users, password resets and passwords for restored copies are set by people in the dashboard. The one exception is [a database for an app](#a-database-for-an-app): its password is made on the assistant's machine, or shown only to you, and Rowsafe never sees it.
- **No queries or commands.** Agents never run SQL or commands on production through Rowsafe and never see what's inside your backups. They test on masked [safe copies](/docs/guides/safe-copies).

## Which agents can make changes

- **Local `rowsafe mcp`**: with `--allow-writes`. See the [MCP reference](/docs/reference/mcp#set-up).
- **The remote endpoint with an API key**: a read-write key. A read-only key can't change anything.
- **Apps signed in with Rowsafe** (ChatGPT, Claude, Cursor...): only if you ticked **Act for you** when you connected them. See [Connect AI apps](/docs/guides/connect-ai-apps).

Whether a change runs right away or waits here is described in [How AI agents act](/docs/guides/agent-autonomy).
