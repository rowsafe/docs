---
title: Find the moment
description: Find out exactly when rows were deleted or changed, or a table was emptied or dropped, so you can rewind to just before it instead of guessing.
---

Something went missing: customers are gone, orders all say "closed", a table is empty. Before you can [rewind](/docs/guides/restore), you need the moment it happened. **Find the moment** tells you: it lists each big delete, update, `TRUNCATE` and `DROP`, with the exact second it happened, the table, how many rows, and its transaction ID.

It only reads. Nothing in the database changes, and your data never leaves your server: the Rowsafe agent reads the database's change log in your storage (PostgreSQL's WAL, MySQL's binary log, MongoDB's oplog, SQLite's WAL pages, the stream of changes Rowsafe follows for Redis and Valkey) on your server, and only names, times and counts reach Rowsafe.

## In the dashboard

1. Open the database, then **Rewind** → **Find the moment**.
2. Pick the tables (or leave **All tables**), how far back to look (the last hour up to 7 days, or your own range), and what happened: deleted rows, changed rows, emptied tables, dropped tables.
3. Click **Find the moment**. The agent picks up the search within seconds. A day of changes usually takes under a minute.

You get the totals, a timeline (click a bar to list only what happened then) and the changes, newest first. Each transaction is one row, even when it touched several tables. A table changed the same way over and over (an hourly cleanup job, say) is folded into one row so the unusual change stands out.

**Rewind to just before this** takes you to Rewind with that point filled in: just before the transaction committed, so everything before it is kept and the change itself is left out. From there, restore a copy next to production, compare, and bring the rows back.

Any member of the organization can search. Rewinding needs the admin or owner role.

## From a terminal

```sh
rowsafe rewind find app --table customers --since 6h
```

```
Searched 2026-09-24 08:00:00 CEST (06:00:00 UTC) to 2026-09-24 14:00:00 CEST (12:00:00 UTC).

WHEN (YOUR TIME ZONE)     WHAT                               TRANSACTION
2026-09-24 11:47:03 CEST  1,204 rows deleted from customers  8841207

Found 1 transaction with matching changes between 06:00 and 12:00 UTC on Sep 24. The biggest: 1,204 rows deleted from customers at 09:47:03 UTC.

Rewind to just before the biggest one (a copy next to production; it never touches it):
  rowsafe rewind copy app --at 2026-09-24T09:47:03.521880Z
```

| Option | What it does |
|---|---|
| `--table T` | Only this table: `schema.table` or `table`. Repeat or comma-separate for several. |
| `--since 24h` | How far back: `30m`, `6h`, `2d`, `1w` (default 24 hours, at most 7 days). |
| `--from TIME`, `--to TIME` | An exact range instead, in your time zone (`"2026-09-24 14:00"`, `"14:00"`, `"2h ago"`) or RFC 3339. |
| `--kind K` | `delete`, `update`, `truncate`, `drop` (comma-separated). |
| `--db DB` | Only this PostgreSQL database, when the server has several. |
| `--min-rows N` | Leave out transactions that changed fewer rows. |
| `--json` | The full result as JSON. |

## For AI agents

The MCP tool `find_moment` does the same search, and it is read-only, so it is available to every key, including read-only ones. An assistant can answer "when were rows deleted from applications?" and give you the exact point, but it never rewinds anything itself: that stays with you, and it can only [ask you to approve](/docs/guides/approvals) a rewind. See [Guard](/docs/guides/ai-agents).

## By database

| | Reads | Differences |
|---|---|---|
| PostgreSQL | the WAL in your bucket | to the microsecond, with transaction IDs |
| MySQL, MariaDB | the binary logs in your bucket, with the server's own `mysqlbinlog` | to the second; with `binlog_format = STATEMENT`, only TRUNCATEs and DROPs are found |
| MongoDB | the oplog in your bucket | to the second; outside a multi-document transaction, deletes and updates are grouped by collection and second |
| Redis, Valkey | the stream of changes in your bucket; you type keys or patterns (`user:*`), not tables | to the second; writes grouped by logical database, pattern and second, a `MULTI`/`EXEC` as one; results name only the patterns you typed, never the keys they matched; expired keys show as deleted |
| ClickHouse | the record of the parts ClickHouse wrote, in your bucket | to the microsecond; a mutation is one change at its first part; `UPDATE` rows are those of the parts it rewrote ("up to"); `TRUNCATE` and `DROP PARTITION` show as emptied tables |
| SQLite | the WAL pages in your bucket, replayed on a private copy on your server | to the millisecond Rowsafe copied each change; a `DELETE` without `WHERE` shows as every row deleted (SQLite has no `TRUNCATE`); needs WAL mode ([details](#sqlite)) |

Rows are only counted on your server: their contents never leave it. **To the second** means **Rewind to just before this** goes back to the second before the change: other changes earlier in that same second aren't in the copy. The notes below describe PostgreSQL.

## What it shows, and what it can't

- **Times are commit times.** A change becomes visible when its transaction commits, so that is the moment shown, with microseconds. Rewinding to one microsecond before it, or to just before its transaction ID, leaves it out and keeps everything before.
- **Rows are counted exactly** for deletes and updates. For an emptied or dropped table, the count is PostgreSQL's last estimate of the table's size, marked "about".
- **Rolled-back transactions don't count.** Only committed changes are listed; changes in a savepoint are counted with their transaction. Prepared (two-phase) transactions aren't listed.
- **Not who did it.** PostgreSQL's change log doesn't record the user or the application, so neither does Rowsafe. Your application logs or `log_statement` can tell you who.
- **Names of tables that are gone.** The agent notes table names every 15 minutes and keeps them for 8 days, so a table dropped or emptied later is still named. A table created and dropped within a few minutes may show as "a table Rowsafe couldn't name".
- **The newest minute.** When your range ends now, the agent first sends the latest changes to your storage and waits up to a minute for them.
- **Limits.** One search covers at most 7 days, lists the 100 biggest transactions, and reads at most about 8 GB of stored change log; over that, it searches the most recent part and says so. It can only look back as far as your oldest kept backup. `VACUUM FULL`, `CLUSTER` and table rewrites are not reported: they don't lose rows.
- **ClickHouse.** The search reads the record of the parts ClickHouse wrote that Rowsafe keeps for restores to any second (see [Protect ClickHouse](/docs/guides/clickhouse#how-restores-to-any-second-work)), so it is quick and needs no extra disk. A `DELETE` (lightweight or `ALTER ... DELETE`) is counted exactly; an `UPDATE` shows the rows of the parts it rewrote ("up to"), since ClickHouse doesn't count the rows it changed; `TRUNCATE` and `DROP PARTITION` both show as an emptied table. Times are when ClickHouse wrote a change's first part, with microseconds.
- **Cost on the server.** The search runs at low CPU and IO priority, downloads the change log for the range from your storage a few pieces at a time (16 MB each, deleted as soon as they are read), and needs about 1 GB of free disk under `/var/lib/rowsafe`.

## SQLite

SQLite's change log holds pages, not statements: each transaction is the pages it wrote. So the agent works differently:

- **It replays, then compares.** The agent restores the file as it was at the start of your range into a private scratch file on your server (the newest backup before it plus every change up to it), then replays the range one transaction at a time. Before each transaction, it keeps the pages it will replace; after, it compares the rows on the pages that changed, table by table, by primary key (or row number). Rows that are gone were deleted, rows whose content changed were updated, and a table gone from the file was dropped. Values are compared as hashes on your server, never read out, and the scratch file is deleted when the search ends.
- **Times are when Rowsafe copied each change**, within a second of its commit, to the millisecond. **Rewind to just before this** goes back one millisecond: when Rowsafe copied other changes in that same millisecond, the result says so, because the copy leaves them out too.
- **What it lists.** Deleted rows, changed rows and dropped tables, counted exactly. A `DELETE` without `WHERE` shows as every row deleted (SQLite has no `TRUNCATE`). Added rows aren't listed. A `VACUUM` moves rows to other pages without changing them, so it isn't listed; a table rebuilt by a migration (create, copy, rename) is, with a note. A transaction too big to compare (it rewrote more than about 512 MB, a `VACUUM` of a large file for example) is listed as such, without counts.
- **Needs WAL mode.** In rollback-journal mode there is no record of each change to read: Pulse offers to [turn WAL on](/docs/guides/sqlite#turn-on-continuous-backups).
- **Cost on the server.** It needs about the database file's size free under `/var/lib/rowsafe`, for the scratch file, and stops after 10 minutes of replay: a busy week may need a few searches over shorter ranges, and the result says how far it got.
- There is one database per file, so the database filter doesn't apply.
