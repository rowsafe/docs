## Add a database

Save the database once with `rowsafe add`. On the server, it also protects it:

```sh
sudo rowsafe add shop postgres://app:PASSWORD@localhost:5432/shop
```

Rowsafe checks that it connects (read-only), saves the connection string (readable only by root), then shows what turning on backups changes and asks first. It changes PostgreSQL's settings with `ALTER SYSTEM` and a reload, and never restarts PostgreSQL by itself: when archiving needs a restart, it says so, and `sudo rowsafe restart shop` does it when you choose (it asks first). Rowsafe notices the restart, checks that changes reach your bucket, then takes the first full backup and the first Proof.

### MySQL and MariaDB

```sh
sudo rowsafe add crm mysql://root:PASSWORD@localhost:3306/crm
```

The same, with two differences:

- Rowsafe backs up with its own account on the server (`rowsafe@localhost`, with only the rights backups need; its password stays on the server). When it has none yet, `rowsafe add` asks, then creates it: root logs in through the server's socket (Debian and Ubuntu), or with the password in the connection string.
- Backups need the binary log (MySQL's change log). Rowsafe writes its settings to its own option file, which MySQL reads at start (`/etc/mysql/conf.d/zz-rowsafe.cnf`). MySQL 8 has the binary log on already; when it is off (MariaDB's default), the server needs a restart, which `sudo rowsafe restart crm` does when you choose.

Backups use Percona XtraBackup (MySQL) or mariadb-backup (MariaDB): the installer installs it on a MySQL or MariaDB server, and the plan says when it is missing.

### MongoDB

```sh
sudo rowsafe add docs 'mongodb://admin:PASSWORD@localhost:27017/?authSource=admin'
```

Turning on backups changes nothing in MongoDB and never restarts it: Rowsafe copies its change log (the oplog) to your bucket about every minute and takes a full backup every day.

- Rowsafe backs up with its own MongoDB user (`rowsafe`, its password stays on the server). When it has none yet, `rowsafe add` asks, then creates it with the administrator login in the connection string (none needed when MongoDB doesn't check logins).
- The oplog needs a replica set. A standalone server becomes a replica set of one member, which changes nothing for your apps but needs one restart: the installer does it when you say yes (`--mongodb-replica-set`), and `rowsafe add` says so.

### Redis and Valkey

```sh
sudo rowsafe add cache redis://:PASSWORD@localhost:6379
```

Turning on backups changes nothing in Redis and never restarts it: Rowsafe follows it as a hidden replica that serves nothing, copies every change to your bucket about every minute, and takes a snapshot every day.

- Rowsafe follows it with its own user (`rowsafe`, its password stays on the server). When it has none yet, `rowsafe add` asks, then creates it with the password in the connection string. When Redis can't keep the user by itself (no ACL file, no configuration file it may rewrite), Rowsafe adds the user's line (its password's hash, never the password) to the configuration file.
- When Redis won't let Rowsafe follow it (replication refused, or `min-replicas-to-write`), backups are the daily snapshots only: restores go back to those, not to any second, Marks can't be taken, and `sudo rowsafe status` says why.

### SQLite

A SQLite database is a file your app opens, so the installer adds it: it gives the agent access to the file (an ACL; owners and others' access stay as they are) and turns on its backups.

```sh
curl -fsSL https://rowsafe.sh | sudo sh -s -- --no-account --sqlite /var/www/app/storage/database.sqlite
```

On a terminal, the installer also offers the SQLite files running apps have open. Rowsafe copies each change from the file's `-wal` file to your bucket within seconds and takes a whole copy every day, kept 7 days. A file that doesn't use WAL mode gets the daily copies only: restores reach the newest one and Marks can't be taken until the app opens it in WAL mode.

### ClickHouse

The installer finds ClickHouse and adds it: it gives Rowsafe its own ClickHouse user (a file in `users.d` that ClickHouse loads by itself, or SQL with an administrator's login) and turns on its backups. Nothing restarts. Rowsafe copies each new part to your bucket as it appears, and takes ClickHouse's own backup every hour (in full on Sundays).

### OpenSearch, Qdrant and Meilisearch

The installer finds them and adds them: it gives Rowsafe its own login (OpenSearch) or key (Qdrant, Meilisearch, made with the master key once, which Rowsafe never keeps) and a folder for snapshots. Nothing restarts.

These keep no log of their changes, so backups are snapshots, taken often and cheaply (only what changed): OpenSearch every 5 minutes, Meilisearch every 15, Qdrant every 15 from version 1.17 (every hour before). A restore goes back to a snapshot, not to any second, and a Mark is a snapshot taken when you ask.

### Added before

A database the installer already set up is found again: `rowsafe add` with its connection string saves the name, and that name works for every command. `--yes` answers the question (for scripts); it never restarts PostgreSQL.

## Use it

```sh
sudo rowsafe status shop                 # protected? backups, the change log, Proof
sudo rowsafe mark shop before-migration  # a named restore point (a Mark)
sudo rowsafe marks shop
sudo rowsafe backups shop                # backups, newest first
sudo rowsafe backup shop --type diff     # back up now
sudo rowsafe proof shop                  # run the restore test now
sudo rowsafe proofs shop                 # restore test results
sudo rowsafe pulse shop                  # health score and findings (see Pulse below)
```

Every command takes `--json`. Only root (and the agent's own user) can use it.

## Restore

Restore a copy of the database as it was at any second, or at a Mark, next to production. Production is never touched:

```sh
sudo rowsafe restore shop --to "10m ago"     # or "14:04", "2026-10-17 14:04", or a Mark: --to before-migration
sudo rowsafe restores shop                   # the copy, the recovery window, recent restores
sudo rowsafe rewind compare shop             # rows deleted, changed or added since, by primary key
sudo rowsafe rewind rows shop public.orders  # bring the deleted rows back (a Mark first; you type the name)
                                             # MySQL, MariaDB, MongoDB: DATABASE:TABLE, e.g. crm:orders
                                             # Redis, Valkey: DB:PATTERN, e.g. '0:user:*'
                                             # SQLite: main:TABLE; ClickHouse: DATABASE:TABLE
sudo rowsafe rewind drop shop                # delete the copy (it goes by itself after 24 hours)
```

The copy runs on the server, on a private socket only the agent's user can reach; `sudo rowsafe tasks shop --type rewind_copy --json` shows where. One copy at a time; `sudo rowsafe rewind extend shop --hours 48` keeps it longer (at most 7 days).

## Alerts

Tell Rowsafe where to send alerts: Slack, Discord, [ntfy](https://ntfy.sh) (to your phone) or a webhook.

```sh
sudo rowsafe channels add --type slack --name ops --url https://hooks.slack.com/services/T000/B000/XXXX
sudo rowsafe channels add --type ntfy --name phone --topic a-topic-nobody-can-guess
sudo rowsafe channels add --type discord --name ops --url https://discord.com/api/webhooks/...
sudo rowsafe channels add --type webhook --name pager --url https://hooks.example.com/rowsafe
sudo rowsafe channels test ops           # send a test now
sudo rowsafe alerts                      # what is firing; --all for resolved ones too
sudo rowsafe alerts ack ID               # no more reminders for it
```

You get a message when an alert starts and when it ends, plus a daily reminder for a critical one nobody acknowledged. Each says what to do, with the `sudo rowsafe` command. Alerts on the server:

- **Backups:** no successful backup in 26 hours, no full backup in 8 days.
- **Proof:** the restore test failed, or none passed in 8 days.
- **Continuous backup:** copying changes to your bucket keeps failing.
- **PostgreSQL:** Rowsafe can't reach it, or it is still waiting for a restart after setup (24 hours).
- **Setup:** the check that backups reach your bucket failed.
- **Disk:** less than 15% free, or full within 14 days at its growth of the last two weeks (critical within 3).

A webhook is signed like the dashboard's ([Webhooks](/docs/reference/webhooks)), and prints its signing secret once. URLs stay on the server, readable only by root. They must be `https://`, or `http://` to the server itself or a private network (for example ntfy on your LAN). `--min-severity info|warning|critical` picks what goes where (default `warning`).

**A server can't tell you it is down.** Alerts run on the server, so while it (or the agent) is stopped, nothing is sent. When it comes back after more than 10 minutes, you get one message saying how long it was out. The dashboard watches from outside and alerts you while the server is down.

## Your weekly Pulse

Every Monday at 08:00 UTC, the alert channels above get a summary of the week for each database: protected or not, backups and any that failed, the restore test, how far back you can restore, Marks, alerts and free disk. A webhook gets it as JSON too (event `weekly_report`).

```sh
sudo rowsafe report              # on or off, where it goes
sudo rowsafe report --preview    # this week so far
sudo rowsafe report --send-test  # send it now
sudo rowsafe report --off        # stop it (--on to start again)
```

It is on once a channel exists; the first one comes the Monday after. Email needs the dashboard.

## Restore onto another server

When the server is lost (or to move the database), restore it on a new server from its backups:

1. **Install Rowsafe on the new server** with `--no-account`, the **same bucket** and, at the passphrase question, **Use my own passphrase**: paste the old server's (it's `ROWSAFE_REPO_CIPHER_PASS` in its `/etc/rowsafe/agent.env`). Install the same PostgreSQL major version. Don't add a database there.
2. **Restore it there:**

```sh
sudo rowsafe restore shop --from-bucket                 # the latest point the backups hold
sudo rowsafe restore shop --from-bucket --to "14:04"    # or any second before
```

Rowsafe reads `shop`'s backups with the new server's own storage settings: the passphrase stays on that server and is never sent anywhere. It restores into the empty PostgreSQL there (after you type the name; its own empty data is kept aside), or a new cluster with `--new-cluster`. Then it protects it: a full backup and a Proof, in a new folder of the bucket. The old server's backups stay as they are. A wrong passphrase or bucket stops before anything changes, and says so.

**Test it first:** `sudo rowsafe proof shop --from-bucket` on another server installed the same way restores `shop`'s newest backup into a scratch copy there, checks it starts and lists its databases, then deletes it. Nothing changes on either server. It proves the backups and the passphrase work without the old server. It can't compare with production there: that's the old server's own weekly Proof.

**To move a database** with the old server still running: stop your app's writes, `sudo rowsafe mark shop before-move` on the old server (everything until then is in the bucket once the Mark is), restore on the new server, then point your app at it. `--as NAME` restores it under another name; `--port N` picks the empty cluster when there are several. The old server's Marks stay on it: restore to a time instead.

## Upgrade PostgreSQL

Move to a new major version (16 to 17 or 18) with a test on a copy first and a way back:

```sh
sudo rowsafe upgrade shop                            # versions, and the majors your package sources offer
sudo rowsafe upgrade shop --to 18 --rehearse-only    # test it on a copy of the latest backup; production isn't touched
sudo rowsafe upgrade shop --to 18                    # the upgrade: you type the name; a Mark first
sudo rowsafe upgrade undo shop                       # back to 16, for 7 days
sudo rowsafe upgrade cleanup shop                    # remove the kept 16 (it goes by itself after 7 days)
```

1. **Check and rehearse:** Rowsafe checks the new version's packages, extensions, disk and pgBackRest, then restores the latest backup into a scratch copy, upgrades it and checks every database opens. The report gives the expected downtime. A pass allows the upgrade for 14 days.
2. **Upgrade:** it asks you to type the database's name, saves a Mark, stops PostgreSQL, runs `pg_upgradecluster` (same port, same settings) and starts the new version. If anything fails before it accepts connections, the old version is put back. Then backups move to the new version: a full backup and a Proof.
3. **Undo:** Safe mode (the default) keeps the old version stopped, so undo switches back in seconds; what was written after the upgrade stays in the kept new version. `--mode fast` hard-links the files (less disk, less downtime), and its undo restores the old version from the backup at the Mark instead.

The server's security updates and a reboot work the same way, with a Mark first: `sudo rowsafe security-updates shop` (services keep running) and `sudo rowsafe reboot shop` (you type the server's name).

Root allows each once, at install or later: `sudo rowsafe-allow restart updates`, `security-updates`, `reboot`. Debian and Ubuntu with PostgreSQL from packages; in Docker, change the image in your compose file. More in [Update and upgrade](/docs/guides/updates#major-upgrades).

### Rewind the whole database

When the whole database has to go back:

```sh
sudo rowsafe rewind database shop --to "10m ago"   # or a time, or a Mark: --to before-migration
sudo rowsafe rewind undo shop                      # put it back as it was before the rewind (7 days)
sudo rowsafe rewind cleanup shop                   # delete the data kept aside, to free disk
```

You type the database's name first (`--yes` in scripts). Rowsafe saves a Mark, stops PostgreSQL, restores it to that point and starts it again: apps can't connect meanwhile. The data from before is kept aside on the server for 7 days. It needs the restart permission the installer asks for; without it, restore a copy and bring back rows instead.

Restores, Proof and later rewinds keep working after a rewind or an undo: Rowsafe takes a full backup right after and follows PostgreSQL's history, so a copy at any second of the recovery window shows the data as it was then, even from before the rewind.

## Pulse, with history

```sh
sudo rowsafe pulse shop      # health score and findings, with what the agent saw over time
sudo rowsafe fix shop        # apply what it found (asks first)
sudo rowsafe top shop        # the queries that took the most time, and which got slower
sudo rowsafe insights shop   # largest tables, unused indexes, bloat
sudo rowsafe pulse           # every database on the server
```

The agent keeps what it reads, on the server, so `pulse` also finds what one reading can't:

- **The disk filling up:** when it will be full at its growth of the last two weeks. Alerts warn you within 14 days.
- **Queries that got slower:** more than twice as slow today as yesterday. When their tables' statistics may be out of date, `rowsafe fix` refreshes them (`ANALYZE`); otherwise it says what usually causes it.
- **Backups:** whether the database is protected, from the same check as `rowsafe status`.

`top` compares any range up to 14 days with the one before it: `--since 1h`, `--since 168h`, and `--query ID` for one query hour by hour. It needs [pg_stat_statements](/docs/guides/tuning).

What it keeps, next to its state in `/var/lib/rowsafe` (readable only by the agent's user, a few MB at most): hourly averages of the disk, database size, connections, cache and commits for 30 days; each hour's 50 busiest queries for 14 days, as PostgreSQL normalizes them (values become `$1`); and the newest reading. The queries running right now stay in memory. Forecasts and slow-downs need about two days of readings first.

Without a saved connection string (a database the installer set up), `pulse` works from the agent's readings alone; `rowsafe add` the database to apply fixes.

## Docker

PostgreSQL in the official `postgres` image works the same way, with Rowsafe as one more service in your compose file. Nothing is installed on the host. Save this as `compose.yml` (or add the lines marked `Rowsafe` to yours):

```yaml
services:
  postgres:
    image: postgres:17
    restart: unless-stopped
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
      - pgsocket:/var/run/postgresql   # Rowsafe
      - rowsafe-spool:/rowsafe-spool   # Rowsafe

  # Rowsafe
  rowsafe:
    image: ghcr.io/rowsafe/agent:pg17
    hostname: db-1
    user: "999:999"
    restart: unless-stopped
    depends_on: [postgres]
    env_file: rowsafe.env
    shm_size: 256m
    volumes:
      - pgdata:/var/lib/postgresql/data:ro
      - pgsocket:/var/run/postgresql
      - rowsafe-spool:/rowsafe-spool
      - rowsafe-state:/var/lib/rowsafe

volumes:
  pgdata:
  pgsocket:        # Rowsafe
  rowsafe-spool:   # Rowsafe
  rowsafe-state:   # Rowsafe
```

And `rowsafe.env` next to it (`chmod 600`, never commit it), with your bucket:

```sh
ROWSAFE_URL=unix:///var/lib/rowsafe/control.sock
ROWSAFE_REPO_S3_ENDPOINT=s3.eu-central-1.amazonaws.com
ROWSAFE_REPO_S3_REGION=eu-central-1
ROWSAFE_REPO_S3_BUCKET=myapp-backups
ROWSAFE_REPO_S3_KEY=...
ROWSAFE_REPO_S3_KEY_SECRET=...
ROWSAFE_REPO_CIPHER_PASS=...   # your encryption key: save it in your password manager first
```

`ROWSAFE_URL=unix://…` is what makes it run on its own: the control plane runs inside the `rowsafe` container and nothing talks to rowsafe.sh. Any S3-compatible bucket works (AWS S3, Cloudflare R2, Backblaze B2, MinIO…). Without the encryption key no backup can be read, by you or anyone: `openssl rand -base64 32` makes a good one.

Then:

```sh
docker compose up -d
docker compose exec rowsafe rowsafe add shop postgres://postgres:PASSWORD@postgres:5432/shop
docker compose restart postgres    # when it suits you: a few seconds, apps reconnect
docker compose exec rowsafe rowsafe status shop
```

`rowsafe add` checks that the connection string reaches the PostgreSQL that shares the socket volume, then shows what backups need and asks first. Rowsafe never restarts PostgreSQL by itself: you restart the container when it suits you, and Rowsafe takes the first full backup and the first Proof. Every command above works the same way, with `docker compose exec rowsafe rowsafe …` in place of `sudo rowsafe …`:

```sh
docker compose exec rowsafe rowsafe mark shop before-migration
docker compose exec rowsafe rowsafe backups shop
docker compose exec rowsafe rowsafe restore shop --to before-migration
docker compose exec rowsafe rowsafe channels add --type slack --name ops --url https://hooks.slack.com/...
```

A restored copy runs inside the `rowsafe` container. To update Rowsafe, `docker compose pull rowsafe && docker compose up -d rowsafe` (PostgreSQL keeps running; the container never updates itself).

- PostgreSQL 18 and later: mount the data volume at `/var/lib/postgresql` in both services and use `ghcr.io/rowsafe/agent:pg18`. Alpine images (`postgres:17-alpine`): use `agent:pg17-alpine` and `user: "70:70"`.
- Use Docker on a Linux server for production: Docker Desktop (macOS, Windows) is fine to try Rowsafe.
- `rowsafe login` doesn't connect a Docker setup to the dashboard yet: for the dashboard, set up the agent with an account ([Run the agent in Docker](/docs/guides/docker)).

## Keep a second copy

One bucket is one place that can go wrong: deleted by mistake, an account locked, leaked keys. A second copy keeps the backups and the change log in a second bucket too, ideally at another provider:

```sh
sudo rowsafe secondcopy add shop
```

It asks for the bucket's URL (for example `https://s3.eu-central-003.backblazeb2.com/shop-copy`) and its key, the secret without showing it. It tests the bucket first (writes, reads back and deletes a small file) and saves nothing if that fails. It refuses the bucket you already use. Without a terminal, pass `--endpoint URL` (and `--region` when it can't tell from the URL) and put the key in the environment:

```sh
sudo ROWSAFE_REPO2_S3_KEY=... ROWSAFE_REPO2_S3_KEY_SECRET=... \
  rowsafe secondcopy add shop --endpoint https://s3.eu-central-003.backblazeb2.com/shop-copy --yes
```

- Its key and a **new passphrase** go in `/etc/rowsafe/agent.env`, next to the first storage's, and nowhere else. The passphrase is shown once: keep it in your password manager, apart from the first one. Without it, the copy can't be restored on another server.
- The agent restarts to read them (not while a backup, Proof or restore runs). PostgreSQL doesn't: its change log goes to both buckets after a reload.
- The first full backup into the copy runs right away, then one every Sunday at 03:30 UTC; the last 2 are kept. Proof alternates between the two buckets.
- If the second bucket is down, PostgreSQL and the first bucket carry on, the change log waits in a queue on the server (at most 256 files), and the copy catches up by itself. With alerts set up (`sudo rowsafe channels add`), **Second copy not up to date** fires after 30 minutes.

```sh
sudo rowsafe secondcopy shop                  # where it is, how far it is, its backups
sudo rowsafe status shop                      # shows it too
sudo rowsafe backup shop --second-copy        # a full backup to it now
sudo rowsafe proof shop --second-copy         # a restore test from it now
sudo rowsafe secondcopy remove                # turn it off (what is in its bucket stays there)
```

If the first bucket is lost, restore from the second:

```sh
sudo rowsafe restore shop --to before-migration --second-copy
```

It reaches as far as the newest change that got to the second bucket (usually within a minute of the first). To change the key, run `sudo rowsafe secondcopy add` again with the same bucket: the passphrase stays. The second copy covers every database on the server.

## From your computer, over SSH

Use the server from your laptop, or let an AI agent on it save Marks, with nothing opened on the network: the `rowsafe` CLI goes through your own `ssh` (your keys, `ssh-agent` and `~/.ssh/config`).

```sh
rowsafe add shop ssh://root@db1.example.com    # or --ssh root@db1.example.com, ssh://root@db1:2222, a Host alias
rowsafe status shop
rowsafe mark shop before-migration
rowsafe restore shop --to "10m ago"
rowsafe rewind compare shop
rowsafe alerts shop
```

`rowsafe add` checks that Rowsafe on the server protects that database (read-only) and saves only the server's address on your computer: the connection string stays on the server. When the database has another name there, add `--database NAME`. Then `status`, `mark`, `marks`, `backups`, `backup`, `proof`, `proofs`, `restore`, `restores`, `rewind`, `tasks`, `alerts` and `channels` work as they do with `sudo` on the server. `pulse`, `fix`, `insights`, `top`, `activity`, `settings` and `tune` run on the server with its own `rowsafe`, on the database you saved there with `sudo rowsafe add`. With `rowsafe use shop` in a project, you can leave the name out.

Each command opens one SSH connection and runs Rowsafe's bridge on the server (`/opt/rowsafe/rowsafe-agent control-bridge`), which talks to the agent on its private socket. It runs as root: log in as root, or as a user who may run the bridge with `sudo` without a password. Only that one command, on the server:

```sh
echo 'deploy ALL=(root) NOPASSWD: /opt/rowsafe/rowsafe-agent control-bridge' | sudo tee /etc/sudoers.d/rowsafe
sudo chmod 0440 /etc/sudoers.d/rowsafe
```

Without a terminal (scripts, AI agents), `ssh` never asks anything: the key must work without a question (`ssh-agent`, or a key without a passphrase), and the server's host key must already be known (connect once with `ssh` yourself). On Windows, Rowsafe uses the OpenSSH client that comes with Windows (`ssh.exe`). Set `ROWSAFE_SSH` to use another ssh command, such as `ssh -F ~/.ssh/work-config`.

The bridge needs an agent from this release or later: the agent updates itself, usually within a day. `rowsafe preview` reads the migration file on your computer, so it doesn't run over SSH yet.

## What runs by itself

- **Continuous backups:** every change is copied to your bucket within about a minute (PostgreSQL's change log, MySQL's and MariaDB's binary log), plus a full backup every Sunday at 01:00 UTC and a differential one the other days (MongoDB: its oplog, and a full backup every day at 01:00 UTC; Redis and Valkey: every change, and a snapshot every day at 01:00 UTC; SQLite: every change from its -wal file, and a whole copy every day at 01:00 UTC; ClickHouse: each new part, and a backup every hour; OpenSearch, Qdrant and Meilisearch: a snapshot every few minutes).
- **Proof:** every Sunday evening Rowsafe restores the latest backup into a scratch copy on the server and checks it. The first one runs right after the first backup.
- **Updates:** the agent updates itself to the release Rowsafe published as stable, after checking its signature. Set `ROWSAFE_AUTO_UPDATE=false` in `/etc/rowsafe/agent.env` to turn that off.

The only thing the server fetches from Rowsafe is that release information (from releases.rowsafe.sh). Nothing about your databases is sent.

## Prometheus and Grafana

If you run Prometheus, the server can serve what it knows as metrics: whether each database is protected, the age of its newest backup and passing Proof, continuous backup, how far back you can restore, backup sizes and durations, the alerts firing, the agent's version and whether an update is waiting, plus the database and server readings the agent collects (connections, cache hit, disk free, replication lag, CPU, memory...). It's off until you turn it on: add this line to `/etc/rowsafe/agent.env`, then run `sudo systemctl restart rowsafe-agent`.

```sh
ROWSAFE_METRICS_LISTEN=127.0.0.1:9188
```

Point Prometheus at `127.0.0.1:9188` (path `/metrics`). If Prometheus runs on another machine, listen on an address it can reach and set a token too: the agent refuses any address other than loopback without one, and every scrape must send it as a bearer token.

```sh
ROWSAFE_METRICS_LISTEN=10.0.0.5:9188
ROWSAFE_METRICS_TOKEN=...   # at least 16 characters, e.g. from: openssl rand -hex 32
```

The metrics travel over plain HTTP: keep that address on a private network or a VPN, or put a TLS proxy in front. If a setting is wrong or the port is taken, the agent says why in its log (`journalctl -u rowsafe-agent`) and keeps backing up.

Every series is named `rowsafe_*` with the labels `database` and `host`; times are Unix timestamps, so a backup's age is `time() - rowsafe_backup_last_success_timestamp_seconds`. Ready-made files are in [integrations/prometheus](https://github.com/rowsafe/rowsafe/tree/main/integrations/prometheus): the scrape job, alert rules and a Grafana dashboard (Dashboards → New → Import). The rules add the one alert the server can't send itself: that the server or the agent is down.

## Connect it to the dashboard later

```sh
sudo rowsafe login
```

After the usual login in the browser, it asks whether to connect this server to your account, then does it with nothing to reinstall:

- The agent restarts and connects to the account. PostgreSQL doesn't restart: it keeps sending its changes to your bucket the whole time, so backups never stop.
- Each database moves to the account under the same name, with its backups (the same files, in the same bucket), Proofs and Marks.
- Rowsafe checks that each database's backups are already set up as before: nothing changes on PostgreSQL. If anything doesn't work out, the server is put back as it was, still backing up, and the command says what happened.

It stops before changing anything if the account already has a database with the same name, or while a backup, Proof or restore is running (try again once it's done). A copy restored on the server isn't listed in the dashboard: delete it first (`sudo rowsafe rewind drop shop`), or it goes by itself when it expires. Without a terminal (scripts, AI agents), pass `--yes`, and `--key rsk_…` to log in with an API key.

Once connected, `sudo rowsafe logout` only signs the CLI out: the server stays connected. To run it on its own again, run the installer with `--no-account`. The account then sees the server offline: remove it in the dashboard.
