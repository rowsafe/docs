---
title: Backups and point-in-time recovery
description: Full and differential backups plus a continuous change log let you restore to any second in your recovery window.
---

A nightly dump can only take you back to last night. Rowsafe combines two things so you can go back to any second:

1. **Backups**: a copy of the whole database, taken on a schedule.
2. **A continuous change log**: every change the database makes, archived to your bucket within about a minute.

To restore, Rowsafe starts from a backup and replays the change log up to the moment you choose. Together, this is **Rewind**: every change saved, restore to any second.

## Backup types

| Type | What it copies | Default schedule |
|---|---|---|
| **Full** | Everything | Sundays 01:00 UTC |
| **Differential** | What changed since the last full backup | Monday to Saturday 01:00 UTC |
| **Incremental** | What changed since the last backup of any type | On demand only |

Run one now with `rowsafe backup app` (a full backup by default), or `rowsafe backup app --type diff`.

Backups are compressed, then **encrypted on your server** before they are uploaded. The bucket only ever holds ciphertext.

## The recovery window

You can restore to any moment from the **start of your oldest kept full backup** up to the **last archived change**.

- **Retention** is a count of full backups. The default is 2, which with weekly fulls keeps about two weeks. Change it (1 to 52) in the database's settings in the dashboard, or with `rowsafe set app --retention-full 4`.
- Old backups, and the change log they need, are removed automatically after each backup. Don't add a lifecycle rule to the bucket that deletes objects: it would break restores.
- `rowsafe status app` and the dashboard show the start of your current recovery window.

## How much can you lose?

At most about **a minute** of changes, and usually less. Changes are archived as soon as a log segment fills up, and at least every minute on a quiet database.

Databases set up before archiving every minute was the default archive at least every 5 minutes. **Health** shows "Backups can be up to 5 minutes behind" for them; **Apply fix** changes the setting with a reload, without a restart.

If archiving stops working (for example the bucket's keys were rotated), Rowsafe raises a critical alert within about 10 minutes and the database stops counting as [protected](/docs/concepts/protection-status).

## Restoring

You restore in the dashboard, on the database's **Rewind** tab, to:

- **a point in time**: any second in the window, for example one second before a bad migration;
- **a [Mark](/docs/concepts/restore-points)**: a named restore point you set earlier.

Two ways, both on your own server:

- **Restore a copy** next to production, compare it with production and **bring back** the rows you lost. Production keeps running.
- **Rewind the whole database** to that moment, for the worst case. You can undo it for 7 days.

When the server itself is lost, you restore the backups by hand onto a new server with pgBackRest. [Restore a database](/docs/guides/restore) describes all three.

Rowsafe proves every week that restoring works, with [Proof](/docs/concepts/restore-drills), the weekly restore test.

## By database

| | Backups | Change log | Restore to |
|---|---|---|---|
| PostgreSQL | pgBackRest: weekly full, daily differential | the WAL ([details](/docs/concepts/postgresql)) | any second, or a Mark |
| MySQL, MariaDB | XtraBackup or mariadb-backup: weekly full, daily differential | the binary log ([details](/docs/concepts/mysql)) | any second, or a Mark |
| MongoDB | `mongodump`: a full backup every day | the oplog ([details](/docs/guides/mongodb#what-rowsafe-does)) | any second, or a Mark |
| ClickHouse | ClickHouse's own `BACKUP`: weekly full, hourly differential | none | a backup (one every hour), or a Mark ([details](/docs/guides/clickhouse)) |
| Redis, Valkey | a full snapshot (RDB), sent the way Redis sends one to a new replica | every change, from the agent attached as a replica ([details](/docs/concepts/redis)) | about a second, or exactly a Mark |
| OpenSearch | OpenSearch's own snapshots: every 30 minutes, a full one every day | none | a snapshot, or a Mark ([details](/docs/guides/opensearch#restores-go-back-to-a-snapshot)) |
| Qdrant | Qdrant's own full snapshot, every hour | none | a snapshot, or a Mark ([details](/docs/guides/qdrant#restores-go-back-to-a-snapshot)) |
| Meilisearch | Meilisearch's own snapshot, every hour | none | a snapshot, or a Mark ([details](/docs/guides/meilisearch#restores-go-back-to-a-snapshot)) |

Rewinding the whole database stops PostgreSQL, MySQL and MariaDB briefly while the data is swapped; MongoDB, ClickHouse, Redis, Valkey, OpenSearch, Qdrant and Meilisearch keep running.
