---
title: Restore a database
description: Rewind a PostgreSQL database to any second or to a Mark. Restore a copy and bring back rows, or rewind the whole database, in one click. By hand with pgBackRest when the server is lost.
---

**Rewind** saves every change your database makes, so you can go back to any second in your recovery window, or to a **Mark** you set before a risky change. You do it in the dashboard: open the database's **Rewind** tab, then **Rewind**.

There are two ways back:

- **Restore a copy** of the database as it was, next to production, compare it, and **bring back** the rows you lost. Production keeps running. This is what you want most of the time.
- **Rewind the whole database** to that moment. For the worst case, when too much is damaged to repair row by row. You can undo it.

Everything happens on your server. Rowsafe never sees your data: only names, counts and sizes reach it.

## Which one to use

| What happened | Do this | What happens to production |
|---|---|---|
| Rows deleted or overwritten by mistake: a `DELETE` without `WHERE`, a bad script, a bug | [Restore a copy](#restore-a-copy), [compare](#compare-with-production), [bring back rows](#bring-back-rows) | Only the rows you choose are put back. Everything else, including what was written since, stays. |
| You want to see what the data looked like at 14:04 | [Restore a copy](#restore-a-copy) | Nothing. |
| A migration or a script damaged many tables, or a table was dropped | [Rewind the whole database](#rewind-the-whole-database) | PostgreSQL stops while Rowsafe restores it. Everything written after the moment is removed, and kept aside for 7 days so you can undo. |
| The server is lost, or you want the database on another server | [Restore by hand](#advanced-restore-by-hand-or-to-another-server) | Nothing: you restore onto a new server. |

You can go back to any second from the start of your oldest kept full backup up to the last change that reached your bucket: at most about a minute before now.

## Restore a copy

<Steps>
<Step>

### Pick the moment

The page shows your recovery window. Pick a time, in your own time zone, to the second: just before the mistake, for example 14:04:00 for a `DELETE` at 14:05. Or pick a **Mark** from the list (on the **Marks** page, **Restore a copy at this Mark** does the same): the copy then has everything committed before the Mark and nothing after it.

</Step>
<Step>

### Restore it

Click **Restore a copy**. The copy is kept for 24 hours by default; you can choose up to 7 days. The page shows the progress. It takes about as long as a [Proof](/docs/concepts/restore-drills) run (the **Proof** tab shows how long recent runs took), and longer when the moment is far from the last backup, because there are more changes to replay.

</Step>
<Step>

### Use it

When the copy is ready, you see the last change in it, its size and when it will be deleted. **Extend** keeps it longer, **Delete** removes it now. Then [compare it with production](#compare-with-production).

</Step>
</Steps>

What the copy is:

- **On your server, next to production.** Rowsafe restores a backup and replays the changes up to your moment, the way the weekly Proof does. Every database inside that PostgreSQL server is in the copy.
- **Isolated.** It listens only on a private Unix socket, with no network port, so your applications can't connect to it by mistake. It is read-only, it never archives into your bucket, and it runs at low CPU and IO priority.
- **Deleted by itself** when it expires, even if your server can't reach Rowsafe at that moment. A copy about to expire shows up in **Health**, with **Keep it 24 hours longer**.
- **One at a time.** Each database has at most one copy. Delete it to restore another moment.

It needs free disk of about **1.3 × the database size + 1 GB**, in `/var/lib/rowsafe/rewind`. With less, Rowsafe says how much is free and how much it needs, and doesn't start.

## Compare with production

On the copy's card, click **Compare with production**, for every table or the ones you pick. For each table, Rowsafe counts, by primary key:

| Count | Means |
|---|---|
| **Missing in production** | Rows in the copy whose key is gone from production: deleted since. |
| **Changed** | Rows with the same key and different values. |
| **Only in production** | Rows added since. |

The comparison runs on your server: rows never leave it, and only the counts reach Rowsafe. It doesn't change production; it only uses temporary tables.

Some tables are skipped, with the reason next to them:

- **No primary key.** Without one, Rowsafe can't tell which rows are the same. Rewinding the whole database brings such a table back as it was.
- **Too big**: over 5 GB or 20 million rows.
- **Dropped since**, or its key column changed type.
- Comparing every table covers up to 200 tables at a time. With more, pick the tables.

When a table is linked to others by foreign keys (an `orders` table and its `order_items`), Rowsafe shows them together, so you can bring back their rows in one run. A table can also have a note, for example that a column was added since.

## Bring back rows

Select the tables, check the counts, and click **Bring back N missing rows**. Rowsafe asks you to type the database name to confirm. Then, on your server:

1. It saves a **Mark** first, so you can go back to just before this.
2. It puts back the rows that are **missing** in production, only where their key is missing. Rows that exist in production, and rows added since, are left as they are.
3. Parent tables come before their children, and everything in one PostgreSQL database happens in **one transaction**: either every chosen table gets its rows back, or nothing changes.
4. Your application's **triggers don't fire** for these rows, so no duplicate emails or webhooks go out. Foreign keys aren't checked row by row either; Rowsafe checks them itself first (see below).
5. **Sequences** are moved past the keys it brought back, so new rows don't collide with them.
6. A row whose unique value (an email address, say) now belongs to another row is left out and reported as a **conflict**.

You then see what it did, for example "Brought back 1,204 rows in applications and 3,310 in application_notes."

**Also restore rows that were changed** (off by default) also sets the rows that changed since back to the copy's values. Use it when a bad `UPDATE` did the damage.

Limits for one run:

- Up to **50 tables**.
- Up to a number of rows that depends on your [plan](/docs/concepts/plans-and-limits#rewind-limits): 1 million on Free, 10 million on Pro, 50 million on Business (today the agent itself stops at 10 million). Over the limit, nothing is changed: bring back fewer tables at a time.

Nothing is changed, and Rowsafe tells you why, when:

- some rows would point to rows of another table that aren't in production. Add that table to the same run;
- another session holds a lock on one of the tables for more than 5 seconds. Try again in a moment;
- a column was added since and needs a value that the copy doesn't have;
- restoring changed rows would leave rows elsewhere pointing to values that no longer exist. Bring back only the missing rows.

Added columns get their default, generated columns are computed again, and columns removed since are left out.

## Rewind the whole database

<Callout type="warn" title="The worst case only">

Rewinding replaces the live database. Everything written after the moment you pick is removed from it, in **every database inside that PostgreSQL server**, and PostgreSQL is stopped while Rowsafe restores it. When only some rows are wrong, [bring them back](#bring-back-rows) instead.

</Callout>

On the same page, under **Rewind the whole database to this point**, pick the moment and type the database name. The page tells you exactly what will happen, for example "Everything written after 14:04:00 will be removed from the live database. It is kept aside for 7 days so you can undo."

What Rowsafe does:

1. Saves a **Mark**, then checks everything it needs (below). If anything is missing, it stops before changing anything.
2. **Stops PostgreSQL.** Your applications get errors until it's back: about as long as restoring a copy takes (see [Restore it](#restore-it)).
3. **Keeps the current data aside**: it renames the data directory to `<data directory>.before-rewind-<UTC time>`. Same disk, instant, nothing is copied.
4. Restores the backup into a fresh data directory, keeps your configuration, and replays the changes up to your moment, privately, with no network port.
5. **Starts PostgreSQL** and waits until it accepts connections.
6. Takes a full backup, and checks that changes reach your bucket.

If anything fails after PostgreSQL was stopped, Rowsafe puts the original data back and starts it again, as it was. It does that too if its agent restarts in the middle.

**It needs:**

- PostgreSQL **installed on the server**, or in Docker with the optional [container control service](/docs/guides/docker#let-rowsafe-restart-the-container) and the data volume writable for the agent. Without it, [restore a copy](#restore-a-copy) and bring back rows.
- Permission to **restart or stop PostgreSQL**, given when Rowsafe was installed on that server ("Allow Rowsafe to restart or stop PostgreSQL when you ask?"). A server installed before this release needs the install command run again, even if you allowed restarts then: see [Troubleshooting](/docs/troubleshooting#rewind-the-whole-database-isnt-available).
- The **primary**, not a replica.
- **No tablespaces** of your own. Rowsafe can't rewind those in place yet.
- Free disk of about **the database size + 10%** next to the data directory, because the current data stays on the disk for Undo.

When one of these is missing, the button is disabled and says why.

Standby replicas that streamed from this server no longer match it after a rewind. Rowsafe warns you; set them up again.

### Undo a rewind

Until the kept data is deleted, the page shows **Undo rewind**. It swaps the data back the same way: stop PostgreSQL, swap the directories, start it. What was written after the rewind is kept aside in turn, so undoing loses nothing either. Only the latest rewind can be undone.

The data from before the rewind is kept for **7 days**, then deleted by itself. It uses disk meanwhile: **Delete the old data now** frees it, and then the rewind can't be undone. **Health** reminds you while it's there.

## Who can do this

- Only **owners and admins**, and API keys with write access. Every step is in the [audit log](/docs/guides/teams#audit-log).
- **AI agents can't.** No MCP tool restores a copy, brings rows back or rewinds a database. An assistant can show your recovery window with `rewind_window` and tell you what to do. See [Guard](/docs/guides/ai-agents).

## Do it yourself

You don't need any of this: the buttons above do the same. It's here for scripts, and for tables Rowsafe can't compare.

<Accordions>
<Accordion title="The same from a terminal">

`rowsafe rewind` does what the **Rewind** page does, and asks you to confirm the same way:

```sh
rowsafe rewind app                          # the recovery window, the copy, data kept aside
rowsafe rewind copy app --at "14:04"        # your time zone; or --at "10m ago", or --mark before-migration-42
rowsafe rewind compare app                  # every table; or name some: public.orders public.order_items
rowsafe rewind rows app public.orders public.order_items
rowsafe rewind database app --at "14:04"    # rewind the whole database
rowsafe rewind undo app
```

See the [CLI reference](/docs/reference/cli#rewind) for every flag.

</Accordion>
<Accordion title="Read the copy with psql">

The copy listens on a Unix socket in its own directory, only for the `postgres` user of that server, on the port Proof uses (`ROWSAFE_DRILL_PORT`, 55432 by default). `rowsafe rewind app` shows the copy's ID. On the server:

```sh
sudo -u postgres psql -h /var/lib/rowsafe/rewind/<copy-id>/socket -p 55432 -d app
```

It's read-only. Use it to look at a table that has no primary key, or to `pg_dump --table=...` one.

</Accordion>
</Accordions>

## Advanced: restore by hand or to another server

The buttons above restore on the database's own server. Restore by hand with pgBackRest when:

- the server is lost, or its disk is destroyed: the restored server becomes production;
- you want the database on another server, for example to test or to investigate;
- you can't reach Rowsafe. Your backups are a standard pgBackRest repository in your own bucket, and restoring them needs only pgBackRest.

Practise it once on a scratch server before you need it, and write down how long it took. The examples restore a database named `app` on PostgreSQL 18, on a fresh Debian or Ubuntu server.

Need the old state as a separate database, without restoring by hand? [Fork it](/docs/guides/fork): Rowsafe restores any second or Mark into a new database on one of your servers, with its own backups.

<Callout type="warn" title="Two rules">
  **Never restore over the only copy.** Restore to a new server, or at least a new data directory. The old cluster, even a damaged one, is evidence and a fallback.

  **One writer per bucket path.** A restored cluster must not archive into the same repository while the original still runs. Always restore with `--archive-mode=off`.
</Callout>

### What you need

- **The bucket settings and the passphrase** from your secret manager: endpoint, bucket, access key and secret, and the **encryption passphrase**. Without the passphrase, nothing can be restored.
- The repository path, `/rowsafe/<name>` by default, and the stanza, which is the database's name in Rowsafe.
- If the old server is still reachable, its generated configuration has all of this: `/etc/rowsafe/pgbackrest/app.conf`.
- A server with the **same PostgreSQL major version**, the same extensions installed (compare `shared_preload_libraries` and `\dx`), pgBackRest at the same or a newer version, and free disk of at least the data directory's size plus room for WAL.

<Steps>
<Step>

### Prepare the server

With the [apt.postgresql.org](https://wiki.postgresql.org/wiki/Apt) repository configured:

```sh
sudo apt-get install -y postgresql-18 pgbackrest     # creates and starts cluster 18/main
sudo systemctl stop postgresql@18-main
```

Restoring into this new, empty cluster keeps Debian's layout: configuration in `/etc/postgresql/18/main/`, data in `/var/lib/postgresql/18/main`.

</Step>
<Step>

### Configure pgBackRest

Write the default configuration file, so every command finds it:

```sh
sudo install -d -o postgres -g postgres -m 0750 /etc/pgbackrest /var/log/pgbackrest
sudo install -o postgres -g postgres -m 0600 /dev/null /etc/pgbackrest/pgbackrest.conf
sudoedit /etc/pgbackrest/pgbackrest.conf
```

```ini title="/etc/pgbackrest/pgbackrest.conf"
[global]
repo1-type=s3
repo1-s3-endpoint=<account-id>.eu.r2.cloudflarestorage.com
repo1-s3-bucket=<bucket>
repo1-s3-region=auto
repo1-s3-uri-style=path
repo1-s3-key=<access key id>
repo1-s3-key-secret=<secret access key>
repo1-path=/rowsafe/app
repo1-cipher-type=aes-256-cbc
repo1-cipher-pass=<passphrase>
process-max=4
log-level-console=info
log-path=/var/log/pgbackrest

[app]
pg1-path=/var/lib/postgresql/18/main
```

This server only **reads** the repository. Don't run `backup`, `expire` or `stanza-*` commands from it while the original server is alive. If your bucket token only allows the old server's IP address, create a read-only token (Object Read, this bucket only) for this one.

</Step>
<Step>

### Choose the backup and target

```sh
sudo -u postgres pgbackrest --stanza=app info
```

This lists every backup, with start and stop times, and the WAL archive range. Any moment from the end of the oldest full backup to the end of the archive is reachable.

For a Mark (a named restore point), look it up on your computer:

```sh
rowsafe marks app
```

Use Marks with the status `archived`. Note the **RESTORE FROM BACKUP** column: you need it below.

</Step>
<Step>

### Restore

The new cluster's data directory must be empty. **Check the path twice**: this deletes the contents of the new, empty cluster, never an existing production one.

```sh
sudo -u postgres sh -c 'find /var/lib/postgresql/18/main -mindepth 1 -delete'
```

Then run one of the following.

#### To the latest state

Replays all archived WAL, then promotes:

```sh
sudo -u postgres pgbackrest --stanza=app --archive-mode=off restore
```

#### To a point in time

Stops just before the mistake, then promotes. Always give a UTC offset:

```sh
sudo -u postgres pgbackrest --stanza=app --archive-mode=off \
  --type=time --target="2026-09-20 14:05:00+00" --target-action=promote restore
```

pgBackRest picks the newest backup that ends before the target. Pass `--set=<label>` from `pgbackrest info` to choose one yourself.

#### To a restore point

Stops exactly at a Mark created with `rowsafe mark` (a PostgreSQL restore point), then promotes:

```sh
sudo -u postgres pgbackrest --stanza=app --archive-mode=off \
  --set=20260921-010002F \
  --type=name --target=before-migration-42 --target-action=promote restore
```

<Callout type="warn" title="Always pass --set for a Mark">
  With `--type=name`, pgBackRest can't tell which backup comes before the Mark, so it takes the newest one. If that backup finished after the Mark, recovery never reaches it and PostgreSQL refuses to start ("recovery ended before configured recovery target was reached"). Pass the **RESTORE FROM BACKUP** label from `rowsafe marks`, or any older backup.
</Callout>

Recovery stops just after the Mark: everything committed before it is there, nothing after it.

`--archive-mode=off` writes `archive_mode = 'off'` into the restored `postgresql.auto.conf`, so this cluster can't push WAL into the production repository. The file also carries production's other `ALTER SYSTEM` settings, including Rowsafe's `archive_command`, which does nothing while archiving is off.

</Step>
<Step>

### Start and check

```sh
sudo systemctl start postgresql@18-main
sudo tail -f /var/log/postgresql/postgresql-18-main.log    # "ready to accept connections"
sudo -u postgres psql -Xc "select pg_is_in_recovery()"     # f
```

Check the data around the target: the newest rows in a busy table, and whether the rows from the bad change are gone or present as intended. Then run your application's smoke tests against this server.

</Step>
</Steps>

### Afterwards

<Tabs items={["This server becomes production", "It was a scratch restore"]}>
<Tab value="This server becomes production">

1. **Fence the old primary** so it can never come back and write: stop and disable its PostgreSQL, or shut the server down.
2. Carry over what the restore doesn't include: `pg_hba.conf`, your files in `conf.d/`, TLS certificates and keys, and any systemd drop-ins. Restart PostgreSQL once they are in place.
3. Point your application at the new server and redeploy it.
4. **Protect it again**: run the install command on the new server, and when it asks for a name, give a **new one**, for example `app-2`. The new name gives it a fresh path in the bucket. Leave the old `app` path alone until you no longer need its backups.

</Tab>
<Tab value="It was a scratch restore">

Copy out what you need, for example `pg_dump --table=...` of the affected tables, and load it into production inside a transaction. Then delete the scratch cluster, and revoke the read-only bucket token if you created one.

</Tab>
</Tabs>

### From Docker backups

In the dashboard, restoring a copy and bringing back rows work in Docker as on a server. Rewinding the whole database needs the [container control service](/docs/guides/docker#let-rowsafe-restart-the-container).

The backups of a database that runs in Docker are ordinary pgBackRest backups. Restore them the same way, on a Linux server with the same PostgreSQL major version, using the bucket settings from your `rowsafe-agent.env`.
