---
title: "Recommendations: make your database better"
description: Pulse recommendations look at your schema, your queries and your server's capacity, and tell you what to change, why, and what it costs. Rowsafe applies the safe ones for you.
---

Health tells you what is wrong now. **Recommendations** tell you what will bite later and what would make the database faster or cheaper to run: an id column about to run out of numbers, a foreign key without an index, a query that runs once per row of another, a busy table autovacuum can't keep up with.

Each recommendation says **what** to change, **why** (with the numbers behind it), and **what it costs**: disk, time, a lock, or an app change. When a safe automatic fix exists, it has an **Apply fix** button. When it doesn't (changing a key's type, adding a primary key), it has a step-by-step plan.

Recommendations don't change the health score. They are in every plan, including Free.

## See them

In the dashboard: open a database, then **Pulse**, **Recommendations**. They are grouped into **Schema**, **Queries**, **Capacity** and **Indexes**, most important first.

From a terminal:

```sh
rowsafe recommendations            # every database's top recommendation
rowsafe recommendations app        # all of them, with why and what it costs
rowsafe recommendations app --group queries
```

The Monday email, [Your weekly Pulse](/docs/guides/monitoring#your-weekly-pulse), names each database's top recommendation.

## Apply a fix

Click the button on the recommendation (for example **Create the index**), read what will happen, and confirm. The page shows each step and the result, for example "Created the index orders_customer_id_idx on public.orders (1.3 GB) in 41s", and the recommendation goes away.

From a terminal, `rowsafe fix` lists these fixes together with the health fixes:

```sh
rowsafe fix app                    # numbered list, asks which one
rowsafe fix app fk_without_index:app.public.orders.orders_customer_id_fkey
```

The same safety rules as every [Apply fix](/docs/guides/monitoring#what-keeps-it-safe) hold: only fixes Rowsafe proposed run, with its own parameters; the agent checks the conditions again right before it acts; one fix runs at a time per database; owners and admins only; everything is in the audit log; AI agents can read recommendations but never apply them.

| Recommendation | Button | What Rowsafe does |
|---|---|---|
| A foreign key without an index | **Create the index** | `CREATE INDEX CONCURRENTLY` on the referencing columns. Skipped if an index on them appeared meanwhile; a failed build is cleaned up. Reads and writes keep working. |
| A sequence behind its column (inserts fail with "duplicate key") | **Move the sequence forward** | `setval` to the highest value in the column, only if it is still behind. |
| An invalid index left by a failed concurrent build | **Remove the invalid index** | `DROP INDEX CONCURRENTLY`, only if it is still invalid and no index is being built on the table. |
| Autovacuum waits too long on a large, busy table | **Tune autovacuum** | `ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0, autovacuum_vacuum_threshold = N, ...)`: cleanup after a fixed number of changed rows. Only autovacuum settings, only numbers. The task log shows how to undo it. |

## Not relevant?

Click **Not relevant**, pick a reason (not relevant for this database, on purpose, later, or wrong) and add a note for your team if you like. The recommendation moves to **Dismissed** at the bottom of the page for everyone in your organization, with who dismissed it and why. **Bring back** undoes it. From a terminal:

```sh
rowsafe recommendations app --dismiss no_primary_key:app.public.event_log --reason intended --note "append-only log"
rowsafe recommendations app --restore no_primary_key:app.public.event_log
```

## What Rowsafe looks at

About every 30 minutes, with the table and index insights, the agent reads a few more catalog facts in each database: read-only queries with a 5-second timeout, bounded in size, never your rows. It also uses the last day of query statistics (`pg_stat_statements`) and the last week of metrics.

### Schema

| Recommendation | When |
|---|---|
| **An id column will run out of numbers** | A `smallint`/`integer` column filled from a sequence (serial or identity), or an integer column pointing at one, is 50% used (warning) or 80% (critical), or will run out within 90 days at the current pace. Rowsafe measures the pace from readings over hours and days, and gives the date. The plan: widen it to `bigint` without downtime (a copy column, batches, a quick swap), or with one `ALTER` in a maintenance window, with an estimate of how long that blocks the table. A sequence that stops at the integer maximum while its column is already `bigint` needs only `ALTER SEQUENCE ... AS bigint`. |
| **A sequence is behind its column** | The next value the sequence hands out already exists in the column, usually after rows were copied in with their ids. |
| **A foreign key without an index** | The referencing columns don't lead any index, on a table of at least 10,000 rows. Deletes on the referenced table then read the whole referencing table. |
| **A broken index from a failed build** | An index PostgreSQL marked invalid (a failed `CREATE INDEX CONCURRENTLY`), not being built now. |
| **A table without a primary key** | No primary key and no unique column that can't be empty. Logical replication, online migrations and bringing back rows with Rewind need one. |
| **Duplicate constraints** | The same unique rule, foreign key or check twice, or a unique rule another one already implies. |
| **Times without a time zone** | Columns of type `timestamp without time zone` in tables that get writes. |
| **A large table to partition by time** | Over 10 GB, insert-only, with a time column. |

### Queries

These need `pg_stat_statements` (see [Slow queries](/docs/guides/monitoring#slow-queries)).

| Recommendation | When |
|---|---|
| **N+1 queries** | A cheap query returning one row runs at least once a second, and its calls rise and fall with another query's (a list, then one query per item). |
| **Reads far more than it returns** | A query reads at least 100 pages per row it returns and 8 MB per call, and takes at least 1% of all query time. Links to the index suggestions. |
| **Returns huge results** | A query returns over 10,000 rows per call, without `LIMIT`. |
| **Sorts on disk** | A query writes over 10 MB of temporary files per call, or 1 GB a day. |

### Capacity

| Recommendation | When |
|---|---|
| **Busiest data no longer fits in memory** | Over the last week, under 95% of reads came from memory for a large part of the time. With your database and memory sizes, and `shared_buffers`. |
| **CPUs often fully busy** | The load stayed above the number of CPUs for at least 12 hours and 10% of the week. |
| **Connections near the limit** | Connections reached 90% of `max_connections`, or 80% for several hours. |
| **The disk will be full** | The [disk forecast](/docs/guides/monitoring#disk-forecast) says within 90 days. |
| **Autovacuum waits too long** | A table of over a million rows had updates and deletes of at least 10% of its rows, with the default scale factor (20%). |

### Indexes

The unused, duplicate and missing index findings from the health score, with their fixes.

## Limits

- Estimates are estimates: index sizes, rewrite times and the date an id runs out come from sizes and rates, not measurements of your disks.
- Query recommendations only see the statements `pg_stat_statements` keeps (the busiest, in 5-minute steps).
- On a replica, recommendations that need write statistics (autovacuum, time-series, timestamps) are left out; fixes run on the primary.
- An agent older than the recommendations feature doesn't send the schema facts; update it to see them.
