Rowsafe is built so that the hosted service never needs your data or your secrets. The part that touches your data, the agent, is [open source](https://github.com/rowsafe/rowsafe) under Apache-2.0, so you can read exactly what runs on your servers.

## What runs on your server

- **The agent** (`rowsafe-agent`), as the `postgres` system user. It refuses to run as root.
- **pgBackRest**, which the agent and PostgreSQL's `archive_command` run.
- A systemd unit with `NoNewPrivileges`, a read-only system except its own directories, a private `/dev`, no capabilities and restricted address families. The kernel's out-of-memory killer picks the agent before production PostgreSQL, and it gets half the default CPU and IO weight.

The agent:

- connects to PostgreSQL **only over the local Unix socket**, as the `postgres` role (a superuser is needed for `ALTER SYSTEM` and backups);
- makes **only outbound HTTPS requests**, to `api.rowsafe.sh` and your bucket (or Rowsafe Storage). Nothing listens on your server;
- runs **only a fixed set of tasks**: inspect, adopt (plan or apply), check, backup, drill (Proof), restore point (Mark), restart (only on a server where you allowed it), and maintenance, a short list of fixes described below. It never runs commands or SQL sent over the network.

Proof, the weekly restore test, restores your data onto the same server, into a scratch cluster with no network listener, and deletes it afterwards.

**Fixes run only when a person asks.** Rowsafe can run a fixed set of maintenance actions: `VACUUM` and `ANALYZE` tables, `REINDEX INDEX CONCURRENTLY`, `DROP INDEX CONCURRENTLY`, cancel a query (`pg_cancel_backend`), end a session (`pg_terminate_backend`) and drop an inactive replication slot. It never runs them on its own: only when an owner or admin clicks **Apply fix** in the dashboard (or runs `rowsafe fix`) and confirms. The service proposes each fix from a health finding and the client can only pick one by its ID, never send SQL or object names. The agent checks again right before it runs: the object still exists, the session is still the same one and isn't a Rowsafe, replication or autovacuum session, the slot is still inactive, and an index that backs a constraint is never dropped. Before dropping an index, Rowsafe saves a Mark so you can restore to just before it. Read-only API keys and the MCP server (AI agents) can't apply fixes. See [Apply fix](/docs/guides/monitoring#apply-fix).

**Restarts are opt-in.** Rowsafe never restarts PostgreSQL on its own. It restarts only when someone clicks **Restart** in the dashboard (or runs `rowsafe restart`) and confirms, and only on servers where you allowed it during install. The installer asks; `--no-allow-restart` answers no. The installer itself can also restart PostgreSQL during setup, when you answer yes on the server. Only admins and owners can restart, never with a read-only API key or through MCP, and at most once every 2 minutes. In Docker, Rowsafe can restart PostgreSQL only if you add the optional container control service, which alone holds the Docker socket and acts on that one container; see its [threat model](/docs/guides/docker#threat-model).

## What Rowsafe can and can't do

Someone who controlled the Rowsafe service, or held one of your API keys, **could**:

- queue the fixed tasks for your databases: plans, backups, checks, Proof runs and Marks, and apply an adoption plan (which sets `archive_mode`, `archive_command`, `archive_timeout` and, if it is `minimal`, `wal_level`);
- restart PostgreSQL, a few seconds of downtime, but only on a server where you allowed restarts during install;
- run the maintenance actions above: vacuum or analyze tables (extra load while they run), rebuild or drop indexes (queries that used a dropped index get slower until you recreate it), cancel queries or end sessions (an open transaction is rolled back, so its uncommitted changes are lost), and drop an inactive replication slot (whatever read from it has to start over);
- read metadata: server and database names and sizes, table counts, PostgreSQL settings, task logs, metrics and long-running query text (unless you [turn it off](/docs/guides/monitoring#privacy));
- withhold agent updates, or offer a release that was properly signed but is known to be bad. Agents still self-test it, put it on probation and roll back;
- with [Rowsafe Storage](/docs/guides/rowsafe-storage) only: delete or withhold your backups, because Rowsafe runs that bucket. They still couldn't read them. If that matters to you, use your own bucket.

They **could not**:

- run arbitrary commands or SQL on your server;
- read your backups: they are encrypted with a passphrase that never leaves your server;
- with your own bucket, reach it at all: its keys never leave your server;
- make an agent run a binary that wasn't signed with Rowsafe's release key, or downgrade an agent;
- restart PostgreSQL on a server where you didn't allow it, or stop it;
- read, change or delete your rows, or drop a table: the maintenance actions never touch table data, and an index that backs a primary key, unique or exclusion constraint is never dropped;
- change settings other than the archiving settings above.

## Encryption

- Backups and WAL are compressed, then **encrypted on your server** with `aes-256-cbc`, using your passphrase, before they are uploaded. Your bucket, or Rowsafe Storage, holds only ciphertext.
- The passphrase and the bucket keys live **only on your server**, in `/etc/rowsafe/agent.env` and the generated pgBackRest configuration, both mode 0600 and owned by `postgres`. Anyone who can become `postgres` can already read the database itself.
- Rowsafe can't recover a lost passphrase. Keep it in your secret manager.
- All traffic between the agent, the CLI and Rowsafe uses HTTPS.

## Credentials

| Credential | Prefix | Held by | Allows |
|---|---|---|---|
| API key | `rsk_` | You: CLI, scripts, CI, AI agents | The Rowsafe API for one organization. Read-only keys can only read. |
| Enrollment token | `rse_` | The installer, once | Enrolling one host. Single use, 1 hour by default. |
| Agent token | `rsa_` | `/var/lib/rowsafe/agent.json` (0600) | The agent API for one host: its own tasks and heartbeats. |
| Bucket keys | | `agent.env` and pgBackRest configuration, on your server | Your bucket. |
| Rowsafe Storage credentials | | `/var/lib/rowsafe/storage-credentials.json` and pgBackRest configuration (0600), on your server | Your organization's space in Rowsafe Storage only, for 7 days; renewed daily. |
| Encryption passphrase | | The same files, and your secret manager | Decrypting every backup. |

Rowsafe stores only SHA-256 hashes of API keys, enrollment tokens and agent tokens.

## Signed releases

The installer and the agent only install releases signed with Rowsafe's Ed25519 release key, which is built into them and never stored on the Rowsafe service. Every release also has build provenance, an SBOM and reproducible builds that you can check yourself: see [Verifying releases](/docs/security/verifying-releases).

## Webhooks

Webhook notifications are signed with a per-channel secret ([verify them](/docs/reference/webhooks#verify-the-signature)). Rowsafe only sends them to public `https` URLs, checks every address after DNS resolution, and never follows redirects.
