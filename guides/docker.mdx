---
title: Run the agent in Docker
description: Protect PostgreSQL running in the official postgres image, with the Rowsafe agent as a sidecar container. No changes to your image.
---

If PostgreSQL runs in the official `postgres:NN` image (Debian or Alpine), you don't install anything on the Docker host. The agent runs as a **sidecar container** in the same compose project. You add a few volume mounts and one service. Then you add the database from the dashboard or the CLI: plan, apply, and restart the container yourself. Rowsafe notices the restart. If you want Rowsafe to restart the container for you, and to rewind the whole database with one click, add one more small service: see [Let Rowsafe restart the container](#let-rowsafe-restart-the-container).

<Callout title="Linux Docker hosts only for production">
  Docker Desktop on macOS or Windows runs containers in a VM whose disk and `fsync` behaviour Rowsafe doesn't guarantee. Use it to try Rowsafe, not for data you need to recover. Kubernetes isn't covered.
</Callout>

## How it works

```text
 compose project
 +-------------------------------+        +------------------------------------------+
 | postgres (postgres:17, stock) |        | rowsafe-agent (ghcr.io/rowsafe/agent:    |
 |                               |        |                <version>-pg17)           |
 |  archive_command:             |        |                                          |
 |   cp + fsync + rename --------+--+     |  spool pusher: pgbackrest archive-push   |
 |                               |  |     |    each file in order, delete after OK --+--> your bucket
 |  /var/lib/postgresql/data  <--+--+-----+-- same volume, same path, read-only      |    (encrypted)
 |  /var/run/postgresql       <--+--+-----+-- socket: SQL                            |
 |  /rowsafe-spool/<db>/      <--+--+-----+-- spool: WAL waiting to be pushed        |
 +-------------------------------+        +------------------------------------------+
```

- The stock `postgres` image has no pgBackRest. So `archive_command` only **copies** each WAL file into a shared **spool** volume, with standard tools (`cp`, `sync`, `mv`), and never overwrites a different file.
- The agent **pushes** spooled files to your bucket with pgBackRest, in order, and deletes each one only after it is stored.
- Backups, checks, Marks and Proof (the weekly restore test) run in the agent container. It reads the data volume **read-only**, at the same path.
- Nothing runs inside the PostgreSQL container except `archive_command`. Rowsafe never restarts it, unless you [let it](#let-rowsafe-restart-the-container) and someone clicks Restart.

<Callout type="warn" title="The spool must be on durable disk">
  PostgreSQL treats a WAL file as archived once it is in the spool. Until the agent has pushed it, the spool holds the only copy. Use a named volume on local disk, never `tmpfs` or a network filesystem that ignores `fsync`. Don't delete spooled files by hand.
</Callout>

## Set up

You need a one-time enrollment token (`rowsafe hosts enroll-token`), a bucket and its keys, and an encryption passphrase **stored in your secret manager first**. See steps 2 and 3 of [Adopt an existing database](/docs/guides/adopt).

Put the agent's settings in `rowsafe-agent.env` next to your compose file. Make it readable only by you (`chmod 600`) and never commit it:

```sh title="rowsafe-agent.env"
ROWSAFE_ENROLL_TOKEN=rse_...        # first start only; delete it afterwards
ROWSAFE_REPO_S3_ENDPOINT=<account-id>.eu.r2.cloudflarestorage.com
ROWSAFE_REPO_S3_BUCKET=app-rowsafe
ROWSAFE_REPO_S3_KEY=...
ROWSAFE_REPO_S3_KEY_SECRET=...
ROWSAFE_REPO_CIPHER_PASS=...
# ROWSAFE_PG_USER=app               # if POSTGRES_USER is not postgres
```

Then add the agent to your compose file. Your `postgres` service keeps its image, environment, networks and ports.

<Tabs items={["PostgreSQL 14 to 17", "PostgreSQL 18", "Alpine images"]}>
<Tab value="PostgreSQL 14 to 17">

```yaml title="compose.yml"
services:
  postgres:
    image: postgres:17
    volumes:
      - pgdata:/var/lib/postgresql/data
      - pgsocket:/var/run/postgresql        # added
      - rowsafe-spool:/rowsafe-spool        # added

  rowsafe-agent:
    image: ghcr.io/rowsafe/agent:<version>-pg17
    hostname: db-1                          # the host name Rowsafe shows
    user: "999:999"                         # the postgres user of the Debian images
    restart: unless-stopped
    depends_on: [postgres]
    env_file: rowsafe-agent.env
    shm_size: 256m                          # Proof starts a scratch PostgreSQL here
    volumes:
      - pgdata:/var/lib/postgresql/data:ro  # same volume, same path, read-only
      - pgsocket:/var/run/postgresql
      - rowsafe-spool:/rowsafe-spool
      - rowsafe-state:/var/lib/rowsafe

volumes:
  pgdata:
  pgsocket:
  rowsafe-spool:
  rowsafe-state:
```

</Tab>

Pick the agent image's `<version>` from the [releases](https://github.com/rowsafe/rowsafe/releases). Its PostgreSQL major must match your server's.

Start it:

```sh
docker compose up -d
docker compose logs rowsafe-agent      # "enrolled"
rowsafe hosts list                     # db-1
```

Adding the two mounts recreates the `postgres` container: a few seconds of downtime, so do it in a maintenance window. With a bind mount instead of a named volume, mount the same host directory in both services at the same path.

Keep the `rowsafe-state` volume: it holds the host's identity and the generated pgBackRest configuration. If you lose it, enroll again with a new token.

## Adopt

The one-command installer is for servers. In Docker, add the database in the dashboard (**Databases**, then **Add database**) or with the CLI:

```sh
rowsafe adopt app --host db-1        # read-only plan
rowsafe apply app                    # config, spool directory, ALTER SYSTEM + reload
docker compose restart postgres      # you, in a maintenance window
```

Rowsafe notices the restart by itself and proves that WAL reaches the bucket, through the spool. To check right away, click **Check now** on the database's page or run `rowsafe verify app`.

The settings are written with `ALTER SYSTEM` into `postgresql.auto.conf` in the data volume, so they survive container restarts and re-creation.

## Let Rowsafe restart the container

Optional. By default Rowsafe can't touch the PostgreSQL container: you restart it yourself when setup asks, and Rewind the whole database is not offered (restoring a copy and bringing back rows works either way). Add the `rowsafe-docker-control` service and, from the dashboard:

- **Restart PostgreSQL** restarts the container, waits until it runs (healthy, if it has a health check) and PostgreSQL answers.
- **Rewind the whole database** stops the container, puts the data back as it was at the moment you pick, and starts it again. The data from before is kept for 7 days, so **Undo** is one click too.

The agent never gets the Docker socket. The control service does, and it acts on exactly one container: your PostgreSQL service in the same compose project. See [Threat model](#threat-model) before you add it.

The database's **Settings** page in the dashboard shows these lines with your service and volume names filled in, and updates by itself once the agent reports the service.

<Steps>
<Step>

Add the service (use the same `<version>` as the agent image):

```yaml title="compose.yml"
services:
  rowsafe-docker-control:
    image: ghcr.io/rowsafe/docker-control:<version>
    restart: unless-stopped
    depends_on: [postgres]
    environment:
      ROWSAFE_CONTROL_SERVICE: postgres     # your PostgreSQL service's name
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
      - rowsafe-control:/run/rowsafe-control
    network_mode: none
    read_only: true
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
```

</Step>
<Step>

Give the agent the control volume and, for Rewind the whole database, write access to the data volume (remove `:ro`):

```yaml title="compose.yml"
  rowsafe-agent:
    volumes:
      - pgdata:/var/lib/postgresql/data     # was :ro. PostgreSQL 18+: pgdata:/var/lib/postgresql
      - rowsafe-control:/run/rowsafe-control
      # ... the other volumes as before

volumes:
  rowsafe-control:
```

Keep `:ro` if you only want Restart: the dashboard then shows Rewind the whole database as not allowed and says why.

</Step>
<Step>

Apply it. This recreates the agent container; PostgreSQL keeps running.

```sh
docker compose up -d
docker compose logs rowsafe-docker-control   # "controlling container" myapp-postgres-1
```

</Step>
</Steps>

To take the permission back, remove the service (and the `rowsafe-control` volume). Nothing else changes.

### How a rewind works in Docker

In Docker the data directory can't be renamed: up to PostgreSQL 17 it is the volume itself, and in the 18+ images its parent belongs to root. So the agent moves what is **inside** it, one rename per entry, within the same volume:

1. Rowsafe saves a Mark; the agent checks the backup repository, the free space in the volume and that the data directory is writable;
2. asks the control service to stop the container (PostgreSQL shuts down cleanly);
3. moves the data into `.rowsafe-rewind/<name>.before-rewind-<time>/` inside the data directory;
4. restores the backup into `.rowsafe-rewind/restore-<id>/`, moves it into place and keeps your configuration (`postgresql.conf`, `pg_hba.conf`, archive settings);
5. replays changes up to the moment you picked, in the agent container on a private socket, with no network access;
6. asks the control service to start the container, and waits until PostgreSQL accepts connections.

If any step fails, the agent puts the original data back and starts the container again; if the agent itself stops half way, it does so when it starts. The data directory keeps its owner and permissions. While it is empty, the image's entrypoint can't create a new cluster there, because `.rowsafe-rewind` is in the way. Backups leave `.rowsafe-rewind` out.

It needs free space in the data volume for a second copy of the database (its size plus 10%) until you delete the kept data (**Delete the old data now**) or it expires.

### Threat model

Whoever can talk to the Docker socket controls the host: they can start a privileged container that mounts `/`. Mounting the socket read-only (`:ro`) changes nothing; requests still go through. That is why the agent never gets it, and why this is opt-in.

**What the control service allows.** It exposes a Unix socket on the `rowsafe-control` volume, which only the agent mounts. A request has two fields, an action and an ID for the log; anything else is refused. The actions are `inspect`, `stop`, `start` and `restart`. The container is fixed by the service's own configuration: the compose service named in `ROWSAFE_CONTROL_SERVICE` in the control service's own compose project (or one container named in `ROWSAFE_CONTROL_CONTAINER`). It is resolved to a container ID at start and its labels are checked again before every action; it can never be the control service itself, and a service scaled to two containers is refused. The only Docker API calls in its code are listing containers by label, inspecting one, and stop, start and restart. It can't exec, create, remove, pull, read logs or touch networks, volumes or images.

**Who may ask.** Only processes running as uid 999 or 70 (the `postgres` user of the Debian and Alpine images; `ROWSAFE_CONTROL_ALLOW_UIDS` changes it), checked with the kernel's peer credentials, not anything the caller says. Requests must be small and arrive within 10 seconds.

**Limits and log.** At most one restart a minute, and 20 stops and restarts an hour; starting is never limited, so a rollback can always start PostgreSQL again. Every request is logged with the caller's uid, the action, the container and the outcome: `docker compose logs rowsafe-docker-control`.

**Who triggers it.** Only a person, in the dashboard or with `rowsafe restart`, as an owner or admin, with a read-write API key; never an AI assistant through MCP. Every request is in the audit log.

**If the agent container is compromised,** the attacker can stop, start or restart your PostgreSQL container (a few rate-limited outages), which is less than what the agent's access to the database already allows. They can't reach any other container or the host.

**If the control service is compromised,** the attacker has the Docker socket, that is, root on the host. The service is built to make that hard: one static Go binary, under a thousand lines with its comments, on an empty image (no shell, no package manager), no network at all (`network_mode: none`), no Linux capabilities, a read-only filesystem, `no-new-privileges`. The image is signed with cosign and has SLSA build provenance; see [Verifying releases](/docs/security/verifying-releases). It runs as root inside its container only to open the socket, which root owns.

**Why not a Docker socket proxy?** Generic proxies such as `tecnativa/docker-socket-proxy` filter by API section ("containers", "POST"), not by container: allowing restarts would let the agent stop, start, create or remove any container on the host.

If that trade isn't right for your host, don't add the service: restart the container yourself when Rowsafe asks, and restore copies instead of rewinding in place.

## Upgrade

The agent never updates itself in Docker. To upgrade, change the tag and recreate the container, ideally between backups:

```sh
docker compose up -d rowsafe-agent
```

If a backup or Proof run is interrupted, the new container reports it as failed and the schedule runs it again. WAL waiting in the spool is pushed by the new container.

Rowsafe doesn't do PostgreSQL **major** upgrades. After one, switch to the agent tag for the new major and adopt the database again, so its repository starts a new history.

## Watch the spool

The agent reports the spool with every heartbeat. In Docker, the WAL status that `rowsafe show app` prints describes your **bucket**, not the spool: "last archived" is the last file pushed to the bucket, and failed pushes count as archiving failures. If the oldest spooled file waits longer than 5 minutes (`ROWSAFE_SPOOL_STALL_AFTER`), that counts as a failure too: you get the `wal_archiving_failing` alert and the database stops counting as protected. The API (`GET /v1/databases/{ref}`) also has the spool's file count, size and last push error.

The image's health check fails when a spool is stalled, so `docker ps` shows the container as `unhealthy`.

## Troubleshooting

The agent checks its environment at startup and names the fix:

| Message | Fix |
|---|---|
| `refusing to run as root` | Set `user: "999:999"` (or `"70:70"` for Alpine images). |
| `PostgreSQL's socket directory /var/run/postgresql is owned by uid 70, but the agent runs as uid 999` | Alpine image: use the agent's `-alpine` tag and `user: "70:70"`. |
| `the agent runs as uid N, which has no user in this image` | Use the agent tag that matches your postgres image flavour. |
| `the WAL spool /rowsafe-spool is missing` | Mount the spool volume in both services. |
| `the WAL spool ... is owned by uid 0` | Another container created the volume first. Recreate it while empty, or `chown 999:999` it. |
| `PostgreSQL's data directory ... is not visible in the agent container` | Mount the data volume at the same path in both services (for 18+, at `/var/lib/postgresql`). |
| `... belongs to another cluster (system identifier ...)` | The agent sees a different volume at that path. |
| `this agent image has no PostgreSQL N server binaries` | Use the `-pgN` tag for your server's major version. |
| `Rowsafe can't restart PostgreSQL running in Docker yet` | Add the container control service ([Let Rowsafe restart the container](#let-rowsafe-restart-the-container)), or restart the container yourself. |
| `found no container for the compose service "postgres"` | Set `ROWSAFE_CONTROL_SERVICE` to your PostgreSQL service's name, then `docker compose up -d`. |
| `the PostgreSQL data volume is mounted read-only in the agent container` | Remove `:ro` from the agent's data volume to allow Rewind the whole database. |
| `uid N may not use this service` | The agent runs as another user: set `ROWSAFE_CONTROL_ALLOW_UIDS` on the control service. |

If WAL piles up in the spool, `docker compose logs rowsafe-agent` shows the pgBackRest error. The spool drains by itself once the cause is fixed.

<Accordions>
<Accordion title="Other settings">

- **`POSTGRES_USER` other than `postgres`:** set `ROWSAFE_PG_USER` to that role. The agent must connect as a superuser over the socket.
- **Locales:** the agent image includes `C.UTF-8` and `en_US.UTF-8`. A database created with another locale can't be opened by Proof.
- **Several PostgreSQL containers:** give each one its own agent (and its own control service, if you use one).
- **Rewind the whole database in Docker, limits:** not with tablespaces or on a replica (as on a server); the agent image replays changes with PostgreSQL's standard extensions, so a `shared_preload_libraries` entry the agent image lacks makes the rewind fail and roll back (restore a copy instead); with `restart: always`, a Docker daemon restart in the middle may start the container early, which then fails to start (the data directory holds only `.rowsafe-rewind`) until the rewind finishes or rolls back.
- **Throughput:** the pusher sends one WAL segment at a time, typically tens of MB/s. A database that writes WAL faster for long periods builds a backlog, and the stall alert tells you.
- **Other images** work if they have `sh`, `test`, `cmp`, `cp`, `sync` and `mv`, a `postgres` user the agent can match, and a data directory mounted at the same path.
- Image defaults: see [Agent configuration](/docs/reference/agent-configuration#docker).
