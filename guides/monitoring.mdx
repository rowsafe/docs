**Pulse** watches your databases, with no monitoring stack of your own. The agent collects database and server metrics every minute, and Rowsafe turns them into a **health score**, plain-language findings, graphs, alerts, slow-query insights and a weekly email, "Your weekly Pulse". Most problems it finds, it can also fix: click **Apply fix** and confirm.

Pulse starts as soon as you add a database, before backups are switched on. It is included in every plan, including Free.

## What the agent collects

Every 60 seconds the agent opens one short session (`rowsafe-agent-monitor`) over the Unix socket and runs a few cheap catalog queries. Each query has a 2-second timeout, so on a struggling server you get a gap in the graphs, never a pile-up of monitoring queries. Monitoring never blocks a backup, a Proof run or a Mark.

### Privacy

- `pg_stat_statements` text is normalized by PostgreSQL: literal values become `$1`, `$2`.
- **Activity query text is not normalized**: it is the statement as the client sent it, which can include personal data. Set `ROWSAFE_COLLECT_QUERY_TEXT=false` in `/etc/rowsafe/agent.env` to send activity without query text.
- A statement that looks like it carries a password (`CREATE ROLE ... PASSWORD`, `password=` in a connection string, and similar) is redacted on your server before it is sent.
- `ROWSAFE_MONITORING=false` turns monitoring off. The agent then sends only heartbeats and task results.

### Retention

| Resolution | Kept for |
|---|---|
| 1 minute | 48 hours |
| 5 minutes | 14 days |
| 1 hour | 90 days |

Resolved alerts are kept 90 days, and sent notifications 30 days.

## Health score

Every database gets a score from **0 to 100** and a short list of findings, worst first. Each finding says what's wrong in plain language, why it matters and what to do, and, when Rowsafe can do it for you, has a button that does it (see [Apply fix](#apply-fix)).

| Score | Meaning |
|---|---|
| 90-100 | Healthy |
| 70-89 | Needs attention |
| 50-69 | At risk |
| Under 50 | Critical |

The score starts at 100 and loses points for each problem: backups and Proof (restore tests), whether PostgreSQL answers, disk space, connections, vacuum and transaction ID wraparound, locks and slow queries, replication. **One critical problem caps the score at 59, and a warning at 89**, so a serious problem is never hidden by an otherwise good score. Missing data means fewer findings, never a false alarm.

```sh
rowsafe pulse          # every database, worst first
rowsafe pulse app      # one database: score, findings, and what's fine
```

`rowsafe pulse` exits with code 3 when a database scores below 70, so you can use it in scripts. The score is recorded every 15 minutes, so the dashboard and the weekly email show how it changes.

## Apply fix

Most findings come with a button that fixes them: on the database's **Pulse** tab, under **Health**, and next to the same problem on **Insights**, **Monitoring**, **Queries** and **Alerts**. Click it, confirm if Rowsafe asks, and Rowsafe does the work on your server through the agent. The page shows each step (waiting for the agent, running, done) and what happened, for example "Cleaned up 3 tables; about 1.2 million dead rows removed." Then the finding goes away and the score goes up.

What Rowsafe can fix:

| Problem | Button | What Rowsafe does |
|---|---|---|
| No backup yet, or the last one is too old | **Back up now** | Starts a full backup. |
| The latest Proof failed, or none passed this week | **Run Proof now** | Runs a restore test. |
| Backups can't reach your storage | **Check again** | Tests that changes reach your bucket, once you've fixed what the check reported. |
| Backups aren't on yet | **Turn on backups** | Applies the setup plan (after you confirm). |
| PostgreSQL is waiting for a restart | **Restart PostgreSQL now** | Restarts it, on servers where you allowed restarts during install. |
| Dead rows piling up, vacuum behind, transaction ID wraparound | **Clean up** | `VACUUM (ANALYZE)` on those tables, with `FREEZE` for wraparound. |
| A query got slower | **Refresh statistics** | `ANALYZE` on the tables it reads, so PostgreSQL can pick a better plan. |
| An index with a lot of wasted space | **Rebuild index** | `REINDEX INDEX CONCURRENTLY` (PostgreSQL 12 and later). |
| An unused or duplicate index | **Remove** | `DROP INDEX CONCURRENTLY`, after saving a Mark. |
| A session idle in a transaction, a transaction open too long, a session blocking others | **End this session**, or cancel its query | `pg_terminate_backend`, or `pg_cancel_backend` for a running query. |
| An inactive replication slot holding back WAL | **Remove the slot** | `pg_drop_replication_slot`. |
| The disk is filling up | The fixes above that free space | Removing an inactive slot or unused indexes, cleaning up tables. |

Some things Rowsafe doesn't do for you, and the finding says so in plain words: an **offline agent** (Rowsafe can't reach that server until someone restarts the agent there), **storage keys** (they never leave your server), **adding an index** (which column to index is your call), a **full table rebuild** to give space back to the disk (`VACUUM FULL` or `pg_repack` belong in a quiet hour), connection pooling and replication lag. Where a command helps, it's under **Do it yourself**, folded away.

### What keeps it safe

- **Only fixes Rowsafe proposes.** The dashboard and the CLI only name a finding and one of its fixes. Rowsafe checks the database's health again and runs that exact fix, with its own parameters. Nothing sends SQL, and there is no way to run your own. If the problem is gone by then, you're told the fix no longer applies.
- **A short, fixed list of actions**, checked again on your server right before they run: the table or index still exists, an "unused" index still hasn't been used, the session is still the same one (process ID and start time) and isn't a Rowsafe, replication or autovacuum session, the slot is still inactive. An index that backs a primary key, unique or exclusion constraint is never removed.
- **Owners and admins only.** Members see the buttons, disabled. API keys need write access: read-only keys can't apply fixes. Every fix is in the audit log, for example "applied a fix to app: Remove orders_legacy_idx".
- **You confirm what disrupts.** Ending a session, removing an index or a slot, and restarting PostgreSQL show what will happen first. Ending a session and removing an index or a slot ask you to type the database name.
- **A Mark first.** Before removing an index, Rowsafe saves a Mark (a restore point named `before-fix-...`), so you can [restore to just before it](/docs/guides/restore).
- **Gentle on the server.** Changes to indexes wait at most 5 seconds for a lock and then give up rather than queue behind your traffic. Indexes are rebuilt and removed `CONCURRENTLY`, so reads and writes carry on. Vacuum runs with a small cost delay. One fix runs at a time per database.
- **AI agents can't.** The [MCP server](/docs/reference/mcp) has no tool for fixes: a person clicks, or runs `rowsafe fix`.

From a terminal, `rowsafe fix` lists the same fixes and applies one:

```sh
rowsafe fix app                                        # what Rowsafe can fix, numbered; asks which one
rowsafe fix app 2                                      # apply fix number 2 from that list
rowsafe fix app unused_indexes drop:public.orders_legacy_idx
```

It asks you to confirm like the dashboard does; `--yes` skips the questions (for fixes that ask for the database name, too).

## Disk forecast

Rowsafe fits a trend through the last 14 days of disk use and tells you **when the disk will be full**, for example "in about 9 days". It ignores one-off spikes, such as a big file written and deleted. You need about 2 days of history before the first forecast. The `disk_full_forecast` alert warns you 14 days ahead.

## Table and index insights

About every 30 minutes, the agent looks at each database's tables and indexes (catalog statistics only, never your rows):

- the **largest tables and indexes**, and how fast they grow;
- **unused indexes** that cost disk and slow down writes, and **duplicate indexes**;
- **estimated wasted space** (bloat) in tables and indexes;
- tables with many **dead rows** that vacuum hasn't cleaned up;
- tables read by **full scans** that may need an index;
- **transaction ID age** per database and table.

Next to each suggestion Rowsafe can act on, a button does it: **Remove** an unused or duplicate index, **Rebuild index**, **Clean up** a table. See [Apply fix](#apply-fix).

```sh
rowsafe insights app
```

## Slow queries

With `pg_stat_statements` turned on, Rowsafe keeps 14 days of per-query timing in 5-minute steps. It shows the queries that took the most time in any range, their share of all query time, and **which got slower**: a query whose average time more than doubled against the previous period is flagged.

```sh
rowsafe top app                   # last 24 hours
rowsafe top app --since 168h --sort calls   # last 7 days, by number of calls
```

To turn on `pg_stat_statements`, add it to `shared_preload_libraries` (a restart, which you do), then run `CREATE EXTENSION pg_stat_statements;` in any database.

## Uptime

Each minute the agent reports whether it could query PostgreSQL. Rowsafe shows uptime over 24 hours, 7 days and 30 days, and each outage with its start and length. Minutes when the agent itself was offline aren't counted either way; the `agent_offline` alert covers those.

## Your weekly Pulse

Every Monday morning, "Your weekly Pulse" arrives by email: each database's health score and how it changed, the week's backups and Proof results, size and growth, the disk forecast, the top things to fix, the slowest queries, and any open alerts.

It's on for new organizations. It goes to the addresses you choose, or else to your email alert channels. Every email has a one-click unsubscribe link.

```sh
rowsafe report                    # settings
rowsafe report --preview          # this week's report, as text
rowsafe report --to you@example.com,team@example.com
rowsafe report --send-test        # send it now
rowsafe report --off
```

You can change the same settings in the dashboard under **Settings**, then **Weekly Pulse email**.

## Alert rules

Rowsafe checks every rule every 30 seconds. A condition must hold for the rule's **for** duration before the alert fires.

| Rule | Severity | Default threshold | For | Fires when |
|---|---|---|---|---|
| `backup_stale` | critical | 26 hours | 15m | No successful backup in the threshold, or an active database was never backed up after 12 hours. |
| `full_backup_stale` | warning | 8 days | 15m | No successful full backup in the threshold. |
| `drill_failed` | warning | | | The latest Proof (restore test) failed. |
| `drill_overdue` | warning | 8 days | 15m | No Proof passed in the threshold. |
| `wal_archiving_failing` | critical | | 10m | Archiving keeps failing. Point-in-time recovery stops at the last archived segment, and `pg_wal` grows. |
| `postgres_unreachable` | critical | | 5m | The agent is up but can't query PostgreSQL. |
| `agent_offline` | critical | 5 minutes | 1m | No heartbeat from the agent. |
| `restore_point_unconfirmed` | warning | | 15m | A Mark (restore point) was written but archiving hasn't moved past it. |
| `awaiting_restart` | warning | 24 hours | | A plan was applied, but PostgreSQL wasn't restarted. |
| `disk_free_low` | warning | 15% | 5m | Free disk on the data directory's filesystem below the threshold. |
| `disk_free_critical` | critical | 5% | 5m | Same, lower threshold. |
| `disk_full_forecast` | warning (critical under 3 days) | 14 days | 30m | At the growth rate of the last two weeks, the disk fills up within the threshold. |
| `connections_high` | warning | 80% | 5m | Connections above the share of `max_connections`. |
| `connections_critical` | critical | 95% | 2m | Same, higher threshold. |
| `long_transaction` | warning | 30 minutes | | A transaction has been open longer than the threshold. |
| `idle_in_transaction` | warning | 10 minutes | | A session sat idle in an open transaction longer than the threshold. |
| `xid_wraparound` | critical | 50% | | Transaction ID headroom below the threshold. |
| `replication_slot_inactive` | warning | 1 GiB | 15m | An inactive replication slot holds back more WAL than the threshold. |
| `blocked_queries` | warning | 60 seconds | 1m | A query has waited longer than the threshold for a lock held by another session. |
| `replication_lag` | warning | 5 minutes | 5m | A replica is further behind than the threshold. |
| `deadlocks` | warning | 5 | | More deadlocks than the threshold in 10 minutes. |
| `cache_hit_low` | info | 90% | 30m | Cache hit ratio below the threshold with real read traffic. |

Backup and archiving rules (`backup_stale`, `wal_archiving_failing`, `postgres_unreachable`, the Proof rules, `restore_point_unconfirmed`) wait until backups are switched on for the database, so a database you just added doesn't page you. Disk, connection, wraparound, lock and replication rules apply from the start.

**Critical** means recoverability or availability is degrading now. **Warning** needs attention within a working day. **Info** is for the record.

You can turn each rule off, or change its threshold, duration and severity, in the dashboard under **Alerts** (admins). `rowsafe alerts rules` lists the rules with your settings.

### How alerts behave

- There is at most one open alert per rule and target. When the condition clears, the alert **resolves** and you are notified.
- A **critical** alert that keeps firing is sent again every **4 hours** until someone acknowledges it. Acknowledging stops the reminders; you still hear when it resolves.
- **No data is not good news.** Without fresh metrics, an alert keeps its state. A silent agent raises `agent_offline` rather than resolving a disk alert.
- In the dashboard, an alert Rowsafe can fix has a **Fix it** button: it applies the fix, or opens the problem on the Health page when there's more than one way to fix it.

```sh
rowsafe alerts                # firing alerts (--all adds resolved ones, --resolved shows only those)
rowsafe alerts ack alr_...    # acknowledge: no more reminders
```

## Notification channels

Each channel has a **minimum severity** (default `warning`): it receives alerts of that severity and above. Every message says what is wrong, where, since when, the value and threshold, and links to the problem in the dashboard, where **Fix it** applies the fix when Rowsafe has one.

```sh
rowsafe channels add --type email --name oncall --address oncall@example.com --min-severity critical
rowsafe channels add --type slack --name team --url https://hooks.slack.com/services/T000/B000/XXXX
rowsafe channels add --type discord --name ops --url https://discord.com/api/webhooks/...
rowsafe channels add --type webhook --name pager --url https://hooks.example.com/rowsafe
rowsafe channels test chn_...
rowsafe channels list
rowsafe channels remove chn_...
```

| Type | Destination | Notes |
|---|---|---|
| `email` | Up to 20 addresses (repeat `--address`) | Plain text. |
| `slack` | A Slack [incoming webhook](https://api.slack.com/messaging/webhooks) | |
| `discord` | A Discord webhook | Mentions are off, so nobody is pinged. |
| `webhook` | Any public `https` URL | JSON, signed. The signing secret is printed **once**. See [Webhooks](/docs/reference/webhooks). |

- `channels test` sends a test notification right away, whatever the minimum severity.
- URLs are secrets: Rowsafe never shows them again in full.
- An organization can have up to 20 channels. You can also manage them in the dashboard under **Settings**, then **Notifications**.
