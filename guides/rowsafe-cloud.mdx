No cloud account, and no wish to open one? With **Rowsafe Cloud**, Rowsafe creates the server for you in **Rowsafe's own** DigitalOcean, AWS or OVHcloud account (you pick), installs PostgreSQL and protects it from the first minute: continuous backups you can restore to any second, a restore tested every week (Proof), Pulse watching its health, and Guard for your AI agents.

It's the same server as [Create a server for me](/docs/guides/create-a-server), with one difference: **Rowsafe holds the cloud account and bills you**, by the hour, with Rowsafe included.

<Callout title="What Rowsafe can and can't reach">
  Your server runs in Rowsafe's cloud account (DigitalOcean, AWS or OVHcloud, your pick). We don't log in to it, and backups are encrypted on the server with a passphrase only you have. Because we hold the cloud account, we could reach the server's disk; if you need that ruled out, [create the server in your own cloud account](/docs/guides/create-a-server) instead.
</Callout>

## How billing works

- **Add a card once.** The first Rowsafe Cloud server asks an owner for a card: one pay-as-you-go subscription for the whole organization, through Polar, our merchant of record (it handles sales tax and VAT). An admin can create the server, and an owner adds the card under **Settings → Billing**. After that, new servers are created right away.
- **Billed for every hour a server exists**, from when it's ready until you delete it, and never more than its monthly price in a month. Polar invoices the hours at the end of each month.
- **Change the size and the price follows** from the next full hour; a month never costs more than the monthly price of the biggest size the server had that month. See [Change the size](#change-the-size).
- **Delete a server and its billing stops.**
- **If a payment fails or you cancel**, nothing is deleted right away: you get emails first, your servers keep running for a grace period, and then they are powered off (powered-off hours aren't billed) before they are deleted, after a further notice. Your backups stay in Rowsafe Storage for as long as the database stays in Rowsafe.

### Copies for a test or an AI agent

[Clone to a new server](/docs/guides/fork#clone-to-a-new-server) copies a database (as it is now, at any second, or at a Mark) onto a new Rowsafe Cloud server in one click. It's billed by the hour like any Rowsafe Cloud server, and you can have Rowsafe delete it after **4 hours, 1 day or 7 days**, with an email an hour before. Three hours on the smallest OVHcloud size cost about $0.09.

## Create a Rowsafe Cloud server

1. In the dashboard, open **Servers**, click **Add server** and choose **Create a server for me**.
2. Under **Where should it run?**, choose **Rowsafe Cloud**.
3. Pick a region (the region decides the cloud), a size, a name and the PostgreSQL version.
4. Add the addresses that may connect, and your SSH key if you want to log in yourself.
5. Click **Create server**. The first time, an owner adds a card first.

The rest is the same as for a server in your own account: about 5 minutes, then [save the backup passphrase](/docs/guides/create-a-server#save-the-backup-passphrase) and [connect your app](/docs/guides/create-a-server#connect-your-app).

## Change the size

A Rowsafe Cloud server can move to another size of its cloud, bigger or smaller, in place: same server, same address, same database.

1. Open the server's page and click **Change size**.
2. Pick the new size. Each one shows its price per hour and the most a month costs.
3. Read what happens and click **Change size now**.

What to expect:

- **The database is offline for a few minutes** while the server restarts with the new size. Most apps reconnect by themselves. Rowsafe saves a [Mark](/docs/concepts/restore-points) first, so you can get back to that exact moment.
- **The disk can grow, never shrink.** Moving to a size with a bigger disk grows the disk, and that can't be undone: afterwards the server can't move back to a size with a smaller disk. Sizes with a smaller disk than the server has now can't be picked. (To go smaller anyway, create a smaller Rowsafe Cloud server and [move the database there](/docs/guides/move).)
- **Some bigger sizes aren't offered in every region.** The dashboard only lists the sizes offered where the server runs.
- **If the cloud can't make the change** (for example, it has no room for that size right now), the server comes back at its old size and the page says why. Nothing is billed at the new size.

How billing changes:

- **Every hour is billed at the size the server had when the hour started.** The hour you change the size in is billed at the old size; the new size is billed from the next full hour.
- **A month never costs more than the monthly price of the biggest size the server had that month.** Moving up from Small to Large mid-month: at most Large's monthly price. Moving down from Large to Small: that month still costs at most Large's price, and from the next month at most Small's.
- Settings → Billing shows the hours so far and the most this month can cost.

Owners and admins can change the size; every change is in the audit log. AI assistants can't. Servers paid by the month (not offered today) keep their size.

## With a standby

A standby is a **second server of the same size** that keeps a live, read-only copy of the database, a moment behind the primary. If the primary goes down, the standby takes over, and your apps reconnect to it on their own.

- **When you create a server**, turn on **With a standby**. **Fail over automatically** is ticked; untick it if you'd rather switch yourself.
- **On a server you already have**, open its page and click **Add a standby**. The price is shown before you confirm. Nothing on the primary restarts.

Rowsafe creates the second server right after the first one is ready, copies the database there from the latest backup, and keeps it in sync by streaming every change over an encrypted connection. The server's page shows the steps: **Creating the standby server**, **Installing PostgreSQL**, **Copying the database**, **Standby ready**. For a big database, copying takes longer.

### Where the standby runs

Rowsafe puts the standby somewhere else than the primary when the cloud has somewhere else in that region, and says plainly when it hasn't. The page shows where it is before you create it and once it runs.

| Cloud | Where the standby runs |
|---|---|
| AWS | **Another availability zone** of the same region: a separate datacenter with its own power and network. |
| DigitalOcean | In **New York** and **San Francisco**, the city's **other datacenter** (NYC1 and NYC3, SFO2 and SFO3). In the other regions, which have one datacenter, a **separate server in the same datacenter**. |
| OVHcloud | A **separate server in the same datacenter**: the regions Rowsafe Cloud offers have one datacenter each. |

A standby in the same datacenter covers the primary's server failing (hardware, disk, a crash), not an outage of the whole datacenter.

### Price

The standby is billed like any Rowsafe Cloud server of its size, by the hour and never more than its monthly price: **twice the price** in total. A Small DigitalOcean server with a standby costs about $0.096 an hour, at most $70 a month. A server and its standby count as **one** server against your organization's Rowsafe Cloud limit. Remove the standby and its billing stops.

### Automatic failover, and what it can lose

Automatic failover only acts when **every** condition holds, and the server's page shows them:

- the primary has been **unreachable for about 3 minutes**, both for Rowsafe and for the standby;
- the standby is running and was in sync, **at most about a minute behind** when the primary was last heard from;
- nothing on purpose is going on: no restart, update or other change that stops PostgreSQL. Rowsafe also holds failover while it powers off or deletes one of the two servers itself.

Then Rowsafe stops the old primary for good (as soon as it can reach it again) and promotes the standby, and says so in an alert and in the activity log.

- **Up to about a minute of the newest changes can be lost.** The standby copies changes as they happen, not in lockstep with every commit (asynchronous streaming), so the last changes before the primary died may not have reached it. Usually it's under a second behind; Rowsafe doesn't fail over when it was further behind than a minute.
- **One case to know: a network cut.** If the primary is cut off from Rowsafe and from the standby but your apps can still reach it, both servers could accept writes until the old primary is back on the network, and then Rowsafe stops it. The writes made to the old primary in between aren't on the new one. Keeping your apps on the same network path as the standby, or connecting through a [Rowsafe pooler](/docs/guides/connection-pooling), avoids it. See [Standby](/docs/guides/standby) for the details.

Turn automatic failover off or on any time on the database's **Standby** page. Without it, you switch with one click (**Promote**) when the primary is down.

### Connect so your app follows a failover

The server's page shows **connection strings that follow the primary**: both servers' addresses in one string, and the driver keeps the one that accepts writes, before and after a failover. For example, with libpq, psycopg or pgx:

```
postgresql://USER@PRIMARY_ADDRESS:5432,STANDBY_ADDRESS:5432/DBNAME?target_session_attrs=read-write
```

Java uses `targetServerType=primary`. Drivers that take one address (node-postgres) need a [Rowsafe pooler](/docs/guides/connection-pooling) or a DNS name you move. The standby itself takes read-only queries, for reports. Both servers let in the addresses under **Who can connect**, and each other.

### After a failover

The standby is the primary now, and the old primary is stopped. On the old primary's page, click **Make it the standby again**: Rowsafe reuses its data where it can (else restores the latest backup there) and keeps it in sync, so you have a standby again. Or click **Remove the standby** to delete that server.

### Remove the standby

On either server's page, click **Remove the standby** and type the server's name. The standby server is deleted, its billing stops, automatic failover turns off, and the primary keeps running untouched. Deleting the primary asks to delete its standby too.

While a server has a standby, **Take it with you** isn't offered: remove the standby first.

## Your passphrase, only yours

Backups are encrypted on the server with a passphrase made **on the server**. You save a copy through your browser, encrypted end to end; Rowsafe passes on only the encrypted message and never has the passphrase. Without it, nobody can restore your backups, Rowsafe included, so save it before you rely on the database. The dashboard keeps asking until you confirm you saved it.

## Nothing changes until you click

No maintenance windows and no surprise restarts. Restarts, updates and deleting each wait for someone in your organization to click and confirm. There are no permission switches to set: Rowsafe hosts the server, so restarts, PostgreSQL and security updates, reboots and restored copies are all available, and each runs only after that click. Updates are a button you click: nothing patches or restarts on its own, so keeping up is yours to decide. AI assistants (MCP) can list servers and save Marks, but can't create, resize, restart or delete anything.

## Take it with you

Move your database to your own server whenever you like, with about a minute of downtime:

1. Install Rowsafe on your server ([Quickstart](/docs/quickstart)).
2. On the Rowsafe Cloud server's page, click **Take it with you** and pick your server.
3. Your server gets a copy from the latest backup and keeps it in sync while the database keeps running. Then apps are disconnected for about a minute while your server takes over. Nothing is lost.
4. Check your app works with the new address. The Rowsafe Cloud server is stopped, as a way back, and deleted only when you confirm; its billing stops then.

It's plain PostgreSQL, so there's no lock-in. Rowsafe keeps protecting the database on your server. See [Move to a new server](/docs/guides/move).

## Private connection from your AWS network

If your apps run in AWS, they can reach a Rowsafe Cloud server on AWS **without going over the internet**. This uses **AWS PrivateLink**: AWS carries the traffic from your own network (your VPC) to the server, privately, and only the AWS accounts you name can connect.

- **Price:** $20 a month at most, billed by the hour ($0.028) while it's on, on the same pay-as-you-go subscription as your servers. Turn it off and billing stops.
- **AWS only, same region only.** It works for Rowsafe Cloud servers on AWS, from VPCs in the **same AWS region** as the server (an AWS PrivateLink rule). DigitalOcean and OVHcloud servers don't have it.
- **With a standby, it follows the database.** Turn it on on the primary's page. After a failover, the same endpoint reaches the server that holds the database now, with nothing to change on your side; if you then remove the old primary, the private connection stays.

### Turn it on

1. Open the server's page (**Servers**, then the server) and find **Private connection from your AWS network**.
2. Click **Turn on**, type the IDs of the AWS accounts your apps run in (12 digits, shown at the top right of the AWS console), tick the price and confirm. Owners and admins can do this.
3. After a few minutes Rowsafe shows the **service name** (it starts with `com.amazonaws.vpce.`), the region, and the **zones** your endpoint can use. Zones are shown as AWS zone IDs (like `euc1-az2`), which are the same in every AWS account; your console shows them next to the zone names.

### Connect from your VPC

Your apps connect through an **endpoint** in your VPC.

**If your AWS account is connected to Rowsafe** ([Connect AWS](/docs/guides/cloud-accounts/aws)), click **Create the endpoint for me**, pick the VPC and a subnet in each zone your apps use, and Rowsafe creates the endpoint with a security group that lets that VPC reach port 5432. Accounts connected before this feature need the [updated policy](/docs/guides/cloud-accounts/aws#the-policy) for this button.

**Otherwise, in your AWS console:**

1. Sign in with the account your apps run in, and switch to the server's region (top right).
2. Open the **VPC** console and choose **Endpoints**, then **Create endpoint**.
3. Name it, and under **Type** choose **Endpoint services that use NLBs and GWLBs**.
4. Paste the service name Rowsafe shows under **Service name** and click **Verify service**.
5. Choose the VPC your apps run in, then a subnet in each zone your apps use (only the zones Rowsafe lists work).
6. Choose a security group that lets your apps reach port **5432** (for example, one that allows your VPC's own addresses on 5432).
7. Click **Create endpoint**. When it's **Available**, copy its first DNS name.

Connections from the accounts you named are accepted right away: AWS lets only those accounts create an endpoint to it, so there's nothing to approve. If you remove an account, its endpoints are disconnected at once.

### Connect your app

Use the endpoint's DNS name as the host, port 5432, and `sslmode=require`, with a user from [Databases & users](/docs/guides/databases-and-users):

```
postgresql://USER:PASSWORD@<your endpoint's DNS name>:5432/postgres?sslmode=require
```

Connections stay encrypted. The server's certificate is its own (made when it was set up), so it doesn't carry your endpoint's name: use `sslmode=require`, not `verify-full`, which checks the name and refuses it.

**Only private connections:** once your apps connect privately, you can close the database's port to the internet with one switch (it empties **Who can connect**, after a confirmation). Backups and Rowsafe keep working.

### Turn it off

Click **Turn off** and confirm. Rowsafe deletes the private connection in AWS, with the endpoints it created in your accounts, and billing stops. Endpoints you made yourself stop working; delete them in your VPC console. Deleting the server turns its private connection off too.

## Limits

- **PostgreSQL only**, versions 15 to 18.
- **A standby is optional and costs a second server.** It runs in another availability zone (AWS) or datacenter (DigitalOcean New York and San Francisco) where the region has one, and on a separate server in the same datacenter elsewhere. Failover waits about 3 minutes and can lose up to about a minute of the newest changes; see [With a standby](#with-a-standby).
- **Private connections** are for servers on AWS, from VPCs in the same AWS region only.
- **Changing the size takes the database offline for a few minutes**, and a disk never shrinks: see [Change the size](#change-the-size). A server with a standby can't change size yet: remove the standby, change the size, then add it again.
- SSH keys are set when you create the server.
