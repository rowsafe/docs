## Members and roles

| Role | Can |
|---|---|
| **Member** | View databases, backups, Proof results and activity. |
| **Admin** | Everything a member can, plus adopt databases, run tasks, restart PostgreSQL (on servers that allow it), [Rewind](/docs/guides/restore) (restore copies, bring back rows, rewind a database), manage hosts, alert rules, API keys and members. |
| **Owner** | Everything, including billing and [what AI agents may do](/docs/guides/agent-autonomy#the-team-setting). |

Admins and owners invite people under **Settings → Members** (invitations expire after 7 days). Only owners can make or change an owner. The organization's creator is its first owner.

## API keys

The CLI, scripts, CI and AI agents use **API keys** (`rsk_...`).

- **On your machine:** run `rowsafe login`, approve it in the dashboard (admins and owners only), and a key is made for you.
- **For CI and servers:** create a key under **Settings → API keys** and pass it with `ROWSAFE_API_KEY` or `rowsafe login --key`. See [Save a Mark before every deploy](/docs/guides/deploys).

```sh
rowsafe api-keys create deploy-ci
rowsafe api-keys create dashboards --read-only
rowsafe api-keys list
rowsafe api-keys revoke key_...
```

- A key is shown **once**. Rowsafe stores only a hash. Keep it in a secret manager.
- A **read-only** key can only read. Anything else gets `This API key is read-only.`
- Revoking takes effect on the next request. A key can't revoke itself.
- `rowsafe logout` revokes the key `rowsafe login` made. Keys given with `--key` stay valid.

A read-write key follows its person's role: whoever created it in the dashboard or approved the `rowsafe login` (shown in **Settings → API keys**). Before each change, Rowsafe checks that person's current role:

- **Admin or owner:** the change goes through.
- **Member:** read only, like in the dashboard. Changes get `... is a member now, and members can only view`, and so do AI agents using the key.
- **Left the organization:** no changes; it can still read until revoked, so revoke it. **Settings → API keys** marks these keys.
- **Role can't be confirmed:** nothing changes; try again in a minute.

`rowsafe logout` and cancelling a request always work. AI agents using a key (local `rowsafe mcp` or the remote MCP endpoint) [act as its person](/docs/guides/agent-autonomy).

<Accordions>
<Accordion title="Older keys and keys made by other keys">

- **Made by another key** (`rowsafe api-keys create`, shown as *Made by key ...*): its changes follow the role of the person behind the parent key, but AI agents' changes with it are refused. Create agent keys in the dashboard.
- *Made before Rowsafe recorded who made keys*: works as before, with no person to check. Replace it.
- **Made before agents could act as their person:** agents' changes are refused until its person clicks **Let agents using it act as me**, or makes a new key.

</Accordion>
</Accordions>

## Audit log

Every change is recorded: who, what, and where. See **Settings → Audit log**, or:

```sh
rowsafe audit              # newest first
rowsafe audit --limit 200
```

```text
WHEN                 ACTOR                                      ACTION                TARGET  DETAIL
2026-09-24 14:05:12  key:key_... (CLI · rowsafe CLI on laptop)  restore_point.create  app     before-migration-42
```

AI agents' changes read like `ana@example.com through their AI agent Claude`. The installer's read like `installer on db-1`.

It records, among others: databases added, changed and removed; hosts changed and removed; enrollment tokens created; tasks queued (backups, Proof runs, plans, restarts); Marks; forks (`database.fork`); Rewind (`rewind.copy`, `rewind.copy_extend`, `rewind.copy_delete`, `rewind.compare`, `rewind.rows`, `rewind.in_place`, `rewind.undo`, `rewind.cleanup`); API keys created and revoked; alerts acknowledged; alert rules and notification channels changed; plan changes; letting an app or key act as you; what AI agents may do; and CLI logins approved or denied.
