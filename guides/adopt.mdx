---
title: Adopt an existing database
description: Put a production PostgreSQL server under Rowsafe safely, step by step.
---

This guide puts a production PostgreSQL server under Rowsafe. At the end, every change is archived to your bucket, backups and the weekly Proof run on their own, and you get alerts. Coming from a nightly `pg_dump`, the most you can lose drops from 24 hours to about a minute.

The examples use a database `app` on a server `db-1`. Use your own names.

## Safety principles

- **Read-only until you say yes.** The installer shows its plan first.
- **No surprise restarts.** Rowsafe restarts PostgreSQL only when you say yes in the installer, or when someone clicks **Restart** and confirms, on servers where you allowed it.
- **Never replaces another backup tool silently.** If something else archives WAL, the plan refuses without `--force`.
- **Small, known changes.** At most four settings, all with `ALTER SYSTEM`, all reversible. See [the settings](/docs/concepts/postgresql#the-settings-rowsafe-changes).
- **Keep your old backups** until Rowsafe has proven itself.

**Time:** about an hour, plus one restart of a few seconds.

<Steps>
<Step>

### Check the server

On the server:

```sh
hostname                         # the host name Rowsafe will show
pg_lsclusters                    # e.g. 18  main  5432  online
sudo -u postgres psql -Xc "select name, setting from pg_settings where name in
  ('wal_level','archive_mode','archive_command','archive_library','archive_timeout')"
apt-cache policy pgbackrest | head -3
df -h / && free -h
```

Check that:

- the OS is Debian 12/13 or Ubuntu 22.04/24.04 (amd64 or arm64), with PostgreSQL 13 to 18 on the **primary**;
- `archive_command` is empty or `(disabled)`, and `archive_library` is empty. If something else archives WAL, find out what first;
- for PostgreSQL 18, pgBackRest is **2.55.0 or newer**. Prefer [apt.postgresql.org](https://wiki.postgresql.org/wiki/Apt), which Rowsafe is tested with;
- there's room for [Proof](/docs/concepts/restore-drills): about 1.3 × the data directory + 1 GiB free.

</Step>
<Step>

### Create the bucket

Create a **private** S3-compatible bucket, for example `app-rowsafe`. With Cloudflare R2:

- **R2**, then **Create bucket**. For the EU, choose the EU jurisdiction. Leave **public access** off.
- **Don't add a lifecycle rule** that deletes objects. Rowsafe expires backups itself; a rule would delete WAL that backups need and silently break restores.
- In the bucket's **Settings**, copy the **S3 API** URL (`https://<account-id>.eu.r2.cloudflarestorage.com/app-rowsafe`).

Create an API token with **Object Read & Write** on **this bucket only**, limited to the server's IPs if you can. Copy the key ID and secret: they're shown once. Other providers: [Set up backup storage](/docs/guides/storage).

</Step>
<Step>

### Create the passphrase and store it first

<Callout type="error" title="Without the passphrase, no backup can be restored">
  Every backup is encrypted with it. Lose it and every backup is unreadable forever. Nobody can recover it, Rowsafe included. Store it in two places before the first backup.
</Callout>

```sh
openssl rand -base64 48
```

Store it with the bucket keys in your secret manager, apart from the app's secrets: the app shouldn't be able to read or delete its own backups. Put a second copy in your company password manager, and check that someone else can open it.

</Step>
<Step>

### Run the installer

On the server:

```sh
curl -fsSL https://rowsafe.sh | sudo sh
```

It prints a link to the approval page. Check the code matches your terminal and approve (admins and owners only). The server gets a single-use enrollment token, never an API key.

Or from your own computer (macOS or Linux, [CLI](/docs/reference/cli#install) logged in), over SSH, with nothing to copy or approve:

```sh
rowsafe hosts add root@203.0.113.10
```

It uses your SSH login (any `sudo` user; `-p PORT`, `-i KEY` or a `~/.ssh/config` name), makes a one-time token and runs the same installer, with its questions in your terminal. The token never appears in a command line on the server. Installer options go after `--`, for example `rowsafe hosts add root@203.0.113.10 -- --storage rowsafe`.

To skip the approval, use the command from **Servers**, then **Add a server**. It holds a one-time token, valid for an hour (CLI: `rowsafe hosts enroll-token`):

```sh
curl -fsSL https://rowsafe.sh | sudo sh -s rse_...
```

The installer verifies the agent's signature and installs pgBackRest if missing (check its summary: signature verified, pgBackRest 2.55.0+). Then it asks:

1. **The bucket URL**, key ID and secret. It tests a write, read and delete, and asks again with the reason if that fails.
2. **The passphrase.** Choose **Use my own passphrase** and paste yours.
3. **What Rowsafe may do** on this server: restart PostgreSQL (`Restart or stop PostgreSQL, when someone clicks Restart or Rewind?`), install updates, manage PgBouncer for [connection pooling](/docs/guides/connection-pooling) (installs nothing now), and so on. Always only when an admin or owner clicks and confirms. Change it later with `sudo rowsafe-allow` ([permissions](/docs/guides/permissions)).
4. **The database name**, for example after `Found PostgreSQL 18 on port 5432 (1.2 GB; databases: app)`. It covers the whole PostgreSQL server: lowercase letters, digits and dashes.
5. **The plan**, then `Nothing changes until you say yes. Turn on backups for app now? [Y/n]`.

A typical plan:

| Change | From | To | Restart |
|---|---|---|---|
| write `/etc/rowsafe/pgbackrest/app.conf` (0600) | | | |
| `pgbackrest stanza-create` | | | |
| `archive_mode` | `off` | `on` | **yes** |
| `archive_command` | (empty) | `/usr/bin/pgbackrest --config=/etc/rowsafe/pgbackrest/app.conf --stanza=app archive-push %p` | no |
| `archive_timeout` | `0` | `60` | no |

If `wal_level` is `minimal`, it becomes `replica` (also a restart). **Answer `n` if the plan shows anything else**, especially a warning about an existing `archive_command`.

On yes, the agent writes the config and runs `stanza-create` (if that fails, PostgreSQL is untouched), then sets the settings and reloads. No downtime.

Last: `Restart PostgreSQL now? [y/N]`. For production, answer **N** and restart in your window (next step).

Check the server reports in: in the dashboard, or `rowsafe hosts list` (`db-1`, last seen seconds ago). `sudo journalctl -u rowsafe-agent -n 20` should show `enrolled` and no errors. Then delete the used-up `ROWSAFE_ENROLL_TOKEN` line from `/etc/rowsafe/agent.env`.

</Step>
<Step>

### Restart PostgreSQL in a maintenance window

The database is `awaiting_restart`. The restart is the only downtime: **usually 2 to 10 seconds of refused connections**. Run a checkpoint right before to keep it short, and make sure your app reconnects by itself.

<Tabs items={["On the server", "From Rowsafe"]}>
<Tab value="On the server">

```sh
sudo -u postgres psql -Xc "select name from pg_settings where pending_restart"   # archive_mode
sudo -u postgres psql -Xc "checkpoint"
time sudo systemctl restart postgresql@18-main                                   # your cluster's unit
sudo -u postgres psql -Xc "show archive_mode"                                    # on
```

Use the cluster's systemd unit, so its restart policy stays in charge.

</Tab>
<Tab value="From Rowsafe">

If you allowed restarts, click **Restart PostgreSQL now** on the database's page and confirm. Or:

```sh
rowsafe restart app       # asks to confirm; --yes skips it
```

Admins and owners only, never with a read-only API key, at most once every 2 minutes. An AI agent can restart only [as the person who connected it](/docs/guides/agent-autonomy), if they're an owner or admin.

</Tab>
</Tabs>

</Step>
<Step>

### Check the first backup and run Proof

**Rowsafe notices the restart by itself.** It checks that changes reach your bucket, marks the database `active`, and starts the first full backup. To check now, click **Check now** or run `rowsafe verify app`.

```sh
rowsafe tasks app      # backup running ... succeeded
rowsafe backups app    # type, duration, database size, stored size
```

A few GB take several minutes. Then click **Run Proof now**, ideally in a quiet hour, or:

```sh
rowsafe proof app
rowsafe proofs app     # PASS, recovered to <time>, duration
```

A passing Proof is your first evidence you can restore. `rowsafe status app` now says `app is PROTECTED.`

</Step>
<Step>

### Keep your old backups for 30 days

Keep your old backup job running for 30 days. Meanwhile:

- **every day**, backups succeed (alerts tell you if not);
- **every week**, the Sunday Proof passes;
- **once**, practise: [restore a copy](/docs/guides/restore#restore-a-copy) and compare it, and do one [restore by hand](/docs/guides/restore#advanced-restore-by-hand-or-to-another-server) to a scratch server and run your app's smoke tests. Note how long each took.

Then retire the old job. [Set up alert channels](/docs/guides/monitoring#notification-channels) if you haven't.

</Step>
</Steps>

## Automate it

For cloud-init, config management or scripts, run the installer without questions:

- Put the storage settings in its environment. It writes them to `agent.env` without printing them, and tests the bucket.
- Add `--protect NAME` to register, plan and apply without prompts. It **never restarts** PostgreSQL; Rowsafe notices when you do.

Send secrets over SSH's standard input, so they never land in a shell history, file or command line (`printf` is a shell builtin, so they stay out of the process list):

```sh
printf 'export ROWSAFE_ENROLL_TOKEN=%s ROWSAFE_REPO_S3_KEY=%s ROWSAFE_REPO_S3_KEY_SECRET=%s ROWSAFE_REPO_CIPHER_PASS=%s\n' \
  "$ENROLL_TOKEN" "$S3_KEY" "$S3_SECRET" "$CIPHER_PASS" |
ssh admin@db-1 'sudo sh -c ". /dev/stdin;
  export ROWSAFE_REPO_S3_ENDPOINT=<account-id>.eu.r2.cloudflarestorage.com ROWSAFE_REPO_S3_BUCKET=app-rowsafe;
  curl -fsSL https://rowsafe.sh | sh -s -- --protect app"'
```

If the plan needs anything unusual (another tool archives WAL), `--protect` stops and changes nothing. `--no-allow-restart` keeps **Restart** off on this server; `--allow-restart` turns it on. See the [installer options](/docs/reference/agent-configuration#installer).

## Add the database from the dashboard or the CLI

Use this after `--no-setup` (agent and storage only), when a server runs more than one PostgreSQL, or for [PostgreSQL in Docker](/docs/guides/docker).

In the dashboard: **Databases**, then **Add database**. Or:

```sh
rowsafe adopt app --host db-1    # register and print the read-only plan
rowsafe apply app                # apply it; you confirm with y
```

`adopt` only reads; `rowsafe plan app` shows the plan again. Options: `--port` (default 5432), `--socket-dir` (default `/var/run/postgresql`), `--retention-full` (default 2 full backups). `apply` never restarts PostgreSQL.

## Rollback

Every step can be undone. Pick how far to go.

<Accordions>
<Accordion title="Stop Rowsafe, keep archiving">

```sh
sudo systemctl disable --now rowsafe-agent
```

WAL still goes to your bucket. No backups or Proof until the agent runs again.

</Accordion>
<Accordion title="Stop WAL archiving now, without a restart">

```sh
sudo -u postgres psql -Xc "alter system set archive_command = '/bin/true'" -c "select pg_reload_conf()"
```

PostgreSQL marks WAL as archived without storing it, so `pg_wal` can't fill up. Point-in-time recovery stops from now.

<Callout type="warn">
  Don't just `ALTER SYSTEM RESET archive_command` while `archive_mode` is on. PostgreSQL then keeps every WAL segment and the disk fills up.
</Callout>

</Accordion>
<Accordion title="Return to the original settings (needs a restart)">

In your next maintenance window (`RESET` falls back to `postgresql.conf`):

```sh
sudo -u postgres psql -Xc "alter system reset archive_mode" -c "alter system reset archive_command" \
  -c "alter system reset archive_timeout" -c "select pg_reload_conf()"
sudo -u postgres psql -Xc "checkpoint"
sudo systemctl restart postgresql@18-main
sudo -u postgres psql -Xc "show archive_mode"      # off
```

</Accordion>
<Accordion title="Stop managing the database in Rowsafe">

```sh
rowsafe remove app --keep-archiving
```

Changes nothing on the server or bucket. Without `--keep-archiving`, Rowsafe refuses once a plan was applied, since the server keeps archiving until you turn it off (above).

</Accordion>
<Accordion title="Uninstall the agent">

See [Uninstall](/docs/guides/agent-updates#uninstall). Turn off archiving first if you'll `--purge` the agent's config.

</Accordion>
</Accordions>

Keep the bucket and passphrase until you're sure you won't need any backup in it.
