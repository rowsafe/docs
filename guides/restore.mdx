---
title: Restore a database
description: Rewind to any second or a Mark, bring back rows, or rewind the whole database, in one click.
---

**Rewind** saves every change, so you can go back to any second in your recovery window, or to a **Mark**. Open the database's **Rewind** tab, then **Rewind**.

Two ways back:

- **Restore a copy** next to production, compare it, and **bring back** the rows you lost. Production keeps running. Usually what you want.
- **Rewind the whole database** to that moment. For the worst case. You can undo it.

Everything happens on your server. Only names, counts and sizes reach Rowsafe.

Works for PostgreSQL, MySQL, MariaDB, MongoDB, ClickHouse, Redis and Valkey. This page uses PostgreSQL's words; differences are in [By database](#by-database).

## Which one to use

| What happened | Do this | What happens to production |
|---|---|---|
| Rows deleted or overwritten by mistake (a `DELETE` without `WHERE`, a bad script, a bug) | [Restore a copy](#restore-a-copy), [compare](#compare-with-production), [bring back rows](#bring-back-rows) | Only the rows you choose are put back. Everything else, including newer writes, stays. |
| You want to see the data as it was at 14:04 | [Restore a copy](#restore-a-copy) | Nothing. |
| A migration or script damaged many tables, or a table was dropped | [Rewind the whole database](#rewind-the-whole-database) | PostgreSQL stops while Rowsafe restores. Later writes are removed, and kept aside 7 days for undo. |
| The server is lost, or you want the database elsewhere | [Restore by hand](#advanced-restore-by-hand-or-to-another-server) | Nothing: you restore onto a new server. |

You can go back to any second from the start of your oldest full backup up to the last change in your bucket (at most about a minute ago).

## Restore a copy

<Steps>
<Step>

### Pick the moment

Pick a time, in your time zone, to the second: just before the mistake (14:04:00 for a `DELETE` at 14:05). Or pick a **Mark** (also **Restore a copy at this Mark** on the **Marks** page): the copy has everything committed before it, nothing after.

</Step>
<Step>

### Restore it

Click **Restore a copy**. It's kept 24 hours by default, up to 7 days. It takes about as long as a [Proof](/docs/concepts/restore-drills) run (see the **Proof** tab), longer when the moment is far from the last backup.

</Step>
<Step>

### Use it

When ready, you see its last change, size and expiry. **Extend** keeps it longer, **Delete** removes it. Then [compare it with production](#compare-with-production).

</Step>
</Steps>

The copy is:

- **On your server**, restored like Proof does. It holds every database in that PostgreSQL server.
- **Isolated**: a private Unix socket, no network port, read-only, never archives to your bucket, low CPU and IO priority.
- **Deleted by itself** when it expires, even offline. **Health** offers **Keep it 24 hours longer** before then.
- **One at a time** per database. Delete it to restore another moment.

It needs about **1.3 × the database size + 1 GB** free in `/var/lib/rowsafe/rewind`. With less, Rowsafe says how much and doesn't start.

## Compare with production

On the copy's card, click **Compare with production**, for every table or the ones you pick. Per table, by primary key:

| Count | Means |
|---|---|
| **Missing in production** | Rows in the copy whose key is gone from production: deleted since. |
| **Changed** | Rows with the same key and different values. |
| **Only in production** | Rows added since. |

It runs on your server with temporary tables. Production isn't changed, and only counts reach Rowsafe.

Skipped tables show why:

- **No primary key**: Rowsafe can't match rows. Rewinding the whole database brings such a table back.
- **Too big**: over 5 GB or 20 million rows.
- **Dropped since**, or its key column changed type.
- More than 200 tables: pick the ones to compare.

Tables linked by foreign keys (like `orders` and `order_items`) are shown together, so you can bring them back in one run. Notes flag things like a column added since.

## Bring back rows

Select the tables, check the counts, click **Bring back N missing rows**, and type the database name. Then:

1. Rowsafe saves a **Mark** first.
2. It puts back only rows whose key is **missing** in production. Existing and newer rows stay.
3. Parents before children, all in **one transaction** per database: every table gets its rows back, or nothing changes.
4. **Triggers don't fire**, so no duplicate emails or webhooks. Rowsafe checks foreign keys itself first.
5. **Sequences** move past the restored keys.
6. A row whose unique value (an email, say) now belongs to another row is skipped and reported as a **conflict**.

You see the result, like "Brought back 1,204 rows in applications and 3,310 in application_notes."

**Also restore rows that were changed** (off by default) resets changed rows to the copy's values. Use it after a bad `UPDATE`.

Per run:

- Up to **50 tables**.
- Rows by [plan](/docs/concepts/plans-and-limits#rewind-limits): 1 million on Free, 10 million on Pro, 50 million on Business (today the agent stops at 10 million). Over the limit, nothing changes: bring back fewer tables.

Nothing changes, and Rowsafe says why, when:

- rows would point to rows of another table missing in production: add that table to the run;
- another session locks a table for more than 5 seconds: try again;
- a column added since needs a value the copy doesn't have;
- restoring changed rows would leave other rows pointing to missing values: bring back only missing rows.

Added columns get their default, generated columns are recomputed, and removed columns are left out.

## Rewind the whole database

<Callout type="warn" title="The worst case only">

This replaces the live database. Everything written after your moment is removed, in **every database inside that PostgreSQL server**, and PostgreSQL stops while it runs. If only some rows are wrong, [bring them back](#bring-back-rows) instead.

</Callout>

Under **Rewind the whole database to this point**, pick the moment and type the database name. The page says exactly what will happen.

1. Rowsafe saves a **Mark** and checks everything below. If anything is missing, it stops first.
2. **Stops PostgreSQL.** Apps get errors for about as long as [restoring a copy](#restore-it) takes.
3. **Keeps the current data aside** by renaming the data directory to `<data directory>.before-rewind-<UTC time>` (instant, nothing copied).
4. Restores into a fresh data directory, keeps your config, and replays changes up to your moment, with no network port.
5. **Starts PostgreSQL**.
6. Takes a full backup and checks changes reach your bucket.

If anything fails after the stop, or the agent restarts mid-way, Rowsafe puts the original data back and starts it.

**It needs:**

- PostgreSQL **installed on the server**, or in Docker with the [container control service](/docs/guides/docker#let-rowsafe-restart-the-container) and a data volume the agent can write. Otherwise, restore a copy and bring back rows.
- Permission to **restart or stop PostgreSQL**, given at install. Older servers may need the install command run again: see [Troubleshooting](/docs/troubleshooting#rewind-the-whole-database-isnt-available).
- The **primary**, not a replica.
- **No tablespaces** of your own (not supported yet).
- About **the database size + 10%** free next to the data directory, for Undo.

If something's missing, the button is disabled and says why.

Standby replicas no longer match after a rewind. Rowsafe warns you; set them up again.

### Undo a rewind

**Undo rewind** swaps the data back the same way: stop, swap, start. Writes made after the rewind are kept aside in turn, so nothing is lost. Only the latest rewind can be undone.

The old data is kept **7 days**, then deleted. **Delete the old data now** frees the disk, and ends Undo. **Health** reminds you while it's there.

## By database

Same buttons; what happens underneath depends on the database.

| | Restore a copy to | Compare by | Bring back rows | Rewind the whole database |
|---|---|---|---|---|
| PostgreSQL | any second or a Mark | primary key | one transaction per database; triggers don't fire | stops PostgreSQL and swaps the data directory (needs `restart`) |
| MySQL, MariaDB | any second or a Mark | primary key | one transaction per database; triggers run (MySQL can't turn them off) | stops the server and swaps the data directory's contents (needs `restart`; not in Docker, not with replicas) |
| MongoDB | any second or a Mark | `_id` | not one transaction: running it again finishes the job | swaps each collection with a rename, MongoDB keeps running (not with time series collections) |
| ClickHouse | any second (to the microsecond) or a Mark | all columns (no unique key) | not one transaction; not into Summing, Aggregating or Collapsing tables | swaps data partition by partition, ClickHouse keeps running (not replicated tables) |
| Redis, Valkey | about a second (when each change reached the agent), or exactly a Mark | key, per logical database (large databases are sampled) | keys for a pattern, with their remaining time to live; existing keys only overwritten if you choose | loads each logical database into an empty one and swaps it in (`SWAPDB`), Redis keeps running (needs an empty logical database and free memory for one more copy of the largest) |
| SQLite | any second or a Mark (WAL mode); a backup otherwise | primary key (row number without one) | one transaction; never overwrites a row | writes the restored file into the live one, your app keeps running (writes wait a few seconds) |
| OpenSearch | a snapshot (every 5 minutes) or a Mark | document `_id` (large indices: the first million) | documents with their `_id`; existing ones only overwritten if you choose | deletes each index and restores it from the snapshot, OpenSearch keeps running (searches of an index fail while it's restored) |
| Qdrant | a snapshot (every 15 minutes) or a Mark | not available | not available | restores each collection through Qdrant's API, Qdrant keeps running |
| Meilisearch | a snapshot (every 15 minutes) or a Mark | primary key | documents; existing ones only overwritten if you choose | copies the indexes in under other names, then swaps them in at once, Meilisearch keeps running |

Undo works the same everywhere: the old data is kept 7 days (on the server; for Redis and Valkey, as a snapshot in your bucket). Details: [MySQL and MariaDB](/docs/guides/mysql#rewind-the-whole-server), [MongoDB](/docs/guides/mongodb), [ClickHouse](/docs/guides/clickhouse), [Redis and Valkey](/docs/guides/redis#rewind), [SQLite](/docs/guides/sqlite#restore), [OpenSearch](/docs/guides/opensearch#rewind), [Qdrant](/docs/guides/qdrant#rewind-the-whole-database), [Meilisearch](/docs/guides/meilisearch#rewind). The rest of this page is about PostgreSQL.

## Who can do this

- **Owners and admins** only, and API keys with write access. Every step is in the [audit log](/docs/guides/teams#audit-log).
- **AI agents act as their person.** They can show the window (`rewind_window`) and, when you ask, restore a copy, bring rows back or rewind [as the person who connected them](/docs/guides/agent-autonomy), with the same confirmations and Mark first. It runs at once for an owner's or admin's agent when there's a backup to go back to; otherwise Rowsafe refuses.

## Do it yourself

The buttons do all of this. These are for scripts, and for tables Rowsafe can't compare.

<Accordions>
<Accordion title="The same from a terminal">

`rowsafe rewind` does what the **Rewind** page does, with the same confirmations:

```sh
rowsafe rewind app                          # the recovery window, the copy, data kept aside
rowsafe rewind copy app --at "14:04"        # your time zone; or --at "10m ago", or --mark before-migration-42
rowsafe rewind compare app                  # every table; or name some: public.orders public.order_items
rowsafe rewind rows app public.orders public.order_items
rowsafe rewind database app --at "14:04"    # rewind the whole database
rowsafe rewind undo app
```

Every flag: [CLI reference](/docs/reference/cli#rewind).

</Accordion>
<Accordion title="Read the copy with psql">

The copy listens on a Unix socket for the server's `postgres` user, on Proof's port (`ROWSAFE_DRILL_PORT`, default 55432). `rowsafe rewind app` shows its ID:

```sh
sudo -u postgres psql -h /var/lib/rowsafe/rewind/<copy-id>/socket -p 55432 -d app
```

It's read-only. Use it for tables without a primary key, or to `pg_dump --table=...` one.

</Accordion>
</Accordions>

## Advanced: restore by hand or to another server

Restore by hand with pgBackRest when:

- the server or its disk is lost: the restored server becomes production;
- you want the database on another server, to test or investigate;
- you can't reach Rowsafe. Your backups are a standard pgBackRest repository in your bucket.

Practise once on a scratch server and note how long it took. The examples restore `app` on PostgreSQL 18 on a fresh Debian or Ubuntu server.

Just want the old state as a separate database? [Fork it](/docs/guides/fork) to a new database on one of your servers.

<Callout type="warn" title="Two rules">
  **Never restore over the only copy.** Use a new server, or at least a new data directory. The old cluster, even damaged, is evidence and a fallback.

  **One writer per bucket path.** Always restore with `--archive-mode=off`, so the restored cluster can't archive into the same repository.
</Callout>

### What you need

- **Bucket settings and passphrase** from your secret manager: endpoint, bucket, key, secret and the **encryption passphrase**. Without the passphrase, nothing can be restored.
- The repository path (`/rowsafe/<name>` by default) and the stanza (the database's name in Rowsafe).
- If the old server is reachable, `/etc/rowsafe/pgbackrest/app.conf` has all of this.
- A server with the **same PostgreSQL major version**, the same extensions (compare `shared_preload_libraries` and `\dx`), the same or newer pgBackRest, and disk for the data directory plus WAL.

<Steps>
<Step>

### Prepare the server

With [apt.postgresql.org](https://wiki.postgresql.org/wiki/Apt) configured:

```sh
sudo apt-get install -y postgresql-18 pgbackrest     # creates and starts cluster 18/main
sudo systemctl stop postgresql@18-main
```

This keeps Debian's layout: config in `/etc/postgresql/18/main/`, data in `/var/lib/postgresql/18/main`.

</Step>
<Step>

### Configure pgBackRest

```sh
sudo install -d -o postgres -g postgres -m 0750 /etc/pgbackrest /var/log/pgbackrest
sudo install -o postgres -g postgres -m 0600 /dev/null /etc/pgbackrest/pgbackrest.conf
sudoedit /etc/pgbackrest/pgbackrest.conf
```

```ini title="/etc/pgbackrest/pgbackrest.conf"
[global]
repo1-type=s3
repo1-s3-endpoint=<account-id>.eu.r2.cloudflarestorage.com
repo1-s3-bucket=<bucket>
repo1-s3-region=auto
repo1-s3-uri-style=path
repo1-s3-key=<access key id>
repo1-s3-key-secret=<secret access key>
repo1-path=/rowsafe/app
repo1-cipher-type=aes-256-cbc
repo1-cipher-pass=<passphrase>
process-max=4
log-level-console=info
log-path=/var/log/pgbackrest

[app]
pg1-path=/var/lib/postgresql/18/main
```

This server only **reads**. Don't run `backup`, `expire` or `stanza-*` from it while the original is alive. If your token only allows the old server's IP, make a read-only one (Object Read, this bucket only).

</Step>
<Step>

### Choose the backup and target

```sh
sudo -u postgres pgbackrest --stanza=app info
```

Any moment from the end of the oldest full backup to the end of the archive is reachable.

For a Mark, on your computer:

```sh
rowsafe marks app
```

Use Marks with status `archived`, and note the **RESTORE FROM BACKUP** column.

</Step>
<Step>

### Restore

The new data directory must be empty. **Check the path twice**: this empties the new cluster, never production.

```sh
sudo -u postgres sh -c 'find /var/lib/postgresql/18/main -mindepth 1 -delete'
```

Then run one of these.

#### To the latest state

```sh
sudo -u postgres pgbackrest --stanza=app --archive-mode=off restore
```

#### To a point in time

Stops just before the mistake. Always give a UTC offset:

```sh
sudo -u postgres pgbackrest --stanza=app --archive-mode=off \
  --type=time --target="2026-09-20 14:05:00+00" --target-action=promote restore
```

pgBackRest picks the newest backup ending before the target; `--set=<label>` picks one yourself.

#### To a restore point

Stops exactly at a Mark made with `rowsafe mark`:

```sh
sudo -u postgres pgbackrest --stanza=app --archive-mode=off \
  --set=20260921-010002F \
  --type=name --target=before-migration-42 --target-action=promote restore
```

<Callout type="warn" title="Always pass --set for a Mark">
  With `--type=name`, pgBackRest takes the newest backup. If it finished after the Mark, PostgreSQL refuses to start ("recovery ended before configured recovery target was reached"). Pass the **RESTORE FROM BACKUP** label from `rowsafe marks`, or an older backup.
</Callout>

`--archive-mode=off` writes `archive_mode = 'off'` into `postgresql.auto.conf`, so this cluster can't push WAL to production's repository. Rowsafe's `archive_command` is carried over but does nothing.

</Step>
<Step>

### Start and check

```sh
sudo systemctl start postgresql@18-main
sudo tail -f /var/log/postgresql/postgresql-18-main.log    # "ready to accept connections"
sudo -u postgres psql -Xc "select pg_is_in_recovery()"     # f
```

Check the data around the target, then run your app's smoke tests against this server.

</Step>
</Steps>

### Afterwards

<Tabs items={["This server becomes production", "It was a scratch restore"]}>
<Tab value="This server becomes production">

1. **Fence the old primary** so it can never write again: stop and disable its PostgreSQL, or shut it down.
2. Copy over what the restore lacks: `pg_hba.conf`, your `conf.d/` files, TLS certificates and keys, systemd drop-ins. Restart PostgreSQL.
3. Point your app at the new server and redeploy.
4. **Protect it again**: run the install command and give a **new name** (like `app-2`), for a fresh bucket path. Leave the old `app` path until you no longer need it.

</Tab>
<Tab value="It was a scratch restore">

Copy out what you need (`pg_dump --table=...`) and load it into production inside a transaction. Then delete the scratch cluster and revoke any read-only token you made.

</Tab>
</Tabs>

### From Docker backups

In the dashboard, copies and bringing back rows work in Docker too. Rewinding the whole database needs the [container control service](/docs/guides/docker#let-rowsafe-restart-the-container).

Docker backups are ordinary pgBackRest backups. Restore them the same way on a Linux server with the same PostgreSQL major version, using the bucket settings from `rowsafe-agent.env`.
