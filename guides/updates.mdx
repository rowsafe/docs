---
title: Update and upgrade your database
description: Install your database's bug and security releases with one click (PostgreSQL, MySQL, MariaDB, MongoDB, ClickHouse, Redis, Valkey), keep the server's security updates current, and upgrade to a new major version after a rehearsal, with undo.
---

Rowsafe keeps your database current on your own server. It works for PostgreSQL, MySQL, MariaDB, MongoDB, ClickHouse, Redis and Valkey; this page uses PostgreSQL, and [MySQL, MariaDB, MongoDB and ClickHouse](#mysql-mariadb-mongodb-and-clickhouse) and [Redis and Valkey](#redis-and-valkey) say what differs. Everything happens there, through the agent, and only when someone clicks and confirms (or opted in to automatic minor updates). Rowsafe saves a [Mark](/docs/concepts/restore-points) before each change.

| What | How long PostgreSQL stops | Undo |
|---|---|---|
| **Minor update**, e.g. 16.9 to 16.10: bug and security fixes | A few seconds (a restart) | Minor releases don't change behavior; restore to the Mark if you must |
| **Security updates** of the server (OpenSSL, the kernel, ...) | Not at all; some need a reboot | Not needed |
| **Reboot** | A minute or two | Not needed |
| **Major upgrade**, e.g. 16 to 18 | Measured by the rehearsal: seconds to minutes | 7 days, see [Safe and Fast](#safe-or-fast) |

<Callout title="Rowsafe Cloud servers">
  On a [Rowsafe Cloud](/docs/guides/rowsafe-cloud) server, which Rowsafe hosts, security updates install by themselves (never restarting PostgreSQL, never rebooting), and minor updates, restarts and reboots that are waiting are applied in a weekly [maintenance window](/docs/guides/rowsafe-cloud#updates-and-maintenance). Everything on this page still works there, any time you click.
</Callout>

## Allow it on the server

Rowsafe can only do what root allowed on the server. The installer asks once, on a terminal:

| Question | Name |
|---|---|
| `Install PostgreSQL updates and upgrades, when someone clicks Update? [Y/n]` | `updates` |
| `Install this server's security updates, when someone clicks Install? [y/N]` | `security-updates` |
| `Reboot this server, when someone clicks Reboot? [y/N]` | `reboot` (asked after a yes to security updates) |

They need restarts allowed too: updating the database restarts it, and the same helper does both. On other databases the question names them (*Install MySQL updates and upgrades...*). To change your answers later, on the server:

```sh
sudo rowsafe-allow restart updates        # allow PostgreSQL updates (and restarts)
sudo rowsafe-allow --remove reboot        # stop allowing reboots
```

See [Change what Rowsafe may do on a server](/docs/guides/permissions). The installer's options (`--allow-updates`, `--allow-security-updates`, `--allow-reboot` and their `--no-` forms) answer without asking.

The database's **Updates** tab shows what is allowed on its server, and why a button is off.

## Minor updates

When a newer release of your major is available (from apt.postgresql.org, or your distribution's repository), [Pulse](/docs/guides/monitoring) shows **PostgreSQL 16.10 is available (bug and security fixes)** with an **Update to 16.10** button. The **Updates** tab has the same button. After you confirm, Rowsafe:

1. saves a Mark;
2. installs only your major's own packages (`postgresql-16`, `postgresql-client-16`, `libpq5` and the `postgresql-16-*` extension packages you have), never another major;
3. restarts PostgreSQL if the packages didn't, and waits until it answers;
4. checks that changes still reach your backups.

The result says what happened, for example "Updated PostgreSQL from 16.9 to 16.10 in 12 s; it didn't accept connections for 3 s."

From a terminal:

```sh
rowsafe update app              # shows the versions, asks you to type the name, updates
rowsafe update app --auto on --timezone Europe/Berlin
```

**Automatic minor updates.** Turn on **Install minor updates automatically** on the **Updates** tab (or `rowsafe update app --auto on`): Rowsafe then updates on Sundays at 03:00 in your time zone, with a Mark first, when a new release is available and the agent is online. If it isn't, it waits for the next Sunday. Every automatic update is in the audit log as `rowsafed`.

<Callout type="warn">
  Packages are per major, not per cluster: when you update PostgreSQL 16, the server's other PostgreSQL 16 clusters also run the new release after their next restart (the packages usually restart them right away). The confirmation lists them.
</Callout>

## Security updates and reboots

Pulse shows **12 security updates are waiting; a reboot is needed** with **Install security updates** and, if a reboot is needed, **Reboot the server**. The agent counts the upgrades that come from your distribution's security repository about every hour.

- **Install security updates** installs only upgrades from the security repository. The database servers' own packages are left alone: they go through **Update** ([PostgreSQL](#minor-updates), [the others](#mysql-mariadb-mongodb-and-clickhouse)), which restarts the database in a controlled way. Services aren't restarted by the installation (`needrestart` only lists them); some updates, like a new kernel, only take effect after a reboot.
- **Reboot the server** saves a Mark on the database, then reboots the whole server: everything on it stops for a minute or two, the database included. You type the server's name to confirm. The agent reports back once the server is up and the database answers.

### MySQL, MariaDB, MongoDB and ClickHouse

**Update** works the same way for them: Rowsafe saves a Mark, the helper installs only that server's own packages (for example `mysql-community-server` and its client, `mariadb-server`, `mongodb-org-*`, `clickhouse-*`) at the newest release of the series you run (8.0, 10.11, 7.0, 25.8), from the server's own package sources (the vendor's repository or your distribution's), and restarts the server if the packages didn't. Rowsafe then waits until it answers. Tools versioned on their own (Percona XtraBackup, the MongoDB Database Tools and `mongosh`) are brought up to date with it. Automatic minor updates on Sundays work too.

**Major upgrades** (MySQL 8.0 to 8.4, MariaDB 10.11 to 11.4, MongoDB 7.0 to 8.0, ClickHouse 25.3 to 25.8) follow the same three steps as PostgreSQL's, in Safe mode:

1. **Check** lists the newer versions this server's package sources offer (add the vendor's repository for the version first: Rowsafe installs only from the server's own sources) and what blocks the upgrade. MongoDB goes one major version at a time, and only when its featureCompatibilityVersion matches the running version; MySQL 8.4 warns about accounts that log in with `mysql_native_password`, which 8.4 turns off by default.
2. **Rehearse** downloads the new version's server package as the agent's user (checked by apt like any package, never installed), restores your latest backup into a private copy with the version you run, then starts the new version on that copy: MySQL upgrades its data by itself, MariaDB runs `mariadb-upgrade`, MongoDB sets its featureCompatibilityVersion, ClickHouse reads every table back. Nothing on the server changes.
3. **Upgrade** saves a Mark, then the helper keeps your installed packages and a copy of the data directory, stops the server, installs the new version and starts it (running `mariadb-upgrade` for MariaDB, setting the featureCompatibilityVersion for MongoDB). If it fails, the old version and data are put back.

**Undo** (for 7 days) puts the kept data and packages back; what was written since is kept aside on the server. Removing the kept version (or 7 days) frees the disk. It needs free disk about the data's size. In Docker, the check lists the image change to make in your compose file.

On the server, root allows it with `sudo rowsafe-allow updates` (with restarts: the installer asks *Install MySQL updates and upgrades, when someone clicks Update?*); the allow list then holds `database`. In Docker, pull the newest image of the same version and recreate the container; Rowsafe notices the new version.

### Redis and Valkey

**Update** works the same way on a Debian or Ubuntu server: the helper installs only Redis's own packages (`redis-server`, `redis-tools`, `redis-sentinel` and `redis`, from packages.redis.io or your distribution) or Valkey's (`valkey-server`, `valkey-tools`, `valkey-sentinel`), at the newest release of the series you run (8.2, 7.4, 8.1...), restarts the server if the packages didn't, and waits until it answers and has loaded its data. Apps are disconnected for a few seconds. Automatic minor updates on Sundays work too. Root allows it with `sudo rowsafe-allow updates` (the installer asks *Install Redis updates, when someone clicks Update?*); the allow list then holds `database`.

- **Your distribution's fixes.** Debian and Ubuntu ship fixes of their Redis and Valkey without changing the version number (Debian 12's Redis stays 7.0.15). Rowsafe compares the packages themselves: Pulse shows **A security update of Redis 7.0.15 is available** (or just *an update*) and **Install the update** installs it.
- **The October 2025 security releases.** Redis 8.2.2, 8.0.4, 7.4.6, 7.2.11 and 6.2.20, and Valkey 8.1.4, 8.0.6 and 7.2.11, fix CVE-2025-49844 (a flaw in Lua scripts that lets anyone who can sign in and run a script take over the server) and CVE-2025-46817, CVE-2025-46818 and CVE-2025-46819. When an update brings that fix, Pulse calls it a security update and marks it critical. Rowsafe goes by the version number, so it can't see a fix your distribution added without changing it.
- **A Mark first, when there can be one.** On a server Rowsafe can't follow (scheduled snapshots only), there are no Marks: the update runs without one, and the confirmation says so.
- **Major upgrades** (Redis 7.2 to 7.4 or 8.x, Valkey 8.1 to 9.0) follow the [steps below](#major-upgrades), with the series your server's package sources offer (Redis 8 comes from packages.redis.io). The rehearsal restores your newest backup and the changes since into a temporary server with the version you run, saves it, then opens it with the new version and checks every numbered database has its keys. The upgrade keeps a copy of Redis's data folder and the installed packages for 7 days, so **Undo** puts the old version and its data back; an older Redis can't read what a newer one wrote, so what was written after the upgrade is set aside. Rowsafe refuses to upgrade a server that keeps nothing on its own disk (snapshots and the append-only file both off): the restart would empty it. Turn on snapshots first in **Tuning**. Redis 8 is published under other licenses than Redis 7 (RSALv2, SSPLv1 or AGPLv3); the check says so.
- **Updates and upgrades need snapshots on**: a server that keeps nothing on its own disk would come back empty from the restart, so Pulse offers **Turn on snapshots** first instead of **Update**.
- **In Docker**, Rowsafe can't replace your Redis or Valkey image. The agent image is built on the official image of your series (`redis8.2`, `valkey8.1`), so it knows that series' newest release when it was built, and Pulse shows when yours is older, with the step to run yourself:

```sh
docker compose pull redis && docker compose up -d redis
```

Redis restarts: apps are disconnected for a few seconds. A tag pinned to a release (`redis:8.2.1`) needs changing to the series (`redis:8.2`) first. Rowsafe notices the new version by itself.

## Major upgrades

Open the database's **Updates** tab, or use `rowsafe upgrade`. An upgrade has three steps.

### 1. Check

**Check** looks at the server and changes nothing:

- the new major is available from the server's package sources (apt.postgresql.org has every supported version);
- every extension package you use (`postgresql-16-*`) exists for the new major;
- enough free disk for each mode;
- the database isn't a read-only replica; replicas that stream from it are listed (they must be set up again afterwards);
- pgBackRest supports the new major (PostgreSQL 17 needs 2.53, 18 needs 2.55);
- the cluster is managed by Debian's PostgreSQL tools, and upgrades are allowed on the server.

### 2. Rehearse

**Rehearse** is required before the upgrade. Rowsafe restores the latest backup into a scratch copy on the server (like [Proof](/docs/concepts/restore-drills): no network listener, no archiving), installs the new major if needed, runs `pg_upgrade --check` and then `pg_upgrade` on the copy, starts the upgraded copy, checks every database opens with its tables, refreshes planner statistics, and makes sure pgBackRest accepts it. Then it deletes the copy.

Your database isn't touched. The new major's packages stay installed for the upgrade (Debian creates an empty `main` cluster when it installs them; Rowsafe removes that one).

The report says whether it passed, what `pg_upgrade` found if it didn't, how long each step took, and the **expected downtime** in each mode. A passed rehearsal allows the upgrade for 14 days.

The rehearsal needs free disk in `/var/lib/rowsafe/drills` for the copy: about 1.3 × the database's size + 1 GiB, and as much again to measure the Safe mode's copy (without it, Rowsafe measures the Fast mode and estimates the other).

```sh
rowsafe upgrade app --to 18 --rehearse-only
```

### 3. Upgrade

**Upgrade** asks for the mode and for the database's name, then:

1. saves a Mark;
2. stops PostgreSQL 16 and runs Debian's `pg_upgradecluster`, which moves the configuration from `/etc/postgresql/16/main`, the port and the systemd unit to PostgreSQL 18;
3. starts PostgreSQL 18 on the same port;
4. moves the backups to the new version (`pgbackrest stanza-upgrade`) and checks that changes reach your bucket;
5. refreshes planner statistics in the background (`vacuumdb --analyze-in-stages`);
6. takes a full backup and runs Proof on the new version.

If anything fails before PostgreSQL 18 accepts connections, Rowsafe puts PostgreSQL 16 back and starts it (Fast mode: restores it from the backup at the Mark, see below).

```sh
rowsafe upgrade app --to 18 --mode safe
```

### Safe or Fast

| | Safe | Fast |
|---|---|---|
| How | Copies the data files (or clones them, where the filesystem supports it) | Hard-links them |
| Downtime | Grows with the database's size, unless cloned | Minutes at most, whatever the size |
| Free disk | About the database's size | Little |
| Undo | Switches back to PostgreSQL 16, which is kept stopped: seconds | Restores PostgreSQL 16 from the backup at the Mark saved just before the upgrade |
| Lost by undo | Nothing is deleted: what was written to 18 stays in 18, kept aside | What was written after the upgrade is gone from the live database |

Rowsafe recommends Safe mode when there is disk for it.

### Undo, and remove the old version

For 7 days, the **Updates** tab shows **Undo upgrade**, and Pulse shows **PostgreSQL 16 is kept so you can undo the upgrade** with **Remove PostgreSQL 16**.

- **Undo** (Safe): stops PostgreSQL 18, switches the port back and starts PostgreSQL 16. PostgreSQL 18, with anything written to it since the upgrade, is kept aside, stopped.
- **Undo** (Fast): stops PostgreSQL 18, restores PostgreSQL 16 from the backup at the Mark saved before the upgrade, replays it to that Mark and starts it. Anything written after the Mark is not in it.
- Rowsafe saves a Mark first, so what was written to PostgreSQL 18 stays recoverable.
- After either, Rowsafe moves the backups back to PostgreSQL 16, takes a full backup and runs Proof.
- **Remove** deletes the version kept aside (`pg_dropcluster`), and its programs when no other cluster uses them. Rowsafe removes it by itself after 7 days.

```sh
rowsafe upgrade undo app
rowsafe upgrade cleanup app
```

## Limits

- **Debian and Ubuntu, PostgreSQL from packages.** Rowsafe installs packages with apt and upgrades clusters with Debian's `pg_upgradecluster`, so the cluster must be one `pg_lsclusters` lists, run by its `postgresql@16-main` unit. Elsewhere, Check and Rehearse still work where the new major's programs are installed.
- **Docker.** Rowsafe can't change your container's image. Check shows the steps (a one-off `pg_upgrade` container, then the new image tag), and the rehearsal works if the agent's image has the new major's programs. For minor updates, pull the newest image of the same major and recreate the container.
- **Extensions** must come as packages for the new major. Extensions you built yourself block the upgrade until you install them for the new major.
- **Replicas** that stream from the upgraded server have to be set up again: a major upgrade changes the data files.
- **Tablespaces** are upgraded, but Fast mode isn't offered with them (its undo couldn't restore them).
- **Going back before the upgrade** (Rewind to a time before it) needs the old major's programs: keep the old version until you're sure. Removing it removes them too.
- **Automatic updates** only install minor releases; never a major upgrade and never security updates of the server.

## How it works

The agent runs as `postgres` and can't install anything. Updates go through a small root helper, `/usr/local/lib/rowsafe/rowsafe-pg-restart`, run by `rowsafe-pg-update.service` when the agent writes a request to `/var/lib/rowsafe/restart/update-request`. The helper reads the request as the `postgres` user, accepts only a fixed list of requests (install PostgreSQL N's minor release, install major N for a cluster, upgrade, undo, remove the kept version, install security updates, reboot), checks each against root's `/etc/rowsafe/updates-allowed` and `/etc/rowsafe/restart-allowed`, and builds the package names itself: it never runs a command it was sent. See the [security model](/docs/security).

<Accordions>
<Accordion title="Do it yourself: upgrade by hand">
  The same steps Rowsafe runs, on the server, as root. Take a Mark and wait for a backup first.

  ```sh
  sudo apt-get install postgresql-18 postgresql-client-18    # plus postgresql-18-<extension> for each extension
  sudo pg_dropcluster --stop 18 main                          # the empty cluster the package created
  sudo pg_upgradecluster -v 18 -m upgrade 16 main             # --link for Fast mode
  sudo -u postgres pgbackrest --config=/etc/rowsafe/pgbackrest/app.conf --stanza=app \
    --pg1-path=/var/lib/postgresql/18/main stanza-upgrade
  rowsafe verify app && rowsafe backup app                  # from your workstation
  ```
</Accordion>
